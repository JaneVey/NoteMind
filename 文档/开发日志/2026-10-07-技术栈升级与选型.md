### 1.3 三个真实踩坑

**踩坑 1 — Boot 4 迁移到 Jackson 3，包名整体变更**

Jackson 3 的 groupId 由 `com.fasterxml.jackson` 变为 `tools.jackson`。
原 `WebMvcConfig` 中的 `JavaTimeModule` 导入失效，这是升级后**唯一的编译错误**。

处理方式**不是改包名，而是删除该 Bean**，因为自定义 `ObjectMapper` 会**覆盖 Spring Boot 的自动配置**，导致 `spring.jackson.*` 与其他 starter 注册的序列化模块全部失效。
Boot 默认已关闭时间戳序列化，字段级格式用 `@JsonFormat` 注解即可。

**踩坑 2 — Tika 4.x 的 `tika-parsers-standard-package` 没有 jar**

构建报 `Could not find artifact ... jar:4.1.0`。经 HEAD 请求逐一验证：

| 版本 | pom | jar |
|------|-----|-----|
| 4.1.0 | ✅ | ❌ 404 |
| 4.0.0 | ✅ | ❌ 404 |
| 3.3.2 | ✅ | ✅ |

Tika 4.x 起该 artifact 变为 **pom 聚合包**，解析器拆分为多个 module。**决策：锁定 3.3.2**。

**踩坑 3 — Spring AI 2.0 改用官方 OpenAI Java SDK**

依赖树显示拉入了 `com.openai:openai-java-core:4.49.0`（约 53MB），从自建 WebClient 改为使用官方 SDK。遇到问题时应优先查阅 2.0 文档。

## 二、关键技术决策

### 2.1 Embedding 维度定为 1024（并已修改 schema）

原 `init.sql` 写死 `VECTOR(1536)`，而开发阶段选用的模型是 1024 维，**存在冲突**。

选定 1024 的理由是"**免费/低价模型在 1024 维上交汇**"：

| 模型 | 维度 | 成本 |
|------|------|------|
| 硅基流动 `BAAI/bge-m3` | 1024 | **无限免费** |
| 硅基流动 `Qwen3-Embedding-0.6B` | 1024 | 免费额度 |
| 阿里云百炼 `text-embedding-v3` | 1024（默认） | 新用户免费额度 |
| 本地 Ollama `bge-m3` | 1024 | 免费 |

**已同步修改**：`init.sql` 的 `VECTOR(1024)`、`application.yml` 的 `embedding-dimension`、数据库设计文档。

> 现在修改成本为 1 行；有数据之后修改 = 全库重新解析入库。**必须在 RAG 预研（11 月）前完成**，本次已处理。

### 2.2 Embedding 供应商：硅基流动

**核实结论：硅基流动是模型聚合平台，一个 API Key 覆盖 chat / embedding / rerank**，完全 OpenAI 兼容，`base_url` 为 `https://api.siliconflow.cn/v1`。

| 特性 | 对本项目的价值 |
|------|--------------|
| 一个 Key 覆盖三类模型 | 开发阶段只需配一处密钥 |
| OpenAI 兼容 | 直接用 Spring AI 的 OpenAI 模块，无需专用适配 |
| `bge-m3` 无限免费 | 毕设用量零成本 |
| `bge-reranker` 免费 | P1 精排环节零成本 |
| 国内直连 | 无需代理，答辩演示稳定 |

**开发阶段组合**：对话用 DeepSeek，向量化用硅基流动。

### 2.3 向量索引策略调整

原 `init.sql` 使用 `ivfflat ... WITH (lists = 100)`。**该配置在本项目规模下有害**：

- ivfflat 需先有数据再建（要对数据聚类）
- 几千行规模下每簇不足 100 行，**召回率反而下降**

**决策：开发阶段不建向量索引**，数据量增长后（如 > 1 万块）再启用 **HNSW**（无需训练、小数据量表现好）。
已同步修改 `init.sql` 与数据库设计文档。

### 2.4 `ai_config` 表结构调整（已决策，待实施）

现有表结构一行同时装 chat 与 embedding，并用 `UNIQUE(user_id, provider_name)` 约束，**无法表达"对话用 DeepSeek、向量化用硅基流动"**——而这正是实际需求。

调整方向：新增 `role`（`chat` / `embedding`）与 `dimensions` 字段，`chat_model` / `embedding_model` 合并为 `model`，唯一约束改为按角色区分。详见 [[技术栈选型]] 第 5.4 节。

### 2.5 部署与备案澄清

**租服务器本身不需要备案，备案的对象是"域名"。**

| 场景 | 是否需备案 |
|------|-----------|
| 大陆节点 + 仅 IP 访问 | ❌ 不涉及（但 80/443 受限，无 HTTPS） |
| 大陆节点 + 绑定域名 | ✅ 必须备案（约 2–3 周） |
| **香港 / 海外节点 + 域名** | ❌ **完全免备案** |

**决策：使用香港 / 海外轻量节点**，当天开通、可绑域名、可上 HTTPS、免备案。

### 2.6 其他定稿决策

| 项 | 决策 |
|----|------|
| 框架基座 | **不换若依**（RuoYi-Vue-Plus 是多租户后台管理脚手架，与本项目重合度极低）；转为阅读 `ruoyi-rag` / `ruoyi-ai` 源码学习 RAG 实现 |
| SSE vs WebSocket | **SSE**。前端继续用 `fetch` + `ReadableStream`（**不能用 `EventSource`**，它无法携带 JWT 头） |
| 桌面端 | **不做**。难点在依赖栈（PG+pgvector/Redis/MinIO 无法本地化），且对论文零增益 |
| 第三方 RAG 平台 | **不作为主链路**，但保留为论文对比实验基线 |
| OCR | **砍掉**，改为"扫描件检测 + 标记失败" |
| 文档格式 | P0：MD / TXT / PDF；P1：Word；P2 砍：PPT |
| RAG 实现 | **检索层自研**（分块 / SQL / Top-K / 引用溯源），**模型层复用** Spring AI；**不用 `PgVectorStore`**（表结构与 `knowledge_chunk` 冲突） |
| 实验设计 | 三层：消融实验（必做）+ 有无对比（必做）+ Dify 外部基线（加分） |
