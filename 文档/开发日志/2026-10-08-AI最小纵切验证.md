## 二、五个真实发现（论文素材）

### 发现 1：Spring AI 2.0.1 **确实**支持思考链（先前担心是多余的）

社区中有多个 Issue 反映 `reasoningContent` 恒为 null
（[#6375](https://github.com/spring-projects/spring-ai/issues/6375)、
[#3954](https://github.com/spring-projects/spring-ai/issues/3954)、
[#2283](https://github.com/spring-projects/spring-ai/issues/2283)），
对应的修复 PR 为 [#6382](https://github.com/spring-projects/spring-ai/pull/6382) 与
[#6373](https://github.com/spring-projects/spring-ai/pull/6373)（流式对齐）。

**为确认这些修复是否已进入我们使用的 2.0.1，直接反编译了 jar 字节码**：

```
private static final String REASONING_CONTENT = "reasoningContent";   // 元数据键名
private String getReasoningContent(ChatCompletion$Choice);            // 依次尝试
    → additionalProperties.get("reasoning_content")   // DeepSeek 风格
    → additionalProperties.get("reasoning")           // OpenAI 风格
OpenAiChatModel$ChunkMerger 中存在 accumulatedReasoning              // 流式分片合并
```

**结论**：2.0.1 已包含修复，无需换用专用 DeepSeek 模块，也无需自行解析 HTTP 响应。

> **读取方式**：`response.getResult().getOutput().getMetadata().get("reasoningContent")`

### 发现 2：流式与非流式下，思考链的返回行为**不一致**（最大的坑）

对硅基流动的 `deepseek-ai/DeepSeek-V4-Flash` 实测：

| 请求方式 | `reasoning_content` |
|---|---|
| **非流式** | ✅ 默认就返回 |
| **流式** | ❌ **默认完全不返回**，必须显式传参 |

流式下各参数的有效性：

| 参数 | 思考分片数 | 结论 |
|------|-----------|------|
| 不传 | **0** | ❌ 拿不到 |
| `thinking: {type: "enabled"}` | 22 | ✅ **有效**（DeepSeek 官方写法） |
| `enable_thinking: true` | 82 | ✅ 有效（Qwen 系列写法） |
| `include_reasoning: true` | 0 | ❌ 无效 |

**这一条如果不知道，会直接卡住**：代码没错、框架没错、模型也有思考，
但流式下就是拿不到 —— 因为缺少一个平台特有的参数。

### 发现 3：`reasoning_effort: "high"` 会**关闭**思考（反直觉）

| 请求 | `reasoning_tokens` |
|------|-------------------|
| 非流式，不传 effort | 23（有思考） |
| 非流式，`reasoning_effort: "high"` | **0（思考被关闭）** |
| 流式，`reasoning_effort: "low"` | 有思考（37 分片） |

「提高思考强度」的参数反而让模型不再思考。**因此本项目默认不设置 `reasoning-effort`**，
改为通过 `extraBody` 传供应商文档定义的思考开关。

### 发现 4：Vite 开发代理**不关闭** SSE 连接

| 链路 | 首字节 | 总耗时 | 连接关闭 |
|------|--------|--------|---------|
| 直连后端 8080 | 1.19s | **2.70s** | ✅ 正常关闭 |
| 经 Vite 代理 5173/5174 | 1.52s | **25s+**（打满 `--max-time`） | ❌ **不关闭** |

**后端是正确的**（发出 `done` 后即关闭流），问题在开发代理。

**这直接暴露了原 `sse.ts` 的致命缺陷**：它只在「流关闭」时调用 `onDone()`。
经 Vite 代理时流永不关闭，因此**界面会永远停在"生成中"**。
新实现显式监听 `done` 事件并主动 `reader.cancel()`，因此不受影响。

> 生产环境用 Nginx，需按 [[技术栈选型]] 第七节配置
> `proxy_buffering off; proxy_read_timeout 300s;`，否则流式输出会被缓冲成一整块。

### 发现 5：路由守卫的开发环境放行，掩盖了鉴权问题

**现象**：在验证页上看到「未登录或登录已过期」，第一反应是"登录功能还没做"。

**真实原因**：登录功能**早已完成**（后端 8/8 验证通过，前端 `Login.vue` / `authStore` 齐备），
问题出在路由守卫的第一段代码：

```ts
if (import.meta.env.DEV) {
  next()      // 开发环境直接放行，从不引导去登录
  return
}
```

**后果是一个很隐蔽的组合**：

| 层 | 行为 |
|----|------|
| 前端路由 | 开发环境放行 → **页面能进** |
| 后端接口 | Spring Security 一律要求 JWT → **返回 401** |

于是用户看到页面正常打开、接口却报未登录，**既不知道要去登录，也误以为登录没实现**。

**另外它还有两个代价**：开发阶段无法验证真实登录流程；鉴权相关的 bug 会被长期掩盖。

**修复**：移除开发环境放行（用户系统后端已完成，没有理由绕过）；
同时补充 `redirect` 查询参数 —— 被拦截时记住原目标，登录后回到该页面而不是一律跳首页，
并对 redirect 做站内路径校验，避免被构造成开放重定向。

**顺带补齐**：`utils/sse.ts` 此前不处理 401（只把错误文案显示出来），
现与 axios 链路一致 —— 收到 401 时清除本地 Token 并跳转登录页。
两条链路的 401 行为统一到 `api/request.ts` 的 `redirectToLogin()` 一处实现。

> **可提炼的工程经验**：为了"开发方便"而在鉴权链路上开的口子，
> 会把"没有权限"变成一个看起来像"功能没做"的现象，排查成本远高于它节省的便利。

## 三、Spring AI 2.0 的 API 变更（踩坑记录）

| 项 | 1.x 写法 | 2.0 正确写法 |
|----|---------|-------------|
| 传请求参数 | `options(chatOptions)` | **`options(ChatOptions.Builder)`** —— 收的是 Builder，不是构建好的对象 |
| 读 Generation 元数据 | 当作 `Map` | `ChatGenerationMetadata`，用**泛型 `get(String)`**，不是 Map |
| OpenAI 模块底层 | 自建 WebClient | 改用**官方 OpenAI Java SDK**（`com.openai:openai-java-core`） |

供应商特有参数通过 **`OpenAiChatOptions.Builder.extraBody(Map)`** 传递 ——
这是兼容各平台差异的关键入口。

### 设计要点

**1. 为什么把思考参数做成配置项而不是写死**

`thinking` 与 `enable_thinking` 是不同供应商的写法。做成配置项后，
后续接入 `ai_config` 表时可由用户配置驱动，无需改代码。

**2. 思考分片增量计算**

框架内部存在累积逻辑的可能，因此 `ReasoningDelta` 同时兼容两种上游行为：
新值以已发送内容为前缀则只取增量，否则视为独立增量。
**实测结论：硅基流动返回的是真正的增量**（`[我们]` `[需要]` `[用]`…），
累积分支未被触发，但保留它可避免更换供应商时出现思考内容疯狂重复。

**3. 顺序保证**

用 `concatMap` 而非 `flatMap` —— `flatMap` 不保证顺序，会导致文字乱序。

**4. 错误不抛出**

流式过程中出错时发出 `type=error` 事件而不是抛异常，
否则前端只看到连接被切断、拿不到失败原因。
