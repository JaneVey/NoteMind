## 一、解决"每开新会话就要重新解释项目"的问题

### 1.1 问题

用户原话：

> "你现在是把规范文档写进了我定的文件夹。但是我不想每次开个新窗口开始开发，你就又忘了，
> 所以你有什么办法解决这个问题吗？（Codex 有 AGENT，ClaudeCode 有 Claude，你有没有相应的 md 文件？）"

这是一个**真实的工程问题**，不只是"助手记性差"：
规范写了 5 份文档、几千行，但每个新会话的助手都从零开始，
于是"规范"退化成"需要人反复口头提醒的东西"。

### 1.2 调研结论（没有猜，查了实现）

DSH 的实现里有一个专门的插件：`@deepseek-ai/dsh-agent-instructions`。

```js
const DEFAULT_INSTRUCTION_FILE_CANDIDATES = ["AGENTS.md", "CLAUDE.md"];
```

**它按「从宽泛到具体」加载三层，每个新会话自动注入为持久上下文：**

| 层级 | 路径 | 作用域 |
|------|------|--------|
| 用户全局 | `$DSH_HOME/AGENTS.md`（即 `C:\Users\JanVey\.dsh\AGENTS.md`） | 对所有项目生效 |
| **项目根** | `NoteMind/AGENTS.md` | 本项目 ← **我们要的** |
| 子目录 | 任意子目录的 `AGENTS.md` | 只有助手碰到该目录的文件时才加载 |

补充机制：

- 还支持 `AGENTS.local.md` / `CLAUDE.local.md` 作为**个人覆盖层**（不提交）
- 同一目录下 `AGENTS.md` 与 `CLAUDE.md` **内容相同时只加载一次**（去重）
- 项目根由 `.git` 等标记识别
- **外部编辑不会立即生效**（没有文件监听），会在下一次成功的 `read`/`write`/`edit` 时刷新
- 有 **token 预算**：部署侧配置为 `maxBytes: 65536`（64 KB）。
  超预算时**先丢弃宽泛文件、截断最具体的文件**

### 1.3 落实

新建 `AGENTS.md`（项目根），**135 行 / 7388 字节 —— 仅占预算 11%**，不会被截断。

> 实测验证：文件写入后，当前会话立刻收到了 `system-reminder` 形式的注入，
> 内容正是 `AGENTS.md`。**机制确认可用。**

内容设计原则：**只放「必须记住的铁律 + 去哪看细节」，不抄规范全文。**

理由（也是关键设计判断）：既然有 token 预算且超限会截断，
那么把 5000 行规范塞进去反而**更不安全** —— 一旦超限，丢掉的是后面的规则，
而人不会知道丢了什么。**精炼 + 导航 比 完整 + 超限 可靠。**

包含：
- 10 条铁律，**每条都标注了对应的真实踩坑**（不是凭空立的规矩）
- 文档导航表（详细内容去读哪份文档）
- 本机环境与常用命令（含 Redis 用 6380 这种容易忘的细节）
- 当前状态与下一步
- 协作约定（含"每解决一个问题追加到问题台账"）
- **已知的坑**清单（PowerShell 大小写、CRLF、`Select-Object -First` 掐管道、
  `jar xf` 污染目录等工具链陷阱）

### 1.4 一个附带收获

这套机制**不是 DSH 特有的** —— `AGENTS.md` 是跨工具约定（Codex、Cursor 等都用同名文件）。
将来换工具，这份文件依然有效。

## 二、问题台账（`文档/08-问题记录/问题台账.md`）

用户原话：

> "最好创建一个文件夹，把开发过程中我遇到/发现的问题，以及你遇到/发现的问题，
> 都可以用一个文档来记录，这个东西对以后的论文答辩，以及面试提问，这些都有帮助。"

这个判断是对的：**问题排查过程是答辩与面试中最能体现工程能力的内容**，
而它恰恰是最容易随时间失真的（"当时那个报错是什么来着"）。

### 2.1 归档结果

共 **61 条**，分 6 类：

| 分类 | 数量 | 典型 |
|------|------|------|
| A 环境与工具链 | 14 | Boot 3.5 已停止维护、Tika 4.x 无 jar、CRLF 让正则失效 |
| B 框架与依赖 | 9 | MinIO bucket 静默未创建、流式与非流式思考链行为不一致 |
| C 数据库 | 7 | VECTOR 维度不符、级联删除与逻辑删除语义冲突、timestamptz 类型不匹配 |
| D 前端 | 10 | SSE 靠"流关闭"判断结束而永卡、路由守卫 DEV 放行掩盖鉴权 |
| E 安全 | 11 | API Key 入库、CORS 通配 + 凭据、未认证返回 403 |
| F 架构与流程决策 | 10 | 概念多名分裂、横向分层 vs 纵向切、范围恐慌 |

每条含四列：**现象 / 根因 / 解决 / 可讲的点**。
最后一列是专门为答辩与面试准备的"一句话总结"。

### 2.2 重点问题详解（6 个）

选取标准不是"严重程度"，而是**是否体现排查方法与工程判断**：

1. **MinIO bucket 从未创建** —— 异常被 `catch` 吞掉造成静默失效。
   危害不是"报错"而是**让人以为一切正常**。
2. **TIMESTAMPTZ 与 LocalDateTime 不匹配** —— 编译通过、启动正常、日志无警告，
   **只在读该字段时报 500**。跨"编译期/启动期/运行期"三层检查的问题。
3. **删除笔记本静默丢数据** —— 记录了**有意偏离《阿里巴巴 Java 开发手册》**的完整理由，
   以及答辩时可以怎么表述。
4. **路由守卫的 DEV 放行** —— 把"没有权限"伪装成"功能没做"，
   体现"为开发方便绕过鉴权链路"的代价。
5. **流式与非流式模型行为不一致** —— 完整记录了排查路径：
   先排除自己的代码 → 再排除框架（反编译 jar）→ 最后用最原始方式（curl）问服务本身。
6. **范围恐慌** —— 把 5 件难度差 10 倍的事统称为 "Agent"。
   结论：**动摇的不是方案，是对方案的信心。**

## 三、前端任务 1：目录调整与类型重构

### 3.1 类型定义按领域拆分

原 `types/domain.ts`（81 行）拆为 5 个文件：

```
types/common.ts     Id / IsoDateTime / ApiResponse / PageResult / PageQuery
types/user.ts       UserInfo / LoginResponse / UpdateProfileRequest ...
types/note.ts       Notebook / Folder / Note / NoteLink / 图谱类型
types/knowledge.ts  KnowledgeBase / KnowledgeDocument / ChunkSourceInfo ...
types/ai.ts         Conversation / ChatMessage / AiConfig / ChatStreamChunk ...
```

**同时移除了全部 `[key: string]: unknown` 索引签名**，并收敛三组重复的对冲字段。

> **实测结果出乎意料地好**：移除全部索引签名后，**整个前端只暴露出 14 个类型错误**。
> 这说明这些签名**从来不是真的需要** —— 它们没有"兼容不确定性"，
> 只是让 TypeScript 完全失去了保护作用，同时逼迫调用方到处写 `??` 兜底。
>
> 这是一个可以量化的结论，已写进《前端开发规范》。
> 那 14 个错误全部是"对冲字段被真正使用"的位置，逐个修正后 typecheck 归零。

其它类型修正：

- `DocumentStatus` 由 7 个值收敛为 4 个（此前把 `completed`/`done`/`parsed` 同义词全列上）
- `LoginResponse` 移除 `user?: Partial<UserInfo>` 兼容分支 ——
  它导致 `authStore` 里写满了 `data.userId ?? data.user?.userId ?? null` 的三重兜底
- 新增 `KnowledgeDocumentDetail`：列表接口不返回正文
  （一本 PDF 几十万字，列表一次 20 条会传几 MB 而 99% 用不到）

### 3.2 清理死代码

### 3.3 新增 `composables/` 与 `utils/format.ts`

**`composables/useDropdown.ts`** —— 下拉菜单开关 + 点击外部关闭。

`Notebook.vue` 里有 **10 处以上**各写一份的重复实现（`showXxxMenu` ref +
`xxxMenuRef` + 各自的 `document.addEventListener`），这是收益最大的抽取点。

实现上的两个判断：

1. **文档级监听器全局只挂一个**，用模块级注册表统一管理 ——
   如果每个下拉各加一个 listener，页面上 10 个下拉就有 10 个文档监听器，
   每次点击都要跑 10 次 `contains()` 判断
2. **用捕获阶段**，保证先于触发按钮自身的 `click` 处理器执行，
   使「点 A 打开时自动关闭 B」与「点自身切换开关」两种行为都正确

> **自查时发现并修掉了自己的两个缺陷**（记账在此，因为它体现了自查的价值）：
> ① `entry.close` 未从注册表注销 —— 只关了面板，条目会一直留到组件卸载；
> ② `rootRef.value as HTMLElement` 在 ref 为空时会抛 `TypeError`，
> 改为 `HTMLElement | null` 并在遍历时守卫。

**`utils/format.ts`** —— `formatDateTime` / `formatRelativeTime` / `formatFileSize` /
`formatWordCount` / `truncateFileName` / `formatClock`。

设计依据：后端接口一律返回 **ISO-8601 带时区偏移**的值（无歧义，可被 `new Date()` 正确解析），
而"显示成什么样"属于**展示职责**。

### 3.4 `KnowledgeDetail.vue`

- 字段名跟随类型修正：`name`→`fileName`、`type`→`fileType`、`size`→`fileSize`、
  `status`→`chunkStatus`、`content`→`rawContent`
- 用 `formatFileSize` 替换自实现的 `formatSize`
- **上传时间此前直接渲染 `createdAt`**，会把 `2026-10-08T22:05:20+08:00` 原样显示给用户，
  改为 `formatDateTime`
- 补上解析失败时的 `errorMessage` 展示 —— 否则用户只知道"失败了"却不知道为什么

## 四、前端任务 2：拆分两个大文件

| 文件 | 原行数 | 问题 |
|------|--------|------|
| `views/AIChat.vue` | 1389 | 一屏逻辑全在一个文件 |
| `views/Notebook.vue` | 1125 | 同上，且含 10+ 处重复的下拉逻辑 |

### 4.1 拆分方案

由两个子代理并行执行（目标目录不重叠）：

```
views/aichat/                 views/notebook/
├── ConversationList.vue      ├── NotebookSidebar.vue
├── MessageList.vue           ├── NotebookTree.vue
├── MessageItem.vue           ├── NoteEditor.vue
├── ReasoningPanel.vue        ├── EditorToolbar.vue
└── ChatComposer.vue          ├── FindPanel.vue
                              └── NoteAiPanel.vue
```

`AIChat.vue` / `Notebook.vue` 保留为**页面容器**：只做数据获取与状态编排，
子组件通过 props / emits 通信。目标：各自降到 400 行以内。

> 为什么不顺手一起做：这是一次**纯结构性重构**，行为与视觉必须完全不变。
> 与功能改动混在一起，出问题时无法判断是哪一边引起的。
