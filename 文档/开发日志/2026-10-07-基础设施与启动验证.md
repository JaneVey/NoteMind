### Docker 数据实际存放位置（重要，此前未记录）

**数据不在 `D:\docker-data`，而在 WSL2 的虚拟磁盘里。**

Docker Desktop 配置了 `CustomWslDistroDir = D:\Docker\DockerDesktopWSL`，因此：

```
D:\Docker\DockerDesktopWSL\disk\docker_data.vhdx    22.51 GB   ← 镜像 / 容器 / 命名卷全在这里
D:\Docker\DockerDesktopWSL\main\ext4.vhdx            0.10 GB
```

本项目使用**命名卷**（`notemind_pgdata` / `notemind_miniodata` / `notemind_redisdata`），
在容器内的路径是 `/var/lib/docker/volumes/<卷名>/_data`，物理上位于上述 `docker_data.vhdx` 内。

**`D:\docker-data` 是旧方案的残留**（早前用 `-v D:\docker-data\...` bind mount 时的约定），当前 compose 不使用它：

| 子目录 | 大小 | 说明 |
|--------|------|------|
| `xinyang\mysql\db_mental\` | 220 MB | **另一个项目**（心理健康系统）的 MySQL 数据，**不要动** |
| `NoteMind\postgres-data\` | 67 MB | 旧 NoteMind 的 PG 数据目录，**已孤立**，确认无需后可删 |
| `MinIO\` | 12 MB | 旧 MinIO 数据，已孤立 |
| `Redis\` | 18 KB | 旧 `dump.rdb` |

> **为什么用命名卷而不用 bind mount 到 `D:\docker-data`**：
> Windows 上 PostgreSQL 通过 bind mount 会经过 NTFS ↔ WSL2 的文件系统转换，
> 而 PG 对 `fsync` 与文件权限敏感，性能明显下降且易出权限问题。
> 命名卷走 WSL2 原生文件系统，更快更稳。而"数据不占 C 盘"这一目标已经达成——数据盘本身就在 D 盘。

## 二、本次修复的问题

### 2.1 MinIO bucket 从未被创建（静默失效的 bug）🔴

**现象**：启动日志只有一行 warn「MinIO bucket check failed (may not be connected yet)」。

**真实原因**：`MinioConfig` 在 `@PostConstruct` 中调用本类的 `@Bean minioClient()` 方法。
`@Configuration` 类被 CGLIB 代理，这种**自调用**会尝试在 `minioConfig` Bean 尚未创建完成时
再次获取它，抛出：

```
Error creating bean with name 'minioConfig': Requested bean is currently in creation
```

而该异常被 `catch (Exception e)` 吞掉。**结果：bucket 从未被创建或校验过，但日志看起来"正常"，
直到真正上传文件时才会报错。**

**修复**：改用 `ApplicationRunner`（容器刷新完成后执行），`MinioClient` 通过方法参数注入而非自调用；
失败日志级别由 warn 提升为 **error** 并带上 endpoint，使"MinIO 没起来"一眼可见。

**验证**：重启后日志显示 `MinIO bucket 'notemind' 创建成功（endpoint=http://localhost:9000）`。

### 2.2 CORS 配置是真实的安全漏洞 🔴

原配置同时设置 `allowedOriginPatterns("*")` 与 `allowCredentials(true)`：
前者会**回显任何来源**，叠加后者后任意第三方站点都能发起携带凭据的跨站请求。

> Spring 之所以提供 `allowedOriginPatterns` 而 `allowedOrigins("*")` 会直接报错，
> 正是为了防止这种误用被无意识地写出来 —— 但这个防护被绕过了。

**修复**：改为**显式域名白名单**，从 `app.cors.allowed-origins` 读取（默认只允许本地前端端口），
生产环境通过 `APP_CORS_ALLOWED_ORIGINS` 注入真实域名。同时改由 Spring Security 的 `http.cors()` 统一处理，
避免原来的独立 `CorsFilter` 与 Security 过滤器链互相独立、预检请求被 Security 拦下。

### 2.3 缺少 401 EntryPoint

未配置 `AuthenticationEntryPoint` 时，Spring Security 对未认证请求返回 **403**。
这会让前端无法区分"未登录"与"无权限"。

**修复**：新增 `RestAuthenticationEntryPoint`（401）与 `RestAccessDeniedHandler`（403），
响应体与业务接口的 `Result` 结构一致（`{code, message, data}`）。
JSON 采用手写方式而非注入序列化器：该逻辑运行在过滤器链早期，且 Spring Boot 4 使用 Jackson 3
而类路径仍残留 Jackson 2（由 jjwt-jackson 间接引入），在此处引入序列化器会造成两个版本混用。

### 2.4 异常响应的 HTTP 状态码与业务 code 不一致

原实现混用两种风格：`BusinessException` 不带 `@ResponseStatus` → **HTTP 200 + body code=401**；
而 `UnauthorizedException` 等带 `@ResponseStatus` → HTTP 401。同一语义两种状态码。

**修复**：`GlobalExceptionHandler` 统一改为 `ResponseEntity`，**HTTP 状态码由业务 code 映射得出**，
两者始终一致。响应体结构保持不变。

### 2.5 `LoginUser` 是死代码，且主体类型不当

`LoginUser` 实现了 `UserDetails`，但全项目只有它自己引用自己。
实际链路是 `JwtAuthenticationFilter` 往 SecurityContext 放入一个**裸 `Long`**，
再由各 Controller 写 `(Long) authentication.getPrincipal()` 强转取值（`UserController` 中 3 处）。

**修复**：

- `JwtAuthenticationFilter` 改为放入完整的 `LoginUser`（由 JWT 的 `sub` 与 `username` 声明构造，**不查库**）
- 新增 `SecurityUtils`，业务代码统一用 `SecurityUtils.currentUserId()`，不再手写强转
- `JwtUtils` 新增 `parseClaims()`，过滤器一次解析完成校验与取值（原先"先 validate 再 parse"会解析两次）

### 2.6 删除冗余的 `SpringAiConfig`

该类手写了一个 `ChatClient.Builder` Bean，但 Spring AI 2.0 已通过
`spring-ai-autoconfigure-model-chat-client` 自动配置该 Bean，属重复定义。
删除后还带来一个额外好处：**应用在未配置 AI Key 时也能正常启动**。

### 2.7 密码修改缺少参数校验

`UpdatePasswordRequest` 没有任何校验注解，`@Valid` 形同虚设
（原 `UserController` 甚至没加 `@Valid`）。已补 `@NotBlank` 与 `@Size(min = 6, max = 64)`，
并新增"新密码不能与旧密码相同"检查。

### 2.8 前端 401 处理

`request.ts` 原先完全没有 401 拦截。现已补齐，并区分两类 401：

| 场景 | 处理 |
|------|------|
| 会话过期（非 `/auth/**` 接口返回 401） | 清除本地 Token 并跳转登录页 |
| 凭据错误（`/auth/login`、`/auth/register` 返回 401） | **不触发登出**，交由页面展示错误 |

> 若不区分，用户在登录页输错密码会被提示"登录已过期"并清空状态，属明显的体验缺陷。
> 同时新增 `ApiError` 类型（携带 code），并把 `TOKEN_KEY` / `USER_KEY` 导出为常量。

### 2.9 Redis 改为容器化（修正此前的判断失误）

初次搭建环境时，为了让 Redis "避开端口冲突"，采用了**宿主机上已有的 Redis**。
这个判断是错的，核实后发现：

| 事实 | 证据 |
|------|------|
| 宿主机 Redis 是 **3.0.504** | 2015 年微软的 Windows 移植版，早已停止维护 |
| 以 **Windows 服务**方式安装 | `StartMode: Auto`，开机自启 |
| **存有另一个项目的数据** | `sys_dict:*`（**若依框架的字典缓存前缀**）、`personalityTypes::list`，共 33 个 key |

问题有三：**dev 用 3.0、部署用 `redis:7-alpine`，版本相差十年**；
NoteMind 与另一个项目**共用同一个 `db0`**，互相污染；
以及那个 Redis 是别人的，**不能停**（停了会影响另一个项目）。

**修正**：把 Redis 纳入 `docker-compose.yml`（`redis:7-alpine`，开启 AOF 持久化），
映射到宿主机 **6380** 以避开被占用的 6379；`.env` 中 `REDIS_PORT=6380`。
应用内运行时（compose 的 `app` 服务）仍通过服务名直连 `redis:6379`。

### 2.10 Redis 连接此前无法被验证（新增启动检查）

Spring Boot 的 Redis 自动配置是**懒连接**：启动时只创建 `RedisConnectionFactory`，
不会真正建立连接。因此 `spring.data.redis.*` 配错时**应用照样正常启动**，
直到第一次使用 Redis 才抛异常 —— 与此前 MinIO 那个"看起来正常、其实从未连上"的问题同类。

**新增 `RedisConfig`**，在启动后主动 ping 一次并把版本打进日志；连接失败不中断启动，
但以 **error** 级别告警（因为 Redis 承担限流与登录失败计数，失效会造成实际影响）。

**验证输出**：`Redis 连接成功：PING=PONG version=7.4.9`

## 四、本地启动步骤（长期参考）

### 首次准备

```powershell
# 1. 复制环境变量模板并填入 AI Key
#    JWT_SECRET 需要自己生成（openssl rand -base64 48）
copy .env.example .env

# 2. 启动三个依赖服务
docker compose up -d postgres redis minio
```

> 说明 1：`.env` 同时被 **Docker Compose** 与 **Spring Boot** 读取，一处配置两处生效。
>
> 说明 2：不要执行不带服务名的 `docker compose up -d` —— 它会同时尝试启动 `app` 服务，
> 而 `app` 需要先构建镜像（`mvn clean package` + Dockerfile）。
> 开发阶段后端在宿主机直跑（便于热重载），因此只需三个依赖服务。

### 端口一览

| 服务 | 宿主机端口 | 容器内端口 | 备注 |
|------|-----------|-----------|------|
| PostgreSQL | 5432 | 5432 | 仅绑 `127.0.0.1` |
| Redis | **6380** | 6379 | 仅绑 `127.0.0.1`；6379 被另一个项目的 Redis 3.0 占用 |
| MinIO S3 API | 9000 | 9000 | 仅绑 `127.0.0.1` |
| MinIO 控制台 | 9001 | 9001 | 仅绑 `127.0.0.1`，**切勿对公网开放** |
| 后端应用 | 8080 | — | 宿主机直跑 |
| 前端 Vite | 5173 | — | 宿主机直跑 |

### 启动后端

```powershell
cd backend
mvn spring-boot:run "-Dspring-boot.run.profiles=dev"
```

### 启动前端

```powershell
cd frontend
npm run dev
```

### 常用检查

```powershell
# 应用健康检查
curl http://localhost:8080/api/health

# 容器状态
docker compose ps

# 数据库表
docker exec notemind-postgres psql -U postgres -d notemind -c "\dt"

# 向量维度确认（应为 vector(1024)）
docker exec notemind-postgres psql -U postgres -d notemind -tAc `
  "SELECT format_type(atttypid, atttypmod) FROM pg_attribute WHERE attrelid='knowledge_chunk'::regclass AND attname='embedding';"

# Redis（注意端口是 6380）
docker exec notemind-redis redis-cli ping

# MinIO 存活
curl http://localhost:9000/minio/health/live
```

> 应用启动日志中应能看到两行确认：
> `MinIO bucket 'notemind' 已存在` 与 `Redis 连接成功：PING=PONG version=7.4.9`。
> **若看不到这两行，说明对应的连接没建立起来** —— 这正是此前被静默吞掉的问题。
