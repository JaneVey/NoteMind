## 二、开发流程决策（今日新增，此前未记录）

讨论中对原计划（[[02-MVP开发计划]]）的执行顺序做了修正。**原计划漏掉了一个关键环节，且第 4 阶段的切法有风险。**

### 2.1 修正后的流程

| 步骤 | 内容 | 状态 |
|------|------|------|
| 1 | 环境打通（PostgreSQL / Redis / MinIO / 启动验证） | ✅ 今日完成 |
| 2 | 基础设施（鉴权 / 各类连接 / 统一响应与异常） | ✅ 今日完成 |
| **2.5** | **AI 最小纵切验证（新增）** | ⬅ **下一步** |
| 3 | 前端骨架定稿（布局 / 路由 / 导航 / 触发点 / 接口签名） | 待办 |
| 4 | **按模块纵向打通**：笔记 → AI 助手 → 知识库/RAG → 设置 → 图谱·搜索 | 待办 |

### 2.2 为什么插入"步骤 2.5"

原计划从"基础设施"直接跳到"前端页面"，再跳到"逐个功能实现"，**把整个项目唯一未经验证的技术环节隐含地压进了最后阶段**。

风险：等前端骨架都建好、开始接 AI 时，才发现 Spring AI 2.0 的 API 用法不对 / 思考链字段拿不到 / SSE 在 Nginx 下被缓冲 —— **那时返工代价成倍增加**。

**步骤 2.5 的具体内容**：

> 实现一个接口：接收文本 → 调用模型（开启思考模式）→ 将 `reasoning_content` 与 `content`
> 分区块通过 SSE 推送 → 前端渲染为「思考过程（可折叠）+ 正文（流式吐字）」。

**验收标准**：思考过程与正文分区域正确显示、逐字流式、前端 `utils/sse.ts` 可正常消费。

**收益**：一次性消除四个未知数 —— Spring AI 2.0 API 可用性、思考链可行性、SSE 通路、前端流式接收。
做完后整个项目**没有技术黑箱**，后续工作性质从"趟雷"变为"写代码"。

### 2.3 为什么第 4 阶段要"纵向切"而不是"横向分层"

| 切法 | 做法 | 问题 |
|------|------|------|
| ❌ 横向 | 所有后端接口写完 → 再所有前端接线 → 最后集中联调 | **长期没有任何端到端可跑通的东西**，问题全部堆积到最后爆发，而那时时间最紧 |
| ✅ 纵向 | 按模块切：笔记模块（后端 CRUD + 前端接线 + 联调）一次做完即为**可演示状态**，再做 AI 助手，再做知识库 | 每个模块完成即可演示，风险分散 |

### 2.4 步骤 3 的范围限制

前端骨架阶段**只定**：布局、路由、导航层级、交互触发点、接口签名（可先 mock）。

**不要定**：每个交互的细节与数据形状 —— 因为 AI 层能返回什么（思考链字段、引用数据结构）尚未确定，此时定死必然返工。

## 七、今日经验（可直接用于论文"技术实现"与答辩）

今天抓到的**真实问题**，都是可以写进论文的素材，也是答辩时体现工程深度的内容：

| 问题 | 类型 | 价值 |
|------|------|------|
| Jackson 3 包名变更导致自定义 `ObjectMapper` 失效 | 框架迁移 | 说明"不要手写全家桶 Bean 覆盖框架自动配置" |
| Tika 4.x 的 `tika-parsers-standard-package` 变为 pom 聚合包（无 jar） | 依赖排查 | 版本选择必须验证产物，不能只看元数据 |
| **MinIO bucket 因 `@PostConstruct` 自调用从未被创建** | **静默失效** | 异常被 `catch` 吞掉导致"日志看起来正常"——最值得写的一类问题 |
| **Redis 懒连接导致配置错误无法在启动时暴露** | **静默失效** | 同上，两者构成一组很好的对照案例 |
| CORS `allowedOriginPatterns("*")` + `allowCredentials(true)` | 安全漏洞 | 典型配置错误，可结合 OWASP 论述 |
| 未配置 `AuthenticationEntryPoint` 导致未认证返回 403 而非 401 | 协议语义 | 说明前后端契约设计的重要性 |
| 业务异常 HTTP 200 + body code 401 与安全层 401 不一致 | 接口设计 | 说明"统一响应壳"与 HTTP 语义的取舍 |
| `ivfflat` 索引在小数据量下反而降低召回率 | 检索优化 | **论文实验章节可直接用**：索引策略与数据规模的关系 |
| Spring AI 与 Spring Boot 的版本矩阵硬约束 | 技术选型 | 说明选型不能只看单组件版本 |

> 建议：写论文时把这些整理成独立小节，比空泛描述"使用了 XX 技术"有说服力得多。
