# 可行性分析

> 项目：基于 RAG 的 NoteMind 智能知识管理平台
> 分析日期：2026-07-20（重构后更新）

---

## 项目概述

做一个融合 Obsidian 知识管理能力与 RAG 文档智能能力的 AI 知识管理平台。

**一句话定位**：笔记负责知识创造和沉淀，知识库负责知识理解和检索，AI 负责辅助整理、分析、生成。

**四大模块**：
1. **AI助手** — 类似 ChatGPT 首页的通用 AI 对话入口，支持可选知识库绑定、用户画像
2. **笔记系统** — 多仓库 Markdown 笔记创作，支持 AI 辅助写作、双向链接知识图谱
3. **知识库系统** — 独立文档管理 → RAG 智能问答，支持多格式上传和引用溯源
4. **设置** — AI 模型管理、Prompt 快捷指令、基础设置

## 技术可行性

### 技术难度评估

| 模块 | 掌握度 | 学习成本 | 风险 |
|------|--------|---------|------|
| Spring Boot 后端 | ✅ 熟悉 | 无 | 🟢 |
| Spring AI | ❓ 新框架 | 3-5 天 | 🟢 简化 AI 对接，降低维护成本 |
| Vue3 + Element Plus 前端 | ✅ 熟悉 | 无 | 🟢 |
| PostgreSQL + pgvector | ❓ 需学习 | 1-2 天（语法迁移） | 🟢 MySQL→PG 迁移成本极低 |
| MinIO 对象存储 | ❓ 需学习 | 1-2 天 | 🟢 S3 兼容 API，Spring Boot 集成简单 |
| Markdown 编辑器 | ❓ 需调研 | 2-3 天（Vditor 集成） | 🟢 有成熟开源组件 |
| SSE 流式输出 | ❓ 有 WebSocket 基础 | 1-2 天 | 🟢 SSE 比 WebSocket 更简单 |
| 多供应商 AI 接入 | ❓ 无经验 | 3-5 天 | 🟡 Spring AI 进一步简化，策略模式封装后复用 |
| RAG（Embedding + 向量检索） | ❌ 新领域 | 1-2 周 | 🟡 概念多但工程实现清晰 |
| OCR（图片/PDF 文字识别） | ❌ 新领域 | 2-3 天 | 🟡 可借助第三方 API（如阿里云 OCR） |
| MinIO 文件管理 | ❓ 需学习 | 1-2 天 | 🟢 接口简单，类似文件系统 |
| 知识图谱（双向链接） | ❓ 有了解 | 3-5 天 | 🟢 基于 Wikilink 解析，不涉及图数据库 |

**结论**：技术可行。新增的 Spring AI 和 MinIO 降低了原有难度，OCR 和知识图谱学习成本可控。

### 关于 Spring AI

重构后引入 Spring AI，原因：
- 提供统一的 AI 供应商抽象（避免手写策略模式轮子）
- 原生支持 SSE 流式输出
- 内置 Token 计算、Prompt 模板管理
- 活跃的社区维护

### 关于 MinIO

重构后引入 MinIO 替代本地文件存储：
- 标准 S3 兼容接口
- 与文档处理流程解耦
- 便于后续扩展（迁移、备份）

## 创新性分析

### 重构后的创新亮点

| 创新点 | 内容 | 可信度 |
|--------|------|--------|
| **笔记 + RAG 融合架构** | 笔记系统与知识库单向联动，笔记中写的内容可以直接成为知识库的 RAG 数据源 | ⭐⭐⭐⭐⭐ |
| **可配置 AI 能力（Prompt 快捷指令）** | 用户自定义 Prompt 指令，集成到右键菜单直接使用 | ⭐⭐⭐⭐ |
| **AI 辅助写作闭环** | 当前笔记对话 + 选中文字操作 + AI 直接修改笔记，三种 AI 参与形式 | ⭐⭐⭐⭐ |
| **Obsidian 双链知识图谱** | Wikilink 双向链接自动生成图谱，仓库级隔离 | ⭐⭐⭐⭐ |
| **多格式文档智能导入** | PDF/Word/图片 → AI 增强转换 → Markdown 笔记 | ⭐⭐⭐ |

### 论文重点

系统设计与技术实现 > 产品功能 > 理论创新。本科论文重点应放在：

1. RAG 引擎的设计与实现（核心创新）
2. 笔记 + 知识库融合架构设计（架构创新）
3. AI 辅助写作与可配置 Prompt 系统（功能创新）
4. 基于 pgvector 的语义检索方案（技术实现）

## 风险分析

| 风险 | 等级 | 说明 | 缓解措施 |
|------|------|------|---------|
| **RAG 效果不可控** | 🟡 中 | 检索质量差 → AI 回答不好 | 好分块策略 + 多路召回 + Top-K 灵活配置 |
| **Embedding API 费用** | 🟢 低 | DeepSeek/Gemini Embedding 价格低 | MVP 阶段用户自备 API Key |
| **LLM API 费用** | 🟡 中 | 多轮对话 + RAG 上下文消耗 | 用户自备 API Key，限制上下文长度 |
| **PostgreSQL 学习曲线** | 🟢 低 | 与 MySQL 语法差异 | 2 天内适应 |
| **Vditor 集成坑** | 🟢 低 | 国产开源组件可能有小 Bug | 三栏布局需较多定制，备选方案 ByteMD |
| **Spring AI 新框架风险** | 🟡 中 | 版本迭代快，API 可能变化 | 抽象层隔离，Spring AI 仅作 AI 调用封装 |
| **MinIO 运维成本** | 🟢 低 | 演示环境需额外容器 | Docker Compose 一键部署 |
| **OCR 实现复杂度** | 🟡 中 | 图片/PDF 文字识别准确率 | MVP 阶段先做 Markdown，OCR 作为 P1 |
| **知识图谱可视化** | 🟡 中 | 前端图形化展示较复杂 | 可选简单方案（D3.js/vis-network） |
| **学业/实习冲突** | 🟡 中 | 课程、实习任务挤占时间 | 合理规划，留 2 周缓冲 |
| **论文创新性质疑** | 🟡 中 | 答辩时被问"和已有产品区别" | 重点强调融合架构和 AI 辅助闭环 |

### 风险总体评估

**整体风险可控**。重构后增加了 MinIO 和 Spring AI 两个新依赖，带来一定的学习成本，但降低了 AI 对接的维护成本。建议 MVP 阶段先聚焦核心链路（笔记 + AI 助手 + RAG），OCR 和知识图谱作为增强特性。

## 推荐结论

### 综合评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 创新性 | ⭐⭐⭐⭐ | 融合架构 + AI 辅助闭环 + 可配置 Prompt，亮点清晰 |
| 工程价值 | ⭐⭐⭐⭐ | 完整 Web 全栈 + AI 架构，有工程参考价值 |
| 技术难度 | ⭐⭐⭐⭐ | RAG + 多格式文档处理 + 知识图谱，深度足够 |
| 实现难度 | ⭐⭐⭐ | 模块多但拆分清晰，单体架构控制复杂度 |
| 工作量 | ⭐⭐⭐⭐ | MVP 3-4 个月，12 张表，适合本科毕设体量 |
| 论文质量 | ⭐⭐⭐⭐⭐ | 几个创新点都能独立成章，论文素材丰富 |
| 答辩风险 | ⭐⭐⭐ | 重构后创新点更多，但需要准备好实现细节 |
| 推荐程度 | ⭐⭐⭐⭐⭐ | **强烈推荐作为本科毕业设计选题** |

### 优点

1. 重构后模块划分更加清晰、功能闭环完整
2. 多个可独立成章的技术创新点，论文好写
3. 技术栈与个人发展方向高度匹配（Java 后端 + AI）
4. 可作为简历项目，综合展示工程能力和 AI 应用能力
5. 覆盖的技术面广（RAG、向量检索、AI 对接、文件处理、知识图谱）

### 缺点

1. 需要学习的新技术较多（Spring AI、MinIO、OCR）
2. RAG 效果不确定性需要预留调试时间
3. 依赖第三方 AI API 和外部 OCR 服务，演示时需要网络

### 主要风险

1. 时间管理（实习 + 课程并行）
2. RAG 检索质量调优
3. 知识图谱可视化前端实现难度

### 是否推荐

**强烈推荐**。重构后的方案相比第一版更加完整、模块划分更清晰、创新点更有说服力。关键是要做好模块优先级排序，按 MVP 思路逐步推进。
