### 1.3 三个真实踩坑（论文"技术实现"章节素材）

#### 踩坑 1：Boot 4 迁移到 Jackson 3，包名整体变更

Jackson 3 的 groupId 由 `com.fasterxml.jackson` 变为 **`tools.jackson`**。
原 `WebMvcConfig` 中的 `com.fasterxml.jackson.datatype.jsr310.JavaTimeModule` 不再存在，这是升级后**唯一的编译错误**。

**处理方式不是改包名，而是删除该 Bean**，理由：

1. Jackson 3 已将 Java 8 日期时间支持内置到 databind，不再需要 `JavaTimeModule`
2. Boot 默认已关闭 `WRITE_DATES_AS_TIMESTAMPS`，日期序列化为 ISO-8601 字符串
3. **最关键**：自定义 `ObjectMapper` Bean 会**覆盖 Spring Boot 的自动配置**，导致 `spring.jackson.*` 配置项、以及其他 starter 注册的序列化模块（如 Spring AI 所需模块）全部失效

> **工程教训**：不要手写 `ObjectMapper` / `RestTemplate` / `ObjectMapper` 这类"全家桶"Bean 去替换框架的自动配置。
> 需要字段级格式时，用 `@JsonFormat(pattern = "...")` 注解即可。
> 同时 `pom.xml` 中显式引入的 `jackson-datatype-jsr310` 已移除。

#### 踩坑 2：Tika 4.x 的 `tika-parsers-standard-package` 没有 jar

升级时最初选了 Tika 最新版 4.1.0，构建失败：

```
Could not find artifact org.apache.tika:tika-parsers-standard-package:jar:4.1.0
```

经 HEAD 请求逐一验证：

| 版本 | pom | jar |
|------|-----|-----|
| 4.1.0 | ✅ | ❌ 404 |
| 4.0.0 | ✅ | ❌ 404 |
| 3.3.2 | ✅ | ✅ |

**原因**：Tika 4.x 起 `tika-parsers-standard-package` 变为 **pom 聚合包**，实际解析器拆分为 `tika-parser-*-module` 系列，需逐个引入。

**决策**：锁定 **Tika 3.3.2**。本项目解析需求固定（PDF / Word / TXT / MD），3.3.2 完全满足，且避免引入十余个模块依赖。

> **顺带修正的既有错误**：原 `pom.xml` 只引入 `tika-core`，它**只提供 API、不含任何 parser**，
> 因此"支持 PDF/Word 解析"此前实际上是不成立的。必须使用 `tika-parsers-standard-package`（已包含 core）。

#### 踩坑 3：Spring AI 2.0 改用官方 OpenAI Java SDK

依赖树显示 Spring AI 2.0.1 的 OpenAI 模块拉入了 `com.openai:openai-java-core:4.49.0`（约 53MB），
即**从自建 WebClient 调用改为使用 OpenAI 官方 Java SDK**。

影响：配置项与异常类型可能与 1.x 不同，遇到问题时应优先查 2.0 文档而非旧教程。

## 四、数据库

| 类型 | 选型 | 用途 |
|------|------|------|
| 关系型 | **PostgreSQL 16** | 业务数据存储 |
| 向量 | **pgvector** | 文档 / 笔记向量存储、相似度检索 |
| 缓存 | **Redis 7** | 见 4.2 |

### 4.1 为什么是 PostgreSQL + pgvector（而非独立向量库）

**决定性理由是"过滤 + 排序必须在同一条 SQL 内完成"。**
`RagService.retrieve(scope)` 需要按知识库过滤、同时按向量相似度排序：

```sql
SELECT id, chunk_content, source_info, 1 - (embedding <=> ?::vector) AS score
FROM knowledge_chunk
WHERE knowledge_base_id = ?          -- 业务过滤（scope）
ORDER BY embedding <=> ?::vector     -- 向量排序
LIMIT ?;
```

若拆分为"PG 存业务 + Milvus/Qdrant 存向量"，该查询会退化为：
先向向量库取 Top-K → 回 PG 查元数据 → 再按 `knowledge_base_id` 过滤。
**结果可能大幅缩水**（例如取回 10 条只有 2 条属于目标知识库），被迫改为"超量取回再重排"，引入正确性风险。

| 备选方案 | 否决理由 |
|---------|---------|
| Milvus / Qdrant / Chroma | 多一个服务需运维；**过滤+排序跨库做不到**；几千 chunk 的规模用不上 |
| Elasticsearch | 唯一真正的竞争者（BM25 + 向量混合检索一体）。但 JVM 内存占用高（2GB+），部署目标为 2 核 4G 服务器，且仍需 PG 存业务数据 → 两个数据库 |
| MySQL | 8.x 无原生向量类型；仍须拆分两个库 |
| Redis Stack | 已有 Redis，但持久化弱，引用溯源所需的元数据查询别扭 |
| SQLite + sqlite-vec | 桌面端方案，服务端不适用 |

> Milvus 作为未来数据规模大幅增长后的备选。

### 4.2 Redis 的定位（必须给它真实用途）

Redis 已引入依赖但**代码中零使用**。规划三个用途，否则该依赖只是装饰：

1. **缓存用户 AI 配置**（避免每次请求都查库 + 解密 API Key）
2. **限流**（公网部署后防止 API Key 被刷爆，属刚需）
3. **登录失败计数**（防爆破）

> **不要**用 Redis 存对话上下文——数据库已足够，多一层缓存只会多一个故障点。

### 4.3 向量索引策略（论文可写的技术点）

**开发阶段不建向量索引。**

| 索引 | 问题 |
|------|------|
| `ivfflat`（原方案 `lists = 100`） | 需先有数据再建（要对数据聚类）。几千行规模下每簇不足 100 行，**召回率反而下降** |
| `hnsw`（推荐后续启用） | 无需训练、小数据量表现好、召回率高。数据量上来后（如 > 1 万块）再建 |

几千行的规模，顺序扫描 + `<=>` 排序在毫秒级完成，**比带索引更精确**。数据量增长后再启用 HNSW，并在论文中记录"索引策略与数据规模的关系"这一实验结论。

## 五、AI 能力

### 5.1 供应商与模型

**核心约束：DeepSeek 不提供 Embedding 接口**（[DeepSeek-V3 issue #806](https://github.com/deepseek-ai/DeepSeek-V3/issues/806)）。
因此**对话与向量化必须来自不同供应商**，这是本项目 RAG 链路的硬约束。

| 用途 | 供应商 | 模型 | 维度 | 说明 |
|------|--------|------|------|------|
| **对话（开发阶段）** | DeepSeek | `deepseek-v4-flash` | — | 性价比高 |
| **Embedding（开发阶段）** | **硅基流动** | `BAAI/bge-m3` | **1024** | **无限免费**，大陆直连 |
| Embedding 备选 | 硅基流动 | `Qwen3-Embedding-0.6B` | 1024 | 可按需切换，**维度不变** |
| Embedding 备选 | 硅基流动 | `Qwen3-Embedding-8B` | 4096 | 精度更高，需改 schema |
| Embedding 备选 | 阿里云百炼 | `text-embedding-v3` | 1024（默认） | 支持 query/document 非对称编码 |
| Reranker（P1） | 硅基流动 | `BAAI/bge-reranker` | — | **免费**，用于检索精排 |
| 离线兜底 | 本地 Ollama | `bge-m3` | 1024 | 答辩防断网 |

> **模型名待核对**：`deepseek-v4-flash` 需以 DeepSeek 控制台当前模型列表为准确认。

### 5.2 硅基流动（SiliconFlow）——开发阶段主力

硅基流动是**模型聚合平台**，特性与本项目设计高度契合：

| 特性 | 对本项目的价值 |
|------|--------------|
| **一个 API Key 覆盖 chat / embedding / rerank** | 开发阶段只需配一处密钥 |
| 完全 OpenAI 兼容 | 直接用 Spring AI 的 OpenAI 模块，无需专用适配 |
| `base_url` = `https://api.siliconflow.cn/v1` | 填入设置页即可 |
| **`bge-m3` 无限免费** | 毕设用量零成本 |
| **`bge-reranker` 免费** | P1 精排环节零成本 |
| 国内直连 | 无需网络代理，答辩演示稳定 |

### 5.3 Embedding 维度决策：**1024**

选定 1024 的理由是"**免费/低价模型在 1024 维上交汇**"，从而获得最大的模型替换自由度：

| 模型 | 维度 | 成本 |
|------|------|------|
| 硅基流动 `BAAI/bge-m3` | 1024 | **无限免费** |
| 硅基流动 `Qwen3-Embedding-0.6B` | 1024 | 免费额度 |
| 阿里云百炼 `text-embedding-v3` | 1024（默认） | 新用户免费额度 |
| 本地 Ollama `bge-m3` | 1024 | 免费 |

**已同步修改**：`init.sql` 的 `VECTOR(1024)`、`application.yml` 的 `embedding-dimension: 1024`、数据库设计文档。

> 🔴 **更换 Embedding 模型会使已有向量全部作废。**
> 切换到其他维度的模型（OpenAI 1536、百炼 v4 可选 1536、智谱 2048）必须同时改 schema 并**重新解析全部文档**。
> 因此设置页需对用户给出硬提示 + 提供「重建索引」入口。

### 5.4 AI 供应商配置管理（设计决策）

**用户提出的"抽象出 chat 与 embedding 两个配置"是正确方向**，且是解决"DeepSeek 无 Embedding"的唯一办法。

需要注意区分两个层次，二者不冲突：

| 层次 | 内容 | 归属 |
|------|------|------|
| **能力层** | 设置页允许用户填入**任意 OpenAI 兼容**服务（`base_url` + `api_key` + `model` + `dimensions`） | 交给用户 |
| **默认层** | 系统预置值、演示环境配置、**论文实验基准** | 开发者必须定死 |

**默认层必须存在**，理由有三（第三条最关键）：

1. 新用户开箱可用——注册后知识库功能不能是死的
2. 答辩演示可控——不能现场让评审填写 API Key
3. **论文实验必须固定基准**——做分块 / Top-K / 混合检索的对比实验时，Embedding 模型必须是常量，否则变量不止一个，实验结果不可比、不可复现

#### `ai_config` 表结构需调整（待实施）

现有表结构一行同时装 chat 与 embedding，并用 `UNIQUE(user_id, provider_name)` 约束，
**无法表达"对话用 DeepSeek、向量化用硅基流动"**（这正是实际需求）。

建议调整为：

```sql
ALTER TABLE ai_config
    ADD COLUMN role       VARCHAR(20) NOT NULL DEFAULT 'chat',  -- 'chat' | 'embedding'
    ADD COLUMN dimensions INTEGER,                              -- 仅 embedding 使用
    DROP COLUMN chat_model,
    DROP COLUMN embedding_model,
    ADD COLUMN model      VARCHAR(100) NOT NULL;                -- 统一为 model

-- 唯一约束改为按角色区分
ALTER TABLE ai_config DROP CONSTRAINT ...;
CREATE UNIQUE INDEX uk_ai_config_role ON ai_config(user_id, role, provider_name);
```

配套要求：

| 要求 | 说明 |
|------|------|
| API Key 加密存储 | 设计文档承诺 AES，**尚未实现**（可用 Jasypt 或 AES-GCM） |
| 前端不回显完整 Key | 只显示后四位 |
| 「测试连接」按钮 | 发一次轻量请求验证 key / url / model |
| 按模型区分可调参数 | **思考模式下 `temperature` 不生效**（见 5.5），需隐藏或置灰 |

### 5.5 思考链路的参数陷阱

据 [DeepSeek 思考模式文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)：

- 思考模式**默认开启**，思维链通过 `reasoning_content` 返回（与 `content` 同级），**支持流式**
- 思考模式下 `temperature`、`presence_penalty`、`frequency_penalty` **传入不报错但不生效**
- `top_p` 仅在思考模式生效，有效范围 `0.95–1.0`；非思考模式恒为 1.0

**影响**：设置页"AI 参数"标签页必须按模型区分可调项，否则用户调整后无任何效果（静默失效）。

### 6.1 格式范围决策

| 优先级 | 格式 | 决策 |
|--------|------|------|
| **P0** | Markdown / TXT | 直接读取 |
| **P0** | PDF | Tika 解析 |
| **P1** | Word (docx) | Tika 解析 |
| **P2 砍** | PPT | 幻灯片结构混乱（备注/母版），价值低 |
| **砍** | 图片 / OCR | **不做**，理由见下 |

### 6.2 为什么砍掉 OCR

1. Tesseract 需要本地 native 库，中文识别未经训练时准确率很差
2. 本项目的语料是**电子版**资料（自行下载的 PDF / Word），不是扫描件
3. 它是时间无底洞，且不产生论文价值

**替代方案（必须做，且是答辩加分点）**：**扫描版 PDF 检测**。
解析后若文本层为空 → 不静默入库，而是将状态置为 `failed` 并将
`error_message` 设为「该 PDF 无文本层，需 OCR（暂不支持）」。
这是文档处理状态机的加分设计，比硬做 OCR 划算得多。

### 6.3 解析库

| 库 | 用途 |
|----|------|
| **Apache Tika 3.3.2**（`tika-parsers-standard-package`） | PDF / Word / TXT / HTML，一个 API 通吃 |
| **commonmark 0.24.0** | Markdown 结构解析（保留标题层级，供结构感知分块使用） |

> 选 Tika 的理由：需要的是"支持多格式"这个**能力**，而非解析精度，Tika 省代码。
> 备选方案是显式使用 `pdfbox` + `poi-ooxml`（依赖更小、更可控，但需写两套调用）。

### 6.4 分块策略（真正的难点不是解析）

- **结构感知分块**：优先按标题（`#` / `##`）与段落切分，而非按固定字数硬切
- 目标块大小 ~512 token，**重叠 50–100**
- **必须保留 `source_info`**（文件名 + 页码 / 章节）—— 这是引用溯源的**唯一数据来源**，丢失则无法实现引用
- 上述参数正是论文消融实验的自变量（见第九节）

## 七、流式输出：SSE（不用 WebSocket）

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 单向（服务端 → 客户端） | 双向 |
| 本项目需求 | **只需服务端推送** | 不需要双向 |
| 复杂度 | 纯 HTTP，简单 | 需握手 / 心跳 / 重连管理 |
| Nginx / 网关 | 友好 | 需额外配置 upgrade |
| 中断生成 | `AbortController` 即可取消 | 需自定义协议 |

**结论：SSE。**

### 7.1 前端实现方式（重要）

当前 [frontend/src/utils/sse.ts](<../../frontend/src/utils/sse.ts>) 使用 **`fetch` + `ReadableStream`**，而非 `EventSource`。

**这是正确的选择，不要改**：`EventSource` 只支持 GET，且**无法携带 `Authorization` 头**，本项目基于 JWT 鉴权，`EventSource` 无法使用。

### 7.2 需要补齐的 4 项

| # | 项 | 说明 |
|---|---|------|
| 1 | **分流 `reasoning_content` 与 `content`** | 思考过程与正文分区块渲染 |
| 2 | **SSE 多行 `data:` 拼接** | 当前按 `\n` 切分，跨行字段会丢失 |
| 3 | **心跳** | 防止 Nginx 60s 超时断流 |
| 4 | **Nginx 配置** | `proxy_buffering off; proxy_read_timeout 300s;` —— 遗漏此项会导致流式输出被缓冲成一坨，表现为"不流式" |

## 八、RAG 实现分工：检索层自研，模型层复用

| 环节 | 由谁实现 | 理由 |
|------|---------|------|
| 调用 Embedding API | **Spring AI `EmbeddingModel`** | 无需自己写 HTTP + 重试 + 序列化 |
| 文档解析 | **Tika** | 见第六节 |
| **分块策略** | ✅ **自研** | 论文素材（结构感知分块、重叠、source_info） |
| **写入 pgvector** | ✅ **自研** | `knowledge_chunk` 带 `source_info` JSONB，现成组件的表结构对不上 |
| **相似度检索 SQL** | ✅ **自研** | `ORDER BY embedding <=> ?::vector LIMIT ?`，可写进论文 |
| **Top-K / 阈值 / 上下文组装** | ✅ **自研** | 论文实验的核心自变量 |
| **引用溯源** | ✅ **自研** | 核心创新点 |
| Reranker 精排（P1） | ✅ 自研调用 | 硅基流动 `bge-reranker` 免费 |

### ⚠️ 不要使用 Spring AI 的 `PgVectorStore`

它会自行创建并管理表结构，与本项目的 `knowledge_chunk`（含 `source_info` 供引用溯源）**不匹配，使用后必然冲突**。自研 SQL 反而更简单，也更能写进论文。

### 8.1 RAG 完整链路

```
用户上传文档
    ↓
MinIO 存储（原始文件）
    ↓
Tika 解析（PDF / Word / MD / TXT）→ 扫描件检测
    ↓
文本清洗
    ↓
结构感知分块（按标题/段落，512 token，重叠 50–100，保留 source_info）
    ↓
Embedding（Spring AI EmbeddingModel → 硅基流动 bge-m3，1024 维）
    ↓
写入 pgvector（自研 SQL）
    ↓
──────────── 以上为入库；以下为问答 ────────────
    ↓
用户提问
    ↓
问题向量化
    ↓
相似度检索（自研 SQL，按 scope 过滤 + Top-K）
    ↓
[P1] Reranker 精排
    ↓
上下文组装 + 引用标注（source_info）
    ↓
LLM 生成（SSE 流式，含 reasoning_content）
    ↓
返回答案 + 引用来源
```

## 九、实验设计（论文必需）

RAG 类论文答辩必被问"你如何证明设计选择更优"。**目前文档中没有任何实验设计，这是论文最大的缺口。**

| 层 | 实验内容 | 必要性 | 成本 |
|----|---------|--------|------|
| **① 消融实验** | 自身系统：分块大小 (256/512/1024)、Top-K (3/5/10)、纯向量 vs 混合检索 | ⭐ **必须，论文主体** | 1–2 天 |
| **② 有无对比** | 无 RAG（直接问 LLM）/ 纯关键词 / 向量检索 | ⭐ 必须 | 半天 |
| **③ 外部基线** | 与 Dify 同语料对比 | 加分项 | 1–2 天 |

**指标**：

- 检索层：**Recall@K**（正确片段是否进入 Top-K）、**MRR**、引用准确率
- 生成层：答案相关性、忠实度（有无幻觉）、引用完整性 —— 人工按固定 rubric 打 1–5 分

**前置条件**：一份固定语料 + 一套固定问题集（30 题），**每题人工标注正确答案出处**——这是唯一费时的部分，也是指标可计算的前提。

> ⚠️ 时间不足时**砍第三层，保住第一层**。评审更可能问"分块为什么是 512 不是 1024"，而不是"和 Dify 比怎么样"。
>
> 实验数据应在开发过程中同步积累，不要留到最后补。

## 十、文件存储与部署

### 10.1 数据分类存放

| 数据 | 存放位置 | 理由 |
|------|---------|------|
| 文档原文件（PDF/Word/图片字节） | **MinIO**（部署在应用同一台服务器） | 免费、S3 兼容、与文档处理解耦 |
| AI 回答 / 消息 | **PostgreSQL `message` 表** | 纯文本，无需额外存储 |
| 向量 | **同库 pgvector** | 保证与业务数据的一致性，避免跨库查询 |
| 用户头像 / 笔记插图 | 同 MinIO（按 bucket 或前缀区分） | |

> 云厂商 OSS / COS 作为备选：按量计费、无需自运维，但毕设规模下 MinIO 已足够。

### 10.2 部署形态

```
轻量应用服务器 2核4G / 60GB SSD（约 ¥70–110/月）
└── Docker Compose
    ├── postgres:16 + pgvector      业务数据 + 向量
    ├── redis:7                     配置缓存 + 限流
    ├── minio                       文件（仅对 Docker 内网暴露）
    ├── app (Spring Boot jar + 前端静态资源)
    └── nginx                       反向代理 + TLS（唯一对外）
```

已按此改造 `docker-compose.yml`：PG / Redis / MinIO 端口**全部只绑 `127.0.0.1`**，MinIO 控制台不再对公网开放。

### 10.3 ⚠️ 关于备案（重要澄清）

**租服务器本身不需要备案。备案的对象是"域名"，不是服务器。**

| 场景 | 是否需要备案 |
|------|-------------|
| 大陆节点 + **仅用 IP 访问** | ❌ 不涉及（但云厂商对 80/443 有管控，通常需用非标准端口，且无法配置 HTTPS） |
| 大陆节点 + **绑定域名** | ✅ **必须备案**（否则云厂商拦截 80/443） |
| **香港 / 海外节点 + 域名** | ❌ **完全免备案** |

备案成本：需已实名域名 + 大陆服务器（一般要求实例剩余时长 ≥3 个月）+ 提交材料 + 管局审核 ≈ **2–3 周**。

> **决策：使用香港 / 海外轻量节点。** 可当天开通、绑域名、上 HTTPS、免备案，带宽通常优于同价大陆节点，延迟对演示无影响。
>
> 若担心校园网络访问海外 IP 受限，退路为"大陆节点 + IP + 非标准端口"。

## 十一、被否决的方案（含理由，避免重复讨论）

| 方案 | 否决理由 |
|------|---------|
| **若依（RuoYi-Vue-Plus）作为基座** | 它是**多租户后台管理系统**脚手架（Sa-Token + WarmFlow 工作流 + RBAC + 部门/岗位），与本项目"产品型应用"重合度极低。可复用的仅"鉴权"，而鉴权已完成；代价是学其约定、剥离多租户/工作流、用 Sa-Token 替换现有 Spring Security、且其 Element Plus 前端完全不可用。**净收益为负** |
| **第三方 Agent（Claude Code CLI 套壳）** | 形态不符（要求桌面端 + 本地 CLI + 用户订阅）、无技术内容可写、不可复现。详见 [[范围决策书]] |
| **第三方 RAG 平台（Dify/RAGFlow/FastGPT）作为主链路** | 论文创新点（引用溯源、融合架构）恰好是平台自带能力，会导致"你做了什么"无法回答。**但作为对比实验基线有价值**（见第九节） |
| **桌面端应用** | 难点不在打包而在依赖栈：需 PostgreSQL+pgvector / Redis / MinIO 三个服务，桌面用户无法安装；改用 SQLite 则向量存储需重写（`<=>` 语法作废）、论文技术点连带失效。**对论文零增益** |
| **WebSocket** | 本项目只需单向推送，SSE 更轻量 |
| **Spring Cloud 微服务** | 单人体量，单体架构更合理 |
| **Milvus / Pinecone** | pgvector 已足够，规模扩大后再考虑 |
| **RabbitMQ 异步任务** | P2，第一版不做 |
| **OCR（Tesseract）** | 见 6.2 |
| **Spring AI `PgVectorStore`** | 表结构与 `knowledge_chunk` 冲突，见第八节 |
