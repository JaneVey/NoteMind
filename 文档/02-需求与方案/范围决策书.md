## 一、决策背景

### 1.1 发生了什么

原方案将系统定位为"融合 Obsidian 知识管理能力与 RAG 文档智能能力"。开发到前端原型阶段后，在录制演示视频时重新审视了三个参考对象（Obsidian、ima、Claudian 插件），发现实际体验远比预期复杂，进而怀疑：

> "要完成 AI 对话，Agent 对应的流程不能少。"
> "如果要实现思考链路 + SSE + 工具调用 + RAG，也就是一个完整的 Agent，我没有信心。"

### 1.2 诊断：一次概念混淆

动摇的真正原因不是能力不足，而是**把 5 件难度相差 10 倍的事，全部塞进了"Agent"这一个词**：

| 被统称为"Agent"的东西 | 它实际是什么 | 难度 |
|---------------------|-------------|------|
| 多轮对话 | 消息持久化 + Prompt 组装 | ★ |
| SSE 流式输出 | fetch + ReadableStream | ★ |
| 思考链路 | API 返回的一个字段 | ★ |
| RAG 检索增强 | 分块 → Embedding → 相似度 → 拼上下文（**管道，不是智能体**） | ★★★ |
| "列出修改建议 → 用户确认 → 执行" | 单次结构化输出 + 前端渲染 + 确认 + 应用 | ★★ |
| 真 Agent（工具调用循环） | LLM 自主决定调用哪个工具、多轮循环执行 | ★★★★ |
| 多 Agent 编排 | 编排、通信、结果仲裁 | ★★★★★ |

**其中只有最后两项是真正的 Agent，而这两项原本就不在方案范围内。**

### 1.3 补记：原方案本来就排除了 Agent

[[方案定位]] 第 191 行"暂不包含"清单中已明确写入：

> - ❌ AI Agent 自动执行

[[01-系统架构设计]] 全文未出现 Agent 相关设计。也就是说，**被动摇的不是原方案，而是对原方案的信心**。本次动摇源于对照了一个更强的第三方产品（Claudian），而非源于原方案本身有缺陷。

## 二、结论（只看这一段）

> **NoteMind 不实现 Agent，也不实现多 Agent 编排。**
> 全部 AI 功能通过 **"单次/多轮模型调用 + 检索增强 + 结构化确认"** 三条机制实现。
> 这足以覆盖 AI 助手、笔记 AI 辅助、知识库问答三个场景的全部预期体验。

## 三、能力分层与取舍

这是本文档的核心。**每一层都是一个可以停下的台阶，停下即为可交付状态。**

| 层 | 能力 | 实现要点 | 是否做 | 说明 |
|----|------|---------|--------|------|
| L0 | 单轮 API 调用 + 持久化 | ChatClient 调用、消息落库 | ✅ 必做 | 基础 |
| L1 | 多轮上下文 + 用户画像注入 | 取历史消息拼 Prompt，注入 `user_profile` | ✅ 必做 | 已有设计 |
| L2 | SSE 流式输出 | 前端 `utils/sse.ts` 已实现 | ✅ 必做 | 前端已完成 |
| L3 | 思考链路展示 | 解析 `reasoning_content` 并折叠渲染 | ✅ 必做 | **成本极低，见第五节** |
| L4 | RAG 检索增强 + 引用溯源 | 分块 → Embedding → pgvector 检索 → 上下文组装 | ✅ 必做 | **论文命脉** |
| L5 | 结构化确认（建议 → 确认 → 写入） | 1 次 JSON 输出 + 前端 diff + 用户勾选 + 应用 | ✅ 必做 | **论文创新点，见第七节** |
| L6 | 真 Agent（工具调用循环） | LLM 自主选工具、多轮执行、自主读写文件 | ❌ **不做** | 见第十节翻案条件 |
| L7 | 多 Agent 编排 | 多智能体协同、通信、仲裁 | ❌ **不做** | 本科毕设不适用 |

**L0–L5 全部完成 = 项目完成。L6/L7 不在交付范围内，也不写入论文的"已实现"部分。**

## 四、关于 Claudian 路径的核实结论

### 4.1 核实结果：猜测正确

Claudian（[YishenTu/claudian](https://github.com/YishenTu/claudian)）自述：

> "An Obsidian plugin that **embeds AI coding agents** (Claude Code, Codex CLI, Grok Build, OpenCode, Pi) in your vault. Your vault becomes the agent's working directory — file read/write, search, bash, and multi-step workflows all work out of the box."

其 Requirements 第一条为"至少安装一个 harness（Claude Code / Codex CLI / …）"，并标注 **Desktop only**。架构目录中包含 `core/process/`（CLI 发现与子进程管理）、`providers/claude/`（Claude Agent SDK 适配器）、`providers/acp/`（Agent Client Protocol）。

**结论：所有智能（文件读写、搜索、bash、多步工作流、内联 diff）均由第三方 CLI 完成，插件只承担 UI、进程管理与协议适配。它是中间件，不是智能体实现。**

### 4.2 为什么不能作为本项目的核心技术路线

| # | 致命伤 |
|---|--------|
| 1 | **形态不符**：要求桌面端 + 本地安装 CLI + 用户自有订阅。NoteMind 是 Web 应用，答辩演示无法要求评审先安装 CLI。 |
| 2 | **无技术内容可写**：智慧 100% 在第三方，论文无法论证任何设计决策，答辩必被质疑"你做了什么"。 |
| 3 | **不可复现**：CLI 版本升级或订阅中断即失效，系统失去可演示性。 |

### 4.3 但其中一条思想被采纳

Claudian 模式中"把模型供应商的配置与成本下放给用户"这一决策是**正确的**，且原方案已经采用：

- [[技术栈选型]]：用户自备 API Key
- [[03-AI供应商接入设计]]：不做自动路由与成本统计，只做手动切换

**保留该决策，放弃 CLI 套壳。**

## 五、思考链路是近乎免费的（重要澄清）

原判断"思考链路很贵"是错误的。据 [DeepSeek 思考模式文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)：

- 思考模式**默认开启**，思维链通过 `reasoning_content` 返回，"与 `content` 同级"
- **支持流式输出**
- 开关与强度由 `thinking: {type: enabled/disabled}` 与 `reasoning_effort` 控制

因此本项目的"思考链路"实现成本为：

> **从 SSE 流中多解析一个字段 + 前端多渲染一个可折叠区块。**

无需实现任何推理框架、规划器或状态机。

### 5.1 必须记录的参数陷阱

思考模式下：

- `temperature`、`presence_penalty`、`frequency_penalty` **传入不报错但不生效**
- `top_p` 仅在思考模式生效，有效范围 `0.95–1.0`，低于 0.95 按 0.95 处理；非思考模式恒为 1.0

**影响**：[[01-系统架构设计]] 与设置页"AI 参数"标签页需要按模型区分可调项，否则用户调整后无任何效果，属于静默失效。

### 5.2 工具调用模式下 `reasoning_content` 的回传要求（备查）

若请求携带 `tools` 参数，则历史轮次的 `reasoning_content` **必须完整回传**，否则 API 返回 400。本项目 L6 不做，故 MVP 阶段不涉及；若将来启用工具调用，此条为前提。

## 六、架构收敛：一个 ChatService + 一个 RagService

### 6.1 修正的误解

原担忧："主页、笔记侧边栏、知识库三处 AI 都需要知识库，工作量翻三倍。"

**实际：这不是三个 AI 功能，是一个服务的三种调用范围。**

```
                    ┌──────────────────────────────┐
                    │  ChatService（唯一）           │
                    │  · 上下文组装                  │
                    │  · reasoning_content 解析     │
                    │  · SSE 推送                   │
                    └───────────────┬──────────────┘
                                    │
                    ┌───────────────▼──────────────┐
                    │  RagService.retrieve(scope)   │
                    │  scope: NONE | KB |          │
                    │         NOTEBOOK | NOTE      │
                    └───────────────┬──────────────┘
                                    │
      ┌──────────────┬──────────────┼──────────────┬──────────────┐
      ▼              ▼              ▼              ▼
  主页通用对话   主页绑定知识库   笔记侧边栏AI    知识库问答
  (NONE)         (KB)           (NOTEBOOK/NOTE) (KB)
```

### 6.2 关键点

1. **检索服务只有一个**，通过 `scope` 参数区分检索范围。
2. **三个入口共用同一套流式输出、思考链解析、消息持久化逻辑。**
3. 这正是论文中"笔记与知识库融合架构"的**落地形态**——不是三个独立 AI 模块的堆叠，而是一个统一 AI 服务对接不同知识范围。

> 该收敛同时降低了实现量与论文描述的复杂度，**是本次决策最大的收益**。

### 6.3 与既有设计的一致性

[[01-系统架构设计]] 第 5 节规定"笔记 → 知识库单向联动"，与本节的 `scope=NOTEBOOK` 检索**不冲突**：

- 单向联动指**数据流入**方向：笔记内容可主动加入知识库成为持久 RAG 数据源
- `scope=NOTEBOOK` 指**检索范围**：笔记侧边栏 AI 临时把当前仓库作为检索语料，不产生持久向量数据

两者是不同层面的机制，需在论文中明确区分，避免答辩时被质疑自相矛盾。

## 七、"确认后执行"的正确实现（这不是 Agent）

### 7.1 机制

**一次模型调用 + 一次用户确认 + 一次应用**，全程无循环、无工具自主选择。

```json
{
  "analysis": "该段落缺少论证支撑，且用词不准确",
  "edits": [
    {
      "find": "Spring 事务很快",
      "replace": "Spring 事务通过 AOP 代理实现，主要开销在代理调用链",
      "reason": "补充实现原理，修正绝对化表述"
    }
  ]
}
```

流程：

```
用户选中文字 / 点击"AI 修改"
    ↓
模型返回结构化 JSON（不直接改笔记）
    ↓
前端渲染为 diff 清单 / 勾选项
    ↓
用户勾选并确认
    ↓
后端按 edit 列表应用补丁、更新 NoteLink
```

### 7.2 为什么这个设计对论文有利

[[NoteMind项目详细说明书]] 已记载该设计意图：

> "通过'先展示建议、再确认写入'的方式，系统保留用户对原始笔记的控制权。"

相比 Claudian 的自主编辑模式，**本方案在论文中更易论证**：可控性、可追溯性、错误可回滚，都是明确的工程论证点。同时实现成本仅为 L5（★★），不触及 L6。

## 八、四个页面的最终归属

| # | 页面 | 定位 | 技术实质 | 优先级 |
|---|------|------|---------|--------|
| 1 | 主页 AI 助手 | 通用对话 + 可选绑定知识库 | ChatService + L1/L2/L3 | **P0** |
| 2 | 笔记 | 笔记 CRUD + 侧边栏 AI | ChatService(scope=NOTE) + L5 | **P0** |
| 3 | 知识库 | 入库 + RAG 问答 + 引用溯源 | RagService + L4 | **P0（论文命脉）** |
| 4 | 知识图谱 | — | `note_link` 表上的一个**视图** | **P1（可砍）** |

### 8.1 知识图谱的归属定论

**此前悬而未决的问题（第四个大功能 / 嵌入笔记模块）在此定论：两者都不是。**

- 它不是独立功能模块：后端仅是 Wikilink 正则解析 + 图谱查询 API（约 100 行），数据完全来源于 `note_link` 表
- 也不需要"嵌入"，它天然是笔记数据的**视图**

**决策：导航层级上作为笔记模块内的一个标签页 / 面板，不设顶级菜单入口。**

理由：其数据本就是笔记范围的；独立成顶级模块会使系统在答辩时显得复杂 25%，招致无必要的追问。

## 十、翻案条件（防止再次动摇）

**只有在以下条件全部满足时，才重新评估 L6（Agent）**：

1. L0–L5 全部完成并通过全链路联调
2. 引用溯源已可稳定演示

4. 距答辩仍有 ≥ 4 周空闲
