## 一、先纠正一个常见误解：分层到底是什么

### 1.1 「Controller - Service - Entity」这个说法有问题

学校里流传的分层表述是 `Controller → Service → Entity`。**这个链条的第三环错了。**

```
❌  Controller → Service → Entity
✅  Controller → Service → Mapper(DAO) → 数据库

    而 Entity / DTO / VO 不是"层"，是"在各层之间流动的数据模型"
```

**为什么这个区别重要？**

- 「层」是**有行为的组件**（能接收调用、能返回值、有职责边界）
- `Entity` 是**没有行为的纯数据**（只有字段 + getter/setter），它不会"处理"什么，只是被传来传去
- 把 Entity 当层，会导致一个典型错误：**以为 Controller 可以"调用 Entity"**，于是把数据库操作写进 Controller

一句话记住：

> **层负责做事，模型负责装数据。**

### 1.2 完整分层与职责（本项目采用）

```
┌─────────────────────────────────────────────────────────┐
│ Controller（Web 层）                                      │
│   职责：接收 HTTP 请求、参数校验、调 Service、包装响应      │
│   禁止：业务逻辑、直接注入 Mapper、直接返回 Entity          │
├─────────────────────────────────────────────────────────┤
│ Service（业务层）                                         │
│   职责：业务规则、事务边界、组装 DTO/VO、调用 Mapper        │
│   禁止：出现 HttpServletRequest / Response 等 Web 概念     │
├─────────────────────────────────────────────────────────┤
│ Mapper（数据访问层 / DAO）                                 │
│   职责：只做数据读写                                       │
│   禁止：业务判断（"如果状态是 X 就不查" 属于 Service）      │
├─────────────────────────────────────────────────────────┤
│ 数据库                                                    │
└─────────────────────────────────────────────────────────┘
```

### 1.3 一张对照表：学校教的 vs 工程实践

| 主题 | 常见理解 | 工程实践 | 为什么 |
|------|---------|---------|--------|
| 分层第三环 | Entity | **Mapper/DAO** | Entity 是模型不是层；数据库操作必须有专门的层 |
| Entity 用途 | "放表" | 与表一一对应，**只在后端内部流转** | 直接返回给前端会泄露 `password` 等字段 |
| Service 形态 | 接口 + Impl | **保留**（阿里强制），但要理解代价 | 见 1.4 |
| Mapper 用途 | "写 SQL 的" | 简单 CRUD 用 MyBatis-Plus 内置方法，**只把复杂查询写进 XML** | 你的理解是对的 ✅ |
| 事务加在哪 | 不明确 | **Service 层** | Controller 太外层，Mapper 太内层（多步操作无法回滚） |
| DTO 粒度 | 一个 DTO 走天下 | 至少分 **入参 Request / 出参 Response** | 入参与出参字段本就不同 |
| 异常处理 | try-catch 打日志 | **抛异常 + 全局处理器**，禁止吞 | 见第三节 |

### 1.4 关于「Service 接口 + Impl」——诚实的说明

阿里的原文是**强制**：

> 【强制】对于 Service 和 DAO 类，基于 SOA 的理念，暴露出来的服务一定是接口，内部的实现类用 Impl 的后缀与接口区别。

**但你要知道它的代价**：

- 一个接口只有一个实现时，**改一个方法要改两个文件**
- 接口本身不产生任何抽象价值（没有第二个实现可替换）
- Spring 官方示例、Spring Boot 官方文档里的 Service **通常没有接口**

**我的建议：本项目保留接口 + Impl**，理由：

1. 它是国内 Java 岗位的事实标准，**答辩与面试时是加分项**
2. 项目体量小，代价可接受
3. 将来的能力型接口（如 `NoteParser` 有 Markdown/PDF/Word 三种实现）确实需要接口

**但要清楚**：接口的真正价值在于**"存在多个实现"或"需要跨模块契约"**。如果某个 Service 永远只有一个实现，那这个接口纯粹是仪式 —— 不丢人，但要心里有数。

> **一个务实的例外**：纯粹的 CRUD Service（只转发 Mapper）可以不加接口，直接 `@Service class NoteService`。
> 本项目为保持统一，仍然全部加。

### 1.5 命名（详见《01-项目结构与命名规范》）

```java
// Controller：只做转发与包装

    @Override
    @Transactional(rollbackFor = Exception.class)

        // 业务规则写在这里
    }
}
```

## 二、领域模型（Entity / DTO / VO）的边界

| 类型 | 位置 | 用途 | 能否直接对外 |
|------|------|------|------------|
| `Entity` | `xxx/entity/` | 与数据库表一一对应 | ❌ **禁止返回前端** |
| `XxxRequest` | `xxx/dto/` | 接收前端入参（带校验注解） | 入参方向 |
| `XxxResponse` | `xxx/dto/` | 返回给前端的对象 | ✅ 只放该露的字段 |
| `XxxVO` | `xxx/vo/` | 字段裁剪后的展示对象 | ✅ |
| `XxxQuery` | `xxx/dto/` | 查询条件（**禁止用 `Map` 传参**） | 入参方向 |

**硬规则**：

1. **Controller 的返回值类型里不允许出现 Entity。**
   > 现状核查：项目 4 个 Controller 均合规 ✅。
   > 但 `SysUser`（原 `NoteUser`）含 `password` 字段，一旦哪天有人图省事直接返回，就是密码泄露。
2. **Entity 只做数据承载，不写业务方法。**（本项目采用"贫血模型"，保持一致）
3. **DTO ↔ Entity 的转换集中在 Service 层**，不要在 Controller 里手动 `set` 一堆字段。
4. **不要给 DTO/Entity 属性设默认值。** 否则更新时会把未传的字段覆盖成默认值。

## 三、异常处理规范

### 3.1 总体策略：对内抛异常，对外给错误码

| 场景 | 做法 |
|------|------|
| 应用内部各层之间 | **抛出有业务含义的自定义异常** |
| 到达 Controller 之后 | **由 `GlobalExceptionHandler` 统一转成错误码响应** |
| 业务逻辑分支 | **不要用异常做流程控制**（异常比条件分支慢，且难读） |

**为什么对外必须用错误码**：前端需要程序化地判断失败原因，而不是解析错误文案。

### 3.2 错误码分段（待实施）

现状问题：`BusinessException(400, "用户名已存在")` 与 `BusinessException(400, "旧密码错误")`
在前端看来是**同一个码**，无法区分，日志里也定位不到模块。

**规则**：错误码 = `模块段 + 具体原因`，用枚举统一定义。

```java
public enum ErrorCode {

    // 1xxx 通用
    PARAM_INVALID(1001, "参数校验失败"),
    UNAUTHORIZED(1002, "未登录或登录已过期"),
    FORBIDDEN(1003, "没有访问权限"),

    // 2xxx 用户与认证
    USERNAME_EXISTS(2001, "用户名已存在"),
    PASSWORD_WRONG(2002, "旧密码错误"),
    USER_NOT_FOUND(2003, "用户不存在"),

    // 3xxx 笔记
    NOTE_NOT_FOUND(3001, "笔记不存在"),
    NOTEBOOK_NOT_EMPTY(3002, "笔记本下还有笔记，无法删除"),

    // 4xxx 知识库
    DOCUMENT_PARSE_FAILED(4001, "文档解析失败"),
    DOCUMENT_NEED_OCR(4002, "该 PDF 无文本层，需 OCR（暂不支持）"),

    // 5xxx AI
    AI_NOT_CONFIGURED(5001, "尚未配置 AI 模型"),
    AI_CALL_FAILED(5002, "模型调用失败");

    private final int code;
    private final String message;
    // 构造与 getter 省略
}
```

**HTTP 状态码映射规则**（与业务码保持一致，这条已在本项目踩过坑）：

| 业务码段 | HTTP 状态 |
|---------|----------|
| 1xxx 参数/认证 | 400 / 401 / 403 |
| 2xxx-5xxx 业务 | 400（业务规则拒绝）或 404（资源不存在） |
| 兜底 | 500 |

> **踩坑记录**：本项目曾出现"登录失败返回 **HTTP 200** + body `code=401`"，
> 而安全层返回的是 HTTP 401 —— 同一语义两种状态码，前端拦截器与监控都难以判断。
> 已统一为「HTTP 状态码由业务码映射得出」。

### 3.3 禁止吞异常（本项目真实教训）

```java
// ❌ 反面教材：本项目 MinIO 的真实 bug
@PostConstruct
public void initBucket() {
    try {
        MinioClient client = minioClient();   // 自调用，抛 "bean currently in creation"
        ...
    } catch (Exception e) {
        log.warn("MinIO bucket check failed (may not be connected yet): {}", e.getMessage());
        // 异常被吞掉，bucket 从未创建，日志看起来"正常"
    }
}
```

**规则**：

1. 捕获了要么**处理**，要么**包装后抛出**。不允许"捕获后只打一行日志当没事"。
2. 如果确实要降级（如外部依赖不可用时不中断启动），**必须用 `ERROR` 级别并写清后果**：
   ```java
   log.error("MinIO 不可用（endpoint={}），文件上传功能将无法使用。请确认 MinIO 已启动。原因: {}",
             endpoint, e.getMessage());
   ```
3. **`catch (Exception e)` 不要滥用**，但要清楚：分不清哪些是稳定代码时，宁可捕获宽泛，也不能让异常消失。
4. **禁止用异常做流程控制**。
5. 自定义异常要有业务含义，**不要直接抛 `RuntimeException` / `Exception` / `Throwable`**。

### 3.4 分层异常策略（阿里）

| 层 | 做法 |
|----|------|
| Mapper | 抛 `DAOException`，**不打日志**（避免同一异常重复打） |
| Service | **必须打日志**，且带上参数信息 ——「保护案发现场」 |
| Controller | **不再往上抛**，由全局处理器转成错误码 |

## 四、日志规范

### 4.1 框架选择：SLF4J 门面 + Logback 实现

**结论：用 SLF4J 的 API，不要直接用 Logback/Log4j2 的 API。**

```java
// ✅ 正确：依赖门面
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

// ✅ 本项目用 Lombok 简化
@Slf4j
public class NoteService { ... }
```

**为什么要有"门面"这一层？**

- 门面（SLF4J）只定义接口，具体实现（Logback / Log4j2 / JUL）可以随时替换
- 业务代码只依赖门面，**换日志实现不用改一行业务代码**
- 这是"依赖倒置"在日志领域的应用

Spring Boot 默认已经集成 `SLF4J + Logback`，**不需要额外加依赖**。当前项目用 `@Slf4j` 是正确的，保持不变。

### 4.2 三个硬规则

**① 用占位符，不要字符串拼接**

```java
// ❌ 即使日志级别不够，也会白白拼接字符串、白白调用 toString()
log.debug("处理笔记 id: " + id + " 标题: " + title);

// ✅ 级别不够时不会有任何开销
log.debug("处理笔记 id={} 标题={}", id, title);
```

**② `error` 必须带「案发现场 + 堆栈」**

```java
// ❌ 只有结论，没有现场
log.error("保存笔记失败");

// ✅ 参数 + 异常对象（最后一个参数传 e 才会打堆栈）
log.error("保存笔记失败 userId={} notebookId={} title={}", userId, notebookId, title, e);
```

> 注意：**`{}` 占位符数量必须与参数数量匹配**，多传的异常对象若位置不对，堆栈不会打印。

**③ 级别选择**

| 级别 | 用途 |
|------|------|
| `ERROR` | 系统逻辑出错、异常等**需要人介入**的问题 |
| `WARN` | 用户输入参数错误、可恢复的异常情况 |
| `INFO` | 关键业务节点（启动、配置加载、重要状态变更） |
| `DEBUG` | 开发调试细节，**生产环境禁止输出** |

**禁止**：为了"方便排查"而大量打 INFO/DEBUG，会把磁盘撑爆，也让人找不到重点。
打日志前问自己：**这条日志真的有人看吗？看到能做什么？**

### 4.3 本项目当前日志现状

| 项 | 状态 |
|----|------|
| 使用 `@Slf4j`（SLF4J 门面） | ✅ 合规 |
| 占位符 `{}` 用法 | ✅ 合规 |
| 启动自检日志（MinIO / Redis 连接确认） | ✅ 这是一个好实践，保留 |
| `error` 是否都带堆栈 | ⚠️ 需逐个检查（部分只传了 `e.getMessage()`，丢了堆栈） |
| 吞异常 | ⚠️ 已修复 MinIO 一处，需继续排查 |

## 五、API 设计规范

### 5.1 统一响应结构（沿用现有）

```json
{ "code": 200, "message": "success", "data": { } }
```

- HTTP 状态码**必须**与 `code` 语义一致（见 3.2）
- 分页响应用统一的 `PageResult<T>`：

```json
{ "code": 200, "message": "success",
  "data": { "list": [], "total": 0, "page": 1, "size": 10 } }
```

### 5.2 分页参数（待定稿，建议如下）

| 参数 | 含义 | 默认 | 约束 |
|------|------|------|------|
| `page` | 页码，**从 1 开始** | 1 | ≥ 1 |
| `size` | 每页条数 | 10 | 1 ≤ size ≤ 100 |

> **`size` 必须设上限**：不限制会导致 `page size` 过大而内存溢出（阿里明确列为安全风险）。

### 5.3 RESTful 约定

| 操作 | 方法 + 路径 |
|------|-----------|
| 列表 | `GET /api/notes?page=1&size=10` |
| 详情 | `GET /api/notes/{id}` |
| 新增 | `POST /api/notes` |
| 全量更新 | `PUT /api/notes/{id}` |
| 部分更新 | `PATCH /api/notes/{id}` |
| 删除 | `DELETE /api/notes/{id}` |
| 子资源 | `GET /api/notebooks/{id}/notes` |
| 动作 | `POST /api/notes/{id}/move` |

**幂等性提醒**：`GET`/`PUT`/`DELETE` 应幂等，`POST` 不保证。

### 5.4 参数校验

- 所有对外接口的入参**必须校验**（Controller 层用 `@Valid` + 注解）
- 校验注解写在 `Request` DTO 上，不写在 Entity 上
- 校验失败由 `GlobalExceptionHandler` 统一返回 400 + 具体字段

> 踩坑记录：项目曾有 `@Valid` 加在无任何校验注解的 DTO 上，形同虚设，已修复。

## 六、MyBatis / Mapper 使用规范

### 6.1 何时用内置方法，何时写 XML

```java
// ✅ 简单 CRUD：直接用 MyBatis-Plus 内置方法，不写 SQL
noteMapper.selectById(id);
noteMapper.selectList(new LambdaQueryWrapper<Note>().eq(Note::getNotebookId, notebookId));
noteMapper.insert(note);

// ✅ 以下情况才写 XML：
//   - 多表关联查询
//   - 需要数据库特有语法（如 pgvector 的 <=> 向量相似度排序）
//   - 复杂聚合统计
//   - 批量操作
```

XML 位置：`src/main/resources/mapper/{模块}/{EntityName}Mapper.xml`
（已配置 `mybatis-plus.mapper-locations: classpath*:mapper/**/*.xml`）

### 6.2 硬规则

| # | 规则 | 原因 |
|---|------|------|
| 1 | **禁止 `SELECT *`** | 增减字段会与映射不一致，也浪费 IO |
| 2 | **禁止 `${}`，必须 `#{}`** | `${}` 是字符串拼接 → SQL 注入 |
| 3 | 更新时**禁止无差别更新所有字段** | 易覆盖未传字段；binlog 膨胀 |
| 4 | 更新必须同时更新 `updated_at` | 否则时间字段失真 |
| 5 | 模糊查询**禁止左模糊/全模糊**（`LIKE '%x'`） | 索引失效；需要全文检索请用专用方案 |
| 6 | **超过 3 张表禁止 JOIN** | 阿里强制；性能不可控 |

## 七、事务规范

| 规则 | 说明 |
|------|------|
| **加在 Service 层** | Controller 太外（无法覆盖多步操作），Mapper 太内（单条语句自带事务） |
| 用 `@Transactional(rollbackFor = Exception.class)` | 默认只回滚 `RuntimeException`，受检异常不会回滚 |
| **注意自调用失效** | 同类内部方法互调不经过代理，`@Transactional` 不生效 |
| 事务内**不要做耗时操作** | 远程调用、文件解析、AI 请求都会长时间占用连接 |
| 不要滥用 | 事务影响并发能力，能用单条 SQL 解决的不要开事务 |

> **本项目特别提醒**：文档解析、Embedding 调用等耗时操作**绝不能放在事务里**。
> 正确做法是先落库状态为 `processing`，事务提交后再异步/同步处理，最后更新状态。

## 八、安全规范（阿里强制条款摘录）

| # | 规则 | 本项目对应 |
|---|------|-----------|
| 1 | **用户个人的数据必须做水平权限校验** | 所有业务查询必须带 `user_id` 条件，禁止只按 `id` 查 |
| 2 | 敏感数据展示必须脱敏 | API Key 只回显后四位 |
| 3 | **SQL 必须参数绑定**，禁止字符串拼接 | 见 6.2 |
| 4 | **所有传入参数必须校验** | 见 5.4；尤其 `page size`、`order by` |
| 5 | 向页面输出用户数据必须转义 | 前端 Markdown 渲染必须用 DOMPurify |
| 6 | 表单/AJAX 提交需 CSRF 过滤 | 本项目为无状态 JWT，天然免疫（无需额外处理，但要知道原因） |
| 7 | 短信/邮件等资源需防重放 | 本项目暂不涉及 |
| 8 | 用户生成内容需防刷与违禁词过滤 | 本项目暂不涉及 |

> **第 1 条是本项目最容易犯的错**：`note`、`knowledge_base`、`ai_conversation` 等表都有 `user_id`，
> **每一个查询都必须带上它**。否则用户 A 改个 id 就能读到用户 B 的笔记。
> 这也是答辩常问的"多用户数据隔离怎么做的"。
