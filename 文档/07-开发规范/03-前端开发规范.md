# 前端开发规范

> 依据：Vue 3 官方风格指南、Vue 3 官方文档、Tailwind CSS 官方建议
> 生效日期：2026-10-08

---

## 一、单文件组件（SFC）结构

### 1.1 块顺序：`template` → `script` → `style`

```vue
<template>
  <!-- 1. 模板 -->
</template>

<script setup lang="ts">
// 2. 逻辑
</script>

<style scoped>
/* 3. 样式（多数情况下可以没有这一段，见第二节） */
</style>
```

**理由**：阅读组件时先看"长什么样"，再看"怎么动"，最后才是细节样式。Vue 官方示例与文档也统一采用这个顺序。项目内**必须一致**，不要有的组件 script 在前、有的在后。

补充约定：

- `<script setup lang="ts">` 一律使用 **`setup` 语法糖 + TypeScript**，不用 Options API
- 一个 SFC **只放一个组件**，不在同一文件里定义多个组件
- 组件文件末尾留一个空行

## 二、样式策略（回答"要不要拆成独立 CSS 文件"）

### 2.1 结论：**默认不拆。** 用 Tailwind class，必要时加 `<style scoped>`

原因有三：

**① 拆出去的 CSS 会失去 `scoped` 隔离**

`<style scoped>` 是**编译期**处理的 —— Vue 编译器给模板元素加上唯一属性（如 `data-v-7ba5bd90`），
再把 CSS 选择器改写成 `[data-v-7ba5bd90]`。**外部 CSS 文件不经过这个流程，因此无法被 scoped 处理。**

结果：拆文件换来的不是"更整洁"，而是**隔离性下降**，样式会全局泄漏。

**② 本项目大量使用 Tailwind，`<style>` 块本来就很少**

```vue
<!-- 典型情况：整个组件的样式都在 class 里，不需要 <style> -->
<div class="flex items-center justify-between rounded-xl border bg-card px-4 py-3 shadow">
```

**③ 拆文件会引入"找样式"的额外成本**

改一个组件要开两个文件，而且文件名映射关系需要额外维护。

### 2.2 什么情况才拆

| 情况 | 放哪 | 说明 |
|------|------|------|
| 全局主题/设计令牌（颜色、圆角等 CSS 变量） | `src/assets/styles/theme.css` | 本来就是全局的，`main.ts` 引入 |
| Tailwind 的自定义基础层 | `src/style.css` | 已存在，保持不变 |
| 需要深度定制第三方组件的样式（Vditor、vis-network） | 组件内 `<style scoped>` + `:deep()` | 仍然不要拆出去 |
| 单个组件样式超过约 100 行 | 优先考虑**拆分组件**，而不是拆样式 | 样式多通常说明组件职责过多 |
| 确实必须拆（极少） | 同目录 `组件名.module.css` + `<style module>` | CSS Modules 自带作用域，是唯一安全的拆法 |

### 2.3 禁止

- ❌ 同目录建 `Xxx.css` 然后用 `<style src="./Xxx.css">`（无 scoped，样式全局泄漏）
- ❌ 在 `.vue` 里写 `@import` 引入外部 CSS
- ❌ 用 `!important` 覆盖样式（说明用法不对，应从根源解决）

## 三、目录职责

```
frontend/src/
├── api/                接口层：每个后端模块一个文件，只做请求封装
│   ├── request.ts      axios 实例 + 拦截器 + ApiError（基础设施，不写业务接口）
│   └── auth.ts / user.ts / note.ts / knowledge.ts / ai.ts / settings.ts
├── assets/             静态资源
│   └── styles/         全局样式与 CSS 变量
├── components/         跨页面复用的组件
│   └── ui/             shadcn-vue 风格的基础组件（33 个）
├── composables/        组合式函数（useXxx.ts）
│   ├── useDropdown.ts  下拉菜单开关 + 点击外部关闭
│   └── useChatStream.ts 流式对话（待建）
├── lib/
│   └── utils.ts        cn()：第三方库的薄封装（保持不动）
├── router/
│   ├── index.ts        路由表
│   └── guard.ts        登录守卫
├── stores/             Pinia（每个领域一个）
├── types/              类型定义，按领域拆分
│   ├── common.ts       Id / IsoDateTime / ApiResponse / PageResult
│   └── user.ts / note.ts / knowledge.ts / ai.ts
├── utils/              项目自己的纯函数
│   ├── sse.ts          streamChat（流式解析）
│   └── format.ts       日期 / 文件大小 / 字数格式化
└── views/              页面级组件（与路由一一对应）
    ├── AIChat.vue             页面容器（只做编排）
    ├── aichat/                只属于 AIChat 的子组件
    ├── Notebook.vue           页面容器
    ├── notebook/              只属于 Notebook 的子组件
    └── ...
```

**三条规则**：

1. **`components/` 放"能在多个页面复用"的组件；只被一个页面用到的子组件，放该页面的子目录里**：
   ```
   views/
   ├── AIChat.vue
   └── aichat/                    ← 只属于 AIChat 的子组件
       ├── ConversationList.vue
       └── MessageItem.vue
   ```
   **大页面必须拆成「容器 + 子组件」**：容器负责数据获取与状态编排，子组件通过
   props / emits 通信。本项目的 `AIChat.vue` 与 `Notebook.vue` 曾各自膨胀到 1389 / 1125 行，
   完全无法复用与测试，就是这个规则缺失的后果。
2. **`lib/` 与 `utils/` 的分工要清楚，不要混放**：

   | 目录 | 放什么 | 判断标准 |
   |------|--------|---------|
   | `lib/` | **第三方库的薄封装** | 这个函数是在"包装别人的库"吗？是 → `lib/` |
   | `utils/` | **项目自己的纯函数** | 这个函数是"我自己的逻辑"吗？是 → `utils/` |

   例：`lib/utils.ts` 的 `cn()` 是 `clsx` + `tailwind-merge` 的封装，**属于 `lib/`**，
   而且是 shadcn-vue 的官方约定位置，**保持不动**。

   > **规范修订记录（2026-10-08）**：本文档初版写的"`lib/` 与 `utils/` 合并到 `utils/`"是**错的** ——
   > 经核查，`lib/utils.ts` 是标准的三方库封装，被全部 30 个 `ui/` 组件引用，位置正确。
   > 当时只看到"两个目录都放着工具"，没核查内容就下了结论。
   > **这正是"先核查再改"的价值，也是规范里"发现不合理就改规范"的实例。**
3. **`types/` 按领域拆文件，禁止用索引签名兜底**（详见第五节）。

## 四、组件拆分规范

### 4.1 现状问题

| 文件 | 行数 | 问题 |
|------|------|------|
| `views/AIChat.vue` | 1389 | 一屏逻辑全在一个文件 |
| `views/Notebook.vue` | 1125 | 同上 |
| `views/Settings.vue` | 601 | 多 Tab 逻辑未拆分 |

**拆分触发条件**（满足任一即拆）：

- 单文件超过 **400 行**
- 模板里出现**重复的结构**（如重复的菜单、列表项）
- 一段逻辑**与其他页面可能复用**
- 一个文件里出现 **3 个以上互不相关的状态区块**（如 Notebook 同时管侧栏/编辑器/工具栏/查找面板/AI 面板）

### 4.2 Composable：把逻辑从组件里抽出来

Vue 3 的核心优势是**逻辑可以脱离组件复用**。凡是"一段有状态的逻辑"，都应该抽成 `composables/`。

```ts
// composables/useDropdown.ts —— 处理"点击外部关闭"（项目里重复了 10 次以上）
import { onBeforeUnmount, onMounted, ref, type Ref } from 'vue'

export function useDropdown(rootRef: Ref<HTMLElement | null>) {
  const isOpen = ref(false)

  function toggle(): void { isOpen.value = !isOpen.value }
  function close(): void { isOpen.value = false }

  function onDocumentClick(event: MouseEvent): void {
    if (rootRef.value && !rootRef.value.contains(event.target as Node)) {
      close()
    }
  }

  onMounted(() => document.addEventListener('click', onDocumentClick))
  onBeforeUnmount(() => document.removeEventListener('click', onDocumentClick))

  return { isOpen, toggle, close }
}
```

> **现状**：`Notebook.vue` 里有 10+ 个 `showXxxMenu` + `xxxMenuRef` + 各自的点击外部关闭逻辑，
> 完全可以被上面这一个 composable 替代。这是最典型、收益最大的重构点。

**命名**：`use` 开头 + 驼峰，文件名 `useXxx.ts`，放 `composables/`。

### 4.3 组件命名与 Prop

| 规则 | 说明 |
|------|------|
| 组件名**必须多词** | `NoteList.vue` ✅ `List.vue` ❌（避免与 HTML 元素冲突） |
| 文件名 = 组件名 | 用 `<script setup>` 时，文件名即组件名 |
| **Prop 必须声明类型** | 禁止 `defineProps(['status'])` 写法 |
| Prop 尽量加 `validator` | 枚举类取值尤其需要 |
| 事件名用 kebab-case 声明 | `emit('update:modelValue')`、`emit('note-selected')` |

```ts
// ✅
const props = defineProps<{
  status: 'pending' | 'processing' | 'done' | 'failed'
  noteId: number
}>()
```

## 五、类型定义规范

### 5.1 禁止用索引签名兜底（现状问题）

```ts
// ❌ 现状：types/domain.ts 里几乎每个接口都有这一行
export interface Note {
  id: Id
  folderId?: Id
  title: string
  content?: string
  [key: string]: unknown      // ← 这一行让整个类型形同虚设
}
```

**后果**：`note.anythingAtAll` 都能通过类型检查，**TypeScript 的保护完全失效**。
而且因为字段不确定，调用方被迫到处写兜底：

```ts
// 这是 authStore.ts 里的真实代码，为什么需要这么多 ?? —— 因为类型不可信
userId: data.userId ?? data.user?.userId ?? null,
```

**规则**：

1. **类型定义必须精确**，字段按后端真实返回写。
2. 后端暂时没实现的接口，把类型标成 `// TODO: 待后端定稿`，也**不要用索引签名兜住**。
3. 确实需要"额外未知字段"时，用 `Record<string, unknown>` 明确命名，而不是偷偷放开。

> **实施效果（2026-10-08）**：拆分 `types/domain.ts` 时移除了全部索引签名，
> 并把重复的对冲字段（`name`/`fileName`、`type`/`fileType`、`size`/`fileSize`）
> 收敛为与数据库列同名的一组。**结果全项目只暴露出 14 个类型错误** ——
> 说明这些索引签名**从来不是真的需要**，只是让人失去了编译器的保护。
> 这 14 个错误全部是"对冲字段被真正使用"的地方，逐个修正后 typecheck 归零。

### 5.1.1 列表类型与详情类型必须分开

同一个实体在不同接口返回的字段可能不同，**不要用一个类型硬套**，也不要用可选字段糊过去：

```ts
// ❌ 把字段标成可选 —— 调用方分不清
//    "这个字段可能没有" 和 "这个接口根本不返回它"
export interface KnowledgeDocument {
  fileName: string
  rawContent?: string        // 列表接口不返回，详情接口才返回
}

// ✅ 分开两个类型
export interface KnowledgeDocument {
  fileName: string
  fileSize: number
  /* 列表接口返回的全部字段 */
}

export interface KnowledgeDocumentDetail extends KnowledgeDocument {
  /** 解析出的纯文本。一本 PDF 可能几十万字，列表接口一次返回 20 条会传几 MB 而无用 */
  rawContent: string | null
  chunkCount: number
}
```

**判断标准**：如果某个字段的"有没有"取决于**调用的是哪个接口**（而不是取决于数据状态），
就应该拆类型。如果取决于**数据本身的状态**（如"解析完成才有 chunkCount"），用可选字段是正确的。

### 5.2 枚举值必须与后端一致（现状问题）

```ts
// ❌ 现状：把同义词全列上了
export type DocumentStatus =
  | 'pending' | 'processing'
  | 'completed' | 'done' | 'parsed'      // ← 三个同义词
  | 'failed' | 'error'                   // ← 两个同义词
```

后端设计只定义了 **4 个状态**：`pending` / `processing` / `done` / `failed`。

**「多列几个以防万一」是坏习惯**：它让类型失去约束力，且这段代码一旦分发给后端就会被质疑。
**枚举必须一对一映射后端定义。**

### 5.3 类型文件组织

`types/` 按领域拆文件，与 `api/` 一一对应：

```
types/
├── common.ts       Id、PageResult、ApiResponse
├── user.ts         UserInfo、LoginRequest…
├── note.ts         Note、Notebook、Folder
├── knowledge.ts    KnowledgeBase、KnowledgeDocument
└── ai.ts           Conversation、ChatMessage、AiConfig
```

## 六、API 层规范

| 规则 | 说明 |
|------|------|
| 一个后端模块 = 一个 api 文件 | `api/note.ts` 只放笔记相关接口 |
| `request.ts` 只放基础设施 | axios 实例、拦截器、`ApiError`、`TOKEN_KEY`；**不写业务接口** |

| 401 行为必须一致 | 普通请求与流式请求都走 `redirectToLogin()`（已统一） |

## 七、Vue 官方「优先级 A：必守」清单

官方把规则分为 A/B/C 三级，**A 级是"违反会产生真实 bug"**，必须遵守：

| # | 规则 | 项目现状 |
|---|------|---------|
| 1 | 组件名必须多词 | ✅ |
| 2 | Prop 定义必须详细（至少含类型） | ✅ |
| 3 | `v-for` 必须带 `:key` | ✅ 50/50 |
| 4 | **禁止 `v-if` 与 `v-for` 用在同一个元素上** | ❌ **7 处待修** |
| 5 | 组件样式必须作用域化（scoped / BEM / CSS Modules） | ✅（Tailwind 天然作用域化） |

### 关于第 4 条

```vue
<!-- ❌ 错误：v-if 优先级高于 v-for，求值时 user 还不存在 -->
<li v-for="user in users" v-if="user.isActive" :key="user.id">

<!-- ✅ 正确一：用 computed 先过滤（更推荐，逻辑更清晰） -->
<li v-for="user in activeUsers" :key="user.id">

<!-- ✅ 正确二：用 <template> 包一层 -->
<template v-for="user in users" :key="user.id">
  <li v-if="user.isActive">
</template>
```

**现状**：`ChatPanel.vue`（1 处）已随死代码清理一并删除；`Notebook.vue` 的 6 处
在拆分重构时修正。**当前全项目扫描为 0 处**（扫描方式见第九节）。

## 八、禁止事项速查

| # | 禁止 | 原因 |
|---|------|------|
| 1 | 类型里用 `[key: string]: unknown` 兜底 | 类型保护失效，调用方到处写 `??` |
| 2 | 枚举值多列同义词"以防万一" | 与后端定义脱节 |
| 3 | 拆分独立 CSS 文件并用 `<style src>` | 失去 scoped，样式全局泄漏 |
| 4 | `v-if` 与 `v-for` 同元素 | 官方 A 级规则 |
| 5 | 单文件超过 400 行还不拆 | 无法维护、无法复用、无法测试 |
| 6 | 组件里直接用 `axios` | 绕过统一拦截器（401、错误规范化会失效） |
| 7 | 业务逻辑写在 `.vue` 里而不抽 composable | 无法复用、无法单测 |
| 8 | 用 `any` | 用 `unknown` + 类型收窄 |

## 九、纯重构的验证方法（本项目实践）

### 9.1 问题：「我看着一样」不是验收依据

拆分一个 1500 行的组件时，改动量以千行计。
**没有人能靠肉眼确认"行为完全没变"** —— 而且漏掉的往往是
最琐碎的差异（多一个空文本节点、class 顺序不同），它们不会报错，只会让样式微妙地偏掉。

### 9.2 做法：SSR DOM 逐字节对比

```ts
// 用 vue/server-renderer 把「重构前」与「重构后」分别渲染成 HTML，然后逐字节比较
import { renderToString } from 'vue/server-renderer'
import { createSSRApp } from 'vue'
import Before from './_Baseline.vue'   // 从 git HEAD 取回的重构前版本
import After from '@/views/Notebook.vue'

const html = await renderToString(createSSRApp(Before))
```

**要点**：

1. **基线必须来自 `git HEAD`**，不能是"我记得原来的样子"
2. 比较前**剥掉 `data-v-*` 作用域属性与注释锚点**（它们每次编译都变）
3. **`class` 属性的 token 顺序也要在比较范围内** —— 本项目就靠这一条抓出了
   `v-on` 对象绑定导致编译器走 `mergeProps` 路径、从而改变属性序列化顺序的问题
4. **把条件分支全部逼出来**：改双方 `ref()` 的初值，让所有弹层/面板同时打开再比一次。
   本项目用这一手覆盖了 9 种状态（下拉全开、查找面板、各种视图模式、反链/出链）
5. 跑完**按 SHA-256 校验还原**被改动的交付文件

### 9.3 附带收益：CSS 声明级比对

除了 DOM，还可以解析所有 `<style scoped>` 规则做声明级比对。
本项目借此发现原文件里有 **3 组从未被任何元素使用的死 CSS 规则**。

### 9.4 覆盖不到的地方（必须诚实说明）

SSR **不执行事件**，所以：

- 交互接线（点击、拖拽、右键、键盘、IME）**不是跑出来的**，是靠逐行审查保证的
- 依赖浏览器布局的行为（溢出检测、`ResizeObserver`）无法覆盖

因此结论应表述为「**静态渲染结构零变化 + 交互经逐行审查**」，
而不是笼统的"完全没变"。

### 9.5 顺带固化的两条经验

1. **纯重构必须是独立提交。**
   本项目修一个「图标漏 import」的 bug（会让 DOM 新增 5 个 `<svg>`）时，
   特意放在重构提交**之后**单独提交 —— 否则"DOM 逐字节一致"这个可验证的结论就没了。
   **能验证的结论比"顺手一起改了"更值钱。**

2. **并行做同类重构时，临时产物目录必须错开。**
   本项目两个并行重构都用了 `frontend/ssr-check/`，
   各自的"清理自己临时文件"动作把对方的删了两次。
   **"清理临时文件"这个正确习惯，在共享工作区里会变成破坏行为。**
