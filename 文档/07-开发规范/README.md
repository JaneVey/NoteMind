## 为什么要写这套规范

项目此前处于"边想边写"的状态，已经出现了几类**真实的不一致**：

| 现象 | 后果 |
|------|------|
| 同一个概念在不同层有不同名字（如"文档" = `document_source` = `DocumentSource` = `KnowledgeDocument`） | 读代码要在脑子里做映射；改代码容易漏改 |
| UI 说"仓库"，代码说 `notebook` | 跨层沟通歧义 |
| 删除语义矛盾（`note` 软删、`notebook` 硬删、中间还挂着级联） | **数据丢失风险** |
| 删除策略只覆盖 14 张表中的 2 张，且无任何说明 | 半年后没人知道哪张表能删、怎么删 |
| 类型定义用 `[key: string]: unknown` 兜底 | TypeScript 保护失效，调用方到处写 `??` |
| 文件规模失控（`AIChat.vue` 1389 行、`Notebook.vue` 1125 行） | 无法复用、无法测试 |

**规范的目的不是"显得专业"，而是让三个月后的自己、以及任何接手的人，不用重新猜。**

## 两条使用原则

1. **规范是"我们项目的规矩"，不是手册摘抄。**
   只写本项目真正执行的条目。阿里手册里的其他内容（如二方库管理、服务器调优）本项目用不上，就不写。

2. **发现规范不合理，就改规范，不要私下破例。**
   破例会让规范失去权威性，最终没人遵守。改规范时在本文件记录修改原因与日期。

### 已知的、有意的偏离

| 规范条目 | 阿里的要求 | 本项目做法 | 理由 |
|---------|-----------|-----------|------|
| 外键 | **不得使用外键与级联** | **保留外键约束，但移除所有 `ON DELETE CASCADE`** | 阿里的理由针对分布式高并发场景；本项目是单机单体，外键的完整性保障收益更大。而**级联删除**才是真正的危害（数据库替应用做删除决策，且与逻辑删除冲突）。详见《04-数据库设计规范》4.3 |
| 时间字段名 | `gmt_create` / `gmt_modified` | `created_at` / `updated_at` | 项目既有约定，且更通用；语义等价 |
| 测试覆盖率 | 语句覆盖 70%，核心 100% | 不设覆盖率指标，只覆盖三类关键目标 | 单人毕设，追求覆盖率是本末倒置。详见《05-测试规范》 |
| 领域模型后缀 | `DO` / `DTO` / `VO` / `BO` | Entity 不加 `DO` 后缀；DTO/VO 保留 | 项目体量小，`Note`/`Notebook` 已足够清晰；加 `DO` 只会增加改动面 |
