# 测试规范

> 依据：《阿里巴巴 Java 开发手册》第 4 章（单元测试）、JUnit 5 与 Spring Boot Test 官方文档
> 生效日期：2026-10-08
> 状态：**本项目当前零测试。本规范定义了务实的起步范围。**

---

## 一、为什么不能"删掉测试"

你的原话是「要不删除？要不就你全权来定吧」。**我的决定是不删**，但理由不是教条：

| # | 理由 | 说明 |
|---|------|------|
| 1 | **论文需要"测试"章节** | 学校要求里明确有系统测试。没有测试，这一章只能靠编 |
| 2 | **答辩会被问** | "你怎么保证功能正确？"——"我手动点了一遍"是常见但很弱的回答 |
| 3 | **它保护你不被自己坑** | 后面要重构数据库、改分层、加 RAG，**没有测试就不知道改坏了什么** |
| 4 | **它是简历/面试的硬指标** | "有单元测试"和"没有"在面试官眼里是两个层次 |

**但也要说清楚：不要为了覆盖率而写测试。** 阿里说语句覆盖 70%，那是**企业级项目**的要求。
本项目只有一个人、几个月时间，追求覆盖率就是本末倒置。

## 二、务实的测试范围：只测三类

### 类别 1：纯逻辑单元测试（最优先，收益最高）

**特征**：不依赖 Spring 容器、不依赖数据库、不依赖网络。**毫秒级执行，随时能跑。**

这是**投入产出比最高**的一类，因为纯函数最容易测，也最容易出错。

**本项目必须覆盖的纯逻辑**：

| 待测目标 | 为什么值得测 |
|---------|------------|
| `ReasoningDelta`（思考链增量计算） | 已有实现，逻辑有分支（累积式/增量式/无变化），**正是容易出 bug 的地方** |
| **文本分块算法**（RAG 核心） | 分块边界处理极易出错；参数化测试（不同 chunkSize / overlap）非常适合 |
| Wikilink 解析（`[[笔记名]]` → 链接关系） | 正则边界情况多（中文、嵌套、别名） |
| 引用上下文组装 + Token 截断 | 截断逻辑错误会导致模型收到不完整上下文 |
| 文件类型判定 / 扩展名映射 | 纯查表逻辑，测起来零成本 |
| 统一响应与错误码映射 | `ErrorCode` → HTTP 状态码的映射表 |

### 类别 2：Service 层业务规则测试

**特征**：需要 mock 掉 Mapper，只测业务规则。

**用 Mockito 伪造 Mapper，不启动 Spring**：

```java
@ExtendWith(MockitoExtension.class)
class NoteServiceImplTest {

    @Mock  private NoteMapper noteMapper;
    @Mock  private NoteNotebookMapper notebookMapper;
    @InjectMocks private NoteServiceImpl noteService;

    @Test
    @DisplayName("删除非空笔记本时应拒绝并抛出业务异常")
    void should_reject_when_deleting_non_empty_notebook() {
        // given
        given(noteMapper.selectCount(any())).willReturn(3L);

        // when & then
        assertThatThrownBy(() -> noteService.removeNotebook(1L))
                .isInstanceOf(BusinessException.class)
                .hasMessageContaining("还有笔记");
    }
}
```

**重点测什么**：

| 类型 | 示例 |
|------|------|
| **业务规则拒绝** | 删非空笔记本 / 用户名重复 / 修改他人数据 |
| **边界值** | 空列表、超大 `page size`、超长文本 |
| **状态机流转** | 文档状态 `pending → processing → done/failed`，禁止非法流转 |
| **多用户隔离** ★ | 用户 A 不能读到用户 B 的笔记 —— **这是答辩必问项，必须有测试证明** |

### 类别 3：接口层集成测试（选最关键的几个）

**特征**：启动 Spring 容器（或 MockMvc），验证"请求进、响应出"。

**只测最关键的链路，不求覆盖所有接口**：

| 待测接口 | 为什么关键 |
|---------|-----------|
| `POST /api/auth/register` + `/login` | 认证是所有功能的前提 |
| 无 Token / 无效 Token 访问受保护接口 → 401 | 鉴权边界（本项目刚修过这个 bug） |
| 越权访问（A 的 Token 读 B 的资源）→ 403/404 | 安全红线 |
| `POST /api/ai/chat/stream` 的 SSE 帧格式 | 刚验证过的核心链路，格式一旦改动就是破坏性变更 |

## 三、明确不测的东西

**不要浪费时间在这些上**：

| 不测 | 原因 |
|------|------|
| Getter / Setter / Lombok 生成的代码 | 没有逻辑，测了是凑覆盖率 |
| MyBatis-Plus 内置 CRUD | 框架自己的功能，不是你的代码 |
| 纯 Controller 转发（只有一行 `return service.xxx()`） | 由类别 3 的集成测试覆盖即可 |
| 前端 UI 交互 | 单人毕设，UI 测试成本极高收益极低（**人工点一遍就够了**） |
| 第三方 API 本身（DeepSeek / 硅基流动） | 不是你的代码；用 Mock 替代真实调用 |

## 四、目录与命名

```
backend/src/test/java/com/notemind/
├── note/
│   ├── service/NoteServiceImplTest.java        ← 与被测类同包路径
│   └── graph/WikilinkParserTest.java
├── knowledge/
│   ├── rag/TextChunkerTest.java
│   └── rag/CitationBuilderTest.java
├── ai/
│   ├── service/ReasoningDeltaTest.java
│   └── controller/AiChatControllerIT.java      ← IT 后缀 = 集成测试
└── support/
    └── TestDataFactory.java                    ← 测试数据构造工具
```

| 规则 | 说明 |
|------|------|
| **目录必须是 `src/test/java`** | 阿里强制：源码构建会自动跳过该目录 |
| 类名以 **`Test`** 结尾 | Maven Surefire 默认只识别 `*Test` / `Test*` / `*Tests` |
| 集成测试用 **`IT`** 结尾 | 便于用 Failsafe 插件单独控制执行时机 |
| **与被测类同包路径** | 便于访问包级可见成员，也便于定位 |
| 一个测试类只测一个类 | |

### 测试方法命名

用 `should_预期行为_when_条件` 或中文 `@DisplayName`：

```java
@Test
@DisplayName("用户 A 不能通过 id 读取用户 B 的笔记")
void should_reject_when_reading_other_users_note() { ... }
```

> 推荐**两个都写**：方法名保持英文（工具链友好），`@DisplayName` 用中文（论文里可直接引用）。

## 五、技术选型

| 用途 | 技术 | 说明 |
|------|------|------|
| 测试框架 | **JUnit 5** | Spring Boot 3+ 默认 |
| 断言 | **AssertJ** | `assertThat(...)` 链式断言，比 JUnit 原生断言可读性好得多。Spring Boot 已内置 |
| Mock | **Mockito** | Spring Boot 已内置 |
| 集成测试 | **`@SpringBootTest` + MockMvc** | |
| 数据库相关 | **Testcontainers**（可选） | 用真实 PostgreSQL 容器跑测试，不污染开发库 |

> **依赖现成**：`spring-boot-starter-test` 已包含 JUnit 5 + AssertJ + Mockito，
> `spring-security-test` 也已引入。**不需要额外加依赖。**

### 关于数据库测试的取舍

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Mock Mapper**（推荐起步） | 快、无依赖 | 不验证 SQL 正确性 |
| Testcontainers 真库 | 验证真实 SQL | 慢、需要 Docker |
| H2 内存库 | 快 | **SQL 方言不同，PG 特有语法（pgvector、JSONB）跑不了** |

**建议**：先用 **Mock Mapper** 覆盖业务规则；对关键 SQL（尤其是向量检索）用 **Testcontainers** 写少量集成测试。
**不要用 H2** —— 本项目有 pgvector 和 JSONB，H2 顶不住。

## 六、执行时机

| 时机 | 跑什么 |
|------|--------|
| 写完一个类 | 跑该类的测试（IDEA 里点一下） |
| 提交前 | `mvn test`（只跑 `*Test`，秒级到十秒级） |
| 打 jar 前 | `mvn verify`（含 `*IT` 集成测试，可能几十秒） |

**Git 提交时**：涉及逻辑变更的提交（`feat` / `fix` / `refactor`）应包含对应测试；
纯文档（`docs`）、配置（`chore`）不需要。

## 七、起步计划（务实版）

不要求一次到位，按这个顺序推进：

| 阶段 | 做什么 | 工作量 |
|------|--------|--------|
| **第 1 步** | 给**已经写好的纯逻辑**补测试：`ReasoningDelta` 优先（它已有分支逻辑，且刚验证过） | 1 小时 |
| **第 2 步** | 之后每写一个 Service，**同步写它的测试**（不回头补旧的） | 随开发进行 |
| **第 3 步** | 认证链路 + 越权访问的集成测试（**答辩必问，必须有**） | 半天 |
| **第 4 步** | RAG 核心（分块、检索、引用组装）的测试，**同时就是论文实验的数据来源** | 与 RAG 开发同步 |

> **第 4 步是隐藏收益**：RAG 的参数对比实验（分块大小 / Top-K / 混合检索）
> 本质上就是"用不同参数跑同一组测试并比较结果"。
> **把它写成参数化测试（`@ParameterizedTest`），实验数据自动产出，论文直接引用。**
> 这样测试不是额外负担，而是论文实验的实现方式。

## 八、禁止事项

| # | 禁止 | 原因 |
|---|------|------|
| 1 | 测试之间互相依赖、依赖执行顺序 | 阿里 AIR 原则：`Independent` |
| 2 | 用 `System.out.println` 代替断言 | 需要人工看的测试不是测试 |
| 3 | 测试依赖外部环境（真实 API、开发库数据） | `Repeatable` 原则；别人跑不通 |
| 4 | 测试里连真实 AI API | 花钱、慢、结果不稳定。必须 Mock |
| 5 | 测试写在 `src/main/java` | 阿里强制 |
| 6 | 为了覆盖率写无意义的 getter/setter 测试 | 自欺欺人 |
| 7 | 断言过于宽松（`assertThat(result).isNotNull()` 了事） | 测了等于没测 |
