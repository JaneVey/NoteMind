# 项目结构与命名规范

> 依据：《阿里巴巴 Java 开发手册（泰山版）》、Vue 3 官方风格指南、Conventional Commits
> 生效日期：2026-10-08
> 适用范围：本项目全部代码、数据库、文档

---

## 一、三条总原则

1. **一致性 > 个人偏好。** 同一种东西只有一种写法。觉得规则不对就改规则，不要私下破例。
2. **名字要自解释。** 需要靠注释解释"这个变量是什么"的名字，就是坏名字。禁止拼音、禁止随意缩写。
3. **同一个概念，在「数据库 / Java / 前端类型 / UI 文案 / 文档」五处必须同名。** 这条最容易破，而且破坏后果最隐蔽。

**前端专有的视图模型**（不存在对应的数据库表，不必与后端同名，但同样要登记）：

| 前端类型 | 用途 |
|---------|------|
| `KnowledgeDocumentDetail` | 文档详情。`extends KnowledgeDocument` 并增加 `rawContent` / `chunkCount`。**列表接口不返回正文** —— 一本 PDF 可能几十万字，列表一次 20 条会传几 MB 而其中 99% 用不到 |
| `ChunkSourceInfo` | 引用溯源信息，对应 `knowledge_chunk.source_info` 这个 JSONB 列的**结构约定**（见《04-数据库设计规范》5.2） |
| `ChatStreamChunk` | SSE 流式分片，与后端 `ChatStreamChunk` 一一对应 |
| `GraphNode` / `GraphEdge` | 知识图谱的节点与边，由笔记与链接**推导**得出，不落库 |
| `PageResult<T>` / `PageQuery` | 分页响应与分页查询参数 |

> **字段名注意**：笔记正文列名是 `content_md`，因此 Java 属性与前端字段都是
> **`contentMd`**（不是 `content`）。同理文件相关字段是 `fileName` / `fileType` / `fileSize`。
> 这三组此前各有重复的对冲字段（`name` + `fileName`、`type` + `fileType`、`size` + `fileSize`），
> 已收敛为与数据库列同名的一组。

### 2.3 关于「仓库」还是「笔记本」

推荐**统一为「笔记本」**，原因：

- **「仓库」在中文开发语境里几乎等同于 Git 仓库**，跨层沟通时容易歧义（"仓库里的笔记"？）
- 「笔记本」对非技术用户更直观
- 代码层已经叫 `notebook`，改文案成本远小于改代码

**待改动**：6 份设计文档中的"多仓库"、`FolderTree.vue`(3 处) 与 `Graph.vue`(2 处) 的 UI 文案。

## 三、后端包结构

### 3.1 决策：按「功能模块」分包，模块内再分层

两种主流方式：

| 方式 | 结构 | 问题 |
|------|------|------|
| ❌ 按层分包 | `controller/` `service/` `mapper/` `entity/` 各自一个大包 | 找一个功能要跳 4 个包；模块边界完全看不出来 |
| ✅ **按功能分包** | `note/` 下自带 `controller/ service/ mapper/ entity/` | 一个功能的内聚在一个包里 |

> 项目现状是**两者混合**：`ai/`、`auth/`、`user/` 按功能，而 `controller/`、`service/`、`entity/`、`mapper/` 又按层 —— 这是最糟的组合，要统一到后者。
>
> （旁证：项目里曾误建一个名为 `{config,controller,service,provider,rag,entity,mapper,common` 的空目录，
> 说明最初打算按层分包。现已清理。）

### 3.2 定稿结构

```
com.notemind
├── NoteMindApplication.java
│
├── common/                     【跨模块复用，不含任何业务】
│   ├── result/                 Result、PageResult
│   ├── exception/              ErrorCode、BusinessException、GlobalExceptionHandler
│   └── util/                   纯工具类（无状态、无依赖）
│
├── framework/                  【基础设施，与业务无关】
│   ├── security/               SecurityConfig、JwtAuthenticationFilter、SecurityUtils、LoginUser
│   ├── config/                 MyBatisPlusConfig、CorsConfig、WebMvcConfig、MinioConfig、RedisConfig
│   └── storage/                文件存储封装（MinioTemplate）
│
├── auth/                       【认证模块】
│   ├── controller/             AuthController
│   ├── service/                AuthService + impl/AuthServiceImpl
│   ├── dto/                    LoginRequest、RegisterRequest、LoginResponse
│   └── util/                   JwtUtils
│
├── user/                       【用户模块】
│   ├── controller/ service/ dto/ vo/
│   ├── entity/                 SysUser、UserProfile
│   └── mapper/                 SysUserMapper、UserProfileMapper
│
├── note/                       【笔记模块】
│   ├── controller/ service/ dto/ vo/
│   ├── entity/                 Note、NoteNotebook、NoteFolder、NoteLink
│   ├── mapper/
│   └── graph/                  知识图谱（它是笔记数据的视图，不独立成模块）
│
├── knowledge/                  【知识库模块】
│   ├── controller/ service/ dto/ vo/
│   ├── entity/                 KnowledgeBase、KnowledgeDocument、KnowledgeChunk
│   ├── mapper/
│   └── rag/                    检索、分块、引用溯源（RAG 子域）
│
└── ai/                         【AI 模块】
    ├── controller/ service/ dto/
    ├── entity/                 AiConfig、AiConversation、AiMessage、PromptShortcut
    └── mapper/
```

**三条硬规则**：

1. **`common` 和 `framework` 不允许出现业务概念**（不许有 Note、Knowledge 之类的类）。
2. **跨模块引用必须显式 import 对方模块的类**，不允许把别人的实体复制一份到自己包里。
3. **包名全小写、单数形式**（`mapper` 而不是 `mappers`）。

### 3.3 每个模块内的固定分层

```
controller/   接收请求、校验参数、调 Service、包装响应
service/      接口（只声明）
service/impl/ 实现（业务逻辑、事务边界）
dto/          对外传输对象（Request / Response）
vo/           返回给前端的展示对象（按需，字段裁剪后）
entity/       与数据库表一一对应
mapper/       数据访问接口（+ resources/mapper/*.xml 放复杂 SQL）
```

## 四、命名规约

### 4.1 Java

| 元素 | 规则 | 示例 |
|------|------|------|
| 类 / 接口 / 枚举 | `UpperCamelCase` | `NoteService`、`ErrorCode` |
| 方法 / 参数 / 成员变量 / 局部变量 | `lowerCamelCase` | `updateNoteTitle` |
| 常量（`static final`） | `ALL_CAPS` 下划线分隔 | `MAX_CHUNK_SIZE` |
| 包 | 全小写、单数 | `com.notemind.note.mapper` |
| 抽象类 | `Abstract` 或 `Base` 开头 | `AbstractNoteParser` |
| 异常类 | `Exception` 结尾 | `BusinessException` |
| 测试类 | 被测类名 + `Test` | `ChatServiceTest` |
| Service 接口 / 实现 | `XxxService` / `XxxServiceImpl` | `NoteService` / `NoteServiceImpl` |
| DTO / VO | `XxxRequest` / `XxxResponse` / `XxxVO` | `CreateNoteRequest` |

**禁止**：

- 拼音混英文（`getYongHu()` ❌）、纯拼音
- 随意缩写（`AbstractClass` → `AbsClass` ❌、`condition` → `condi` ❌）
- 布尔类型 POJO 属性以 `is` 开头（`isDeleted` ❌ → `deleted` ✅）。原因：部分框架序列化时会去掉 `is` 导致字段名对不上。**数据库列名则必须用 `is_xxx`**，两者通过 `@TableField` 映射。
- 美元符 `$`、下划线 `_` 作为命名开头或结尾
- 魔法值（未经定义的常量）直接出现在代码里

### 4.2 Service / Mapper 方法前缀（强制）

| 语义 | 前缀 | 示例 |
|------|------|------|
| 取单个对象 | `get` | `getNote(Long id)` |
| 取多个对象 | `list` | `listNotesByFolder(Long folderId)` |
| 取统计值 | `count` | `countNotesByNotebook(Long id)` |
| 插入 | `save` | `saveNote(Note note)` |
| 删除 | `remove` | `removeNote(Long id)` |
| 修改 | `update` | `updateNoteTitle(Long id, String title)` |

> 好处：不点进方法就知道它返回一个还是一堆、是读还是写。

### 4.3 REST API 路径

| 规则 | 示例 |
|------|------|
| 全部小写，单词间用 `-` | `/api/knowledge-base` ✅ `/api/knowledgeBase` ❌ |
| 用**名词**表示资源，不用动词 | `/api/notes` ✅ `/api/getNotes` ❌ |
| 层级不超过 2 层 | `/api/notebooks/{id}/notes` ✅ 更深用查询参数 |
| 集合用复数（与表名单数区分开） | 表 `note`，接口 `/api/notes` |
| 非 CRUD 动作用子资源或动词后缀 | `POST /api/notes/{id}/move` |
| 路径变量用 `{id}`，不用 `{noteId}`（上下文已明确） | `/api/notes/{id}` |

**统一前缀**：所有接口以 `/api` 开头（前端 `baseURL` 已设为 `/api`）。

### 4.4 数据库

| 元素 | 规则 |
|------|------|
| 表名 | 小写 + 下划线，**单数**，加领域前缀（`note_` / `knowledge_` / `ai_` / `sys_`） |
| 字段名 | 小写 + 下划线（`file_name`） |
| 布尔字段 | `is_xxx`（`is_deleted`、`is_pinned`） |
| 主键 | 统一 `id` |
| 外键列 | `{引用表名单数}_id`（`notebook_id`、`folder_id`） |
| 索引 | `idx_{表名}_{字段}` / `uk_{表名}_{字段}` / `pk_{表名}` |
| 时间字段 | `created_at` / `updated_at`（项目统一，不用阿里的 `gmt_create`/`gmt_modified`） |

### 4.5 前端

| 元素 | 规则 | 示例 |
|------|------|------|
| 组件文件 | `UpperCamelCase.vue`，**必须多词** | `NoteList.vue` ✅ `List.vue` ❌ |
| 页面（views） | `UpperCamelCase.vue` | `KnowledgeBase.vue` |
| 普通 `.ts` 工具 | `kebab-case.ts` | `date-format.ts` |
| Composable | `use` 开头，`camelCase.ts` | `useNoteEditor.ts` |
| Pinia store | `xxxStore.ts`，`useXxxStore` | `noteStore.ts` / `useNoteStore` |
| 类型 | `UpperCamelCase` | `KnowledgeDocument` |
| 常量 | `ALL_CAPS` | `TOKEN_KEY` |

## 五、Git 提交规范（沿用现有）

采用 **Conventional Commits**：

```
<类型>(<范围>): <描述>

[可选正文]

[可选脚注]
```

| 类型 | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构（不改行为） |
| `test` | 增删改测试 |
| `chore` | 构建/依赖/配置等杂务 |
| `perf` | 性能优化 |
| `style` | 格式调整（不影响逻辑） |

**要求**：

- 描述用**中文**，说清"改了什么、为什么"
- 一次提交只做一件事（不要把格式化与功能改动混在一起）
- **禁止把无关文件一起提交**（例如改 A 功能时顺手提交 B 功能的 WIP）

## 六、禁止事项速查

| # | 禁止 | 原因 |
|---|------|------|
| 1 | Controller 注入 Mapper | 绕过 Service，业务逻辑散落 |
| 2 | 直接返回 Entity 给前端 | 会泄露 `password` 等内部字段（`SysUser` 含密码） |
| 3 | 吞异常（catch 后什么都不做或只打日志当没事） | MinIO 那个 bug 就是这么来的 |
| 4 | 数据库外键级联（`ON DELETE CASCADE`） | 数据库擅自删数据，语义失控（见数据库规范） |
| 5 | 前端类型用 `[key: string]: unknown` 兜底 | 类型形同虚设，调用方要写一堆 `??` 兜底 |
| 6 | `v-if` 与 `v-for` 用在同一个元素 | Vue 里 `v-if` 优先级更高，迭代变量还不存在 |
| 7 | 路径/表名/字段名出现大写字母 | Linux 下区分大小写，跨平台会出问题 |
| 8 | 手工拼 SQL 字符串 | SQL 注入。必须用 `#{}` 参数绑定 |
