## 一、命名规约

### 1.1 表名

| 规则 | 说明 |
|------|------|
| 全小写 + 下划线 | PostgreSQL 下不加引号会折叠为小写，混用大小写会出问题 |
| **单数** | `note` 而不是 `notes`（表名表示"一条记录的模板"，不是集合） |
| 加**领域前缀**，让表名自解释 | `note_` / `knowledge_` / `ai_` / `sys_` |
| 禁止保留字 | `user` 是 PostgreSQL 保留字，**必须加前缀**（这正是 `sys_user` 的由来） |
| 长度不超过 32 字符 | |

**定稿表名**（14 张，详见《01-项目结构与命名规范》术语表）：

```
sys_user             用户
user_profile         用户画像
sys_config           系统配置

note_notebook        笔记本
note_folder          文件夹
note                 笔记
note_link            双向链接

knowledge_base       知识库
knowledge_document   文档
knowledge_chunk      知识块

ai_config            AI 供应商配置
ai_conversation      会话
ai_message           消息
prompt_shortcut      快捷指令
```

### 1.2 字段名

| 元素 | 规则 | 示例 |
|------|------|------|
| 普通字段 | 小写下划线 | `file_name`、`chunk_index` |
| 布尔字段 | **`is_xxx`** | `is_deleted`、`is_pinned`、`is_active` |
| 主键 | 统一 `id` | |
| 外键列 | `{引用表单数}_id` | `notebook_id`、`folder_id`、`user_id` |
| 时间字段 | `created_at` / `updated_at` | 统一，不用 `gmt_create` |
| 计数/序号 | `xxx_count` / `xxx_index` | `word_count`、`chunk_index` |

> **Java 侧注意**：数据库列 `is_deleted` ↔ Java 属性必须是 `deleted`（**不能是 `isDeleted`**）。
> 原因见《02-后端开发规范》4.1。用 `@TableField("is_deleted")` 显式映射。

### 1.3 索引命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 主键 | `pk_{表名}` | `pk_note` |
| 唯一索引 | `uk_{表名}_{字段}` | `uk_sys_user_username` |
| 普通索引 | `idx_{表名}_{字段}` | `idx_note_notebook_id` |
| 组合索引 | `idx_{表名}_{字段1}_{字段2}` | `idx_note_user_id_updated_at` |

> **现状**：36 个索引全部使用 `idx_` 前缀 ✅ 已合规（但前缀后的表名需随表重命名同步更新）。

## 二、数据类型选择

### 2.1 时间类型：统一用 `timestamptz` ★

**决策：所有时间字段改为 `TIMESTAMP WITH TIME ZONE`（`timestamptz`）。**

**现状问题**：`init.sql` 用的是 `TIMESTAMP`（即 `timestamp without time zone`），
但《数据库设计文档》写的是 `TIMESTAMP WITH TIME ZONE` —— **文档与实现不一致**。

**为什么必须用 `timestamptz`**：

| 类型 | 行为 |
|------|------|
| `timestamp` | 存"墙上时间"，**不携带时区**。同一时刻在不同时区写入会得到不同值，无法比较 |
| `timestamptz` | **内部统一按 UTC 存储**，读取时按会话时区呈现。跨时区、跨服务器永远正确 |

PostgreSQL 官方明确推荐：**除非有特殊理由，一律用 `timestamptz`**。
本项目将来要部署到云服务器（时区可能不是东八区），用 `timestamp` 会出现"记录时间差 8 小时"这类难查的问题。

```sql
created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

#### ⚠️ Java 侧必须配对使用 `OffsetDateTime`（本项目真实踩坑）

**数据库类型与 Java 类型必须成对修改，只改一边会在运行时报错、编译期完全看不出来。**

| 数据库类型 | 正确的 Java 类型 | 错误的搭配 |
|-----------|----------------|-----------|
| `TIMESTAMPTZ` | **`OffsetDateTime`** | ❌ `LocalDateTime` |
| `TIMESTAMP`（无时区） | `LocalDateTime` | — |

**实际发生的错误**（本项目 2026-10-08）：

```
org.apache.ibatis.executor.result.ResultMapException:
  Error attempting to get column 'created_at' from result set.
  Cause: PSQLException:
    Cannot convert the column of type TIMESTAMPTZ to requested type java.time.LocalDateTime
```

原因：MyBatis 的 `LocalDateTimeTypeHandler` 调用 `rs.getObject(col, LocalDateTime.class)`，
而 PostgreSQL 驱动不会把 `timestamptz` 转成 `LocalDateTime`（它对应 `OffsetDateTime`）。

**这个问题的迷惑性在于**：`mvn compile` 通过、应用能启动、日志里没有任何警告，
**只在真正读取该字段时报 500**。所以「把 timestamp 改成 timestamptz」这件事，
必须同时改：

- 建表脚本：`TIMESTAMP` → `TIMESTAMPTZ`
- 实体字段：`LocalDateTime` → `OffsetDateTime`（含 `import java.time.OffsetDateTime`）
- `MyMetaObjectHandler`：`strictInsertFill(..., OffsetDateTime.class, OffsetDateTime.now())`
- 序列化注解：**移除** `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`

> **为什么移除 `@JsonFormat`**：该 pattern **不含时区偏移**，输出成 `2026-10-08 22:05:20`。
> 前端 `new Date("2026-10-08 22:05:20")` 会按**浏览器本地时区**解析，跨时区必然错。
> 改用 Jackson 默认的 ISO-8601（`2026-10-08T22:05:20+08:00`），前端可被 `new Date()` 正确解析。
> **格式化是前端的展示职责，接口只负责传无歧义的值。**

### 2.2 其他类型约定

| 用途 | 类型 | 说明 |
|------|------|------|
| 主键 / 外键 | `BIGINT` | 对应 Java `Long`；不用 `INT`（避免将来不够用） |
| 自增主键 | `BIGSERIAL` | 单体单库够用；分布式才需要雪花 ID |
| 短文本 | `VARCHAR(n)` | 必须指定长度 |
| 长文本 | `TEXT` | 不加长度限制（PG 的 TEXT 与 VARCHAR 性能相同） |
| 布尔 | `BOOLEAN` | 不用 `TINYINT(1)`（那是 MySQL 习惯） |
| 金额/精确小数 | `NUMERIC(p,s)` | **禁止 `FLOAT`/`DOUBLE`**（精度丢失） |
| 结构化可变数据 | `JSONB` | 见第五节 |
| 向量 | `VECTOR(1024)` | pgvector 扩展；维度必须与 Embedding 模型一致 |
| 枚举 | `VARCHAR(n)` + 应用层枚举 | **不用 PG 的 `ENUM` 类型**（改值要 DDL，迁移麻烦） |

## 三、必备字段

### 3.1 每张表都必须有

```sql
id          BIGSERIAL PRIMARY KEY,
created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

> **现状**：3 张表缺 `updated_at`（`knowledge_chunk`、`message`、`note_link`）。
> 这三张是**只追加**的表（写入后不修改），缺 `updated_at` 是合理的。
> **规范补充**：只追加表可以不设 `updated_at`，但**必须在建表脚本中注释说明这是有意的**。

### 3.2 按需的公共字段

| 字段 | 用于哪些表 | 说明 |
|------|-----------|------|
| `user_id BIGINT NOT NULL` | 所有属于用户的数据 | **多用户隔离的唯一依据**，且必须有索引 |
| `is_deleted BOOLEAN` | 需要软删除的表 | 见第四节 |
| `sort_order INTEGER` | 需要手动排序的表 | 笔记顺序、笔记本顺序 |

## 四、外键与删除策略 ★

### 4.1 先澄清一个概念：外键 ≠ 级联

我此前引用阿里规范说"禁用外键与级联"，这里需要**更精确地说明**，因为两者的风险完全不同：

| 机制 | 作用 | 风险 |
|------|------|------|
| `FOREIGN KEY`（默认 `NO ACTION`/`RESTRICT`） | **阻止**删除被引用的行 | 低。它保护数据完整性，代价是插入/删除时多一次检查 |
| `ON DELETE CASCADE` | **自动级联删除**子行 | **高。数据库擅自替应用做删除决策，且不可恢复** |

### 4.2 本项目的真实危害（必读）

现状：

```
note         有 is_deleted  → 设计意图是「逻辑删除」
note_notebook 没有 is_deleted → 硬删除
但 note.notebook_id → notebook ON DELETE CASCADE
```

**后果**：删除一个笔记本会**硬删除它，并级联删掉下面所有文件夹和笔记，不可恢复**。
而用户按 `note` 的设计预期，会以为笔记进了回收站。

**同一个删除动作，两级语义完全相反。** 这是数据丢失风险，不是风格问题。

### 4.3 决策：保留外键约束，但**移除所有 `ON DELETE CASCADE`**

**为什么不像阿里那样完全去掉外键？**

阿里的理由原文是：「外键与级联更新适用于单机低并发，不适合分布式、高并发集群；
级联更新是强阻塞，存在数据库更新风暴的风险；并且外键影响数据库的插入速度。」

这些理由针对的是**大规模分布式场景**。本项目是**单机单体应用、数据量在万级以内** ——
此时外键带来的**数据完整性保障**远大于它的性能代价。开发期能直接拦住脏数据写入。

**因此本项目采取**：

| 决策 | 内容 |
|------|------|
| ✅ 保留 `FOREIGN KEY` 约束 | 保护引用完整性，开发期就能发现问题 |
| ❌ **移除所有 `ON DELETE CASCADE`** | 删除的级联语义**交给应用层显式决定** |
| ✅ 删除时由 Service 层明确处理 | 见 4.4 |

> 答辩时可以这样表述：「我保留了外键约束保证完整性，但去掉了级联删除 ——
> 因为级联删除会让数据库替应用做业务决策，且与逻辑删除语义冲突。
> 删除的传播规则由 Service 层显式实现，便于加入权限校验和可恢复机制。」

### 4.4 删除策略：逐表明确（待实施）

**规则：每张表必须在 `init.sql` 中注释声明它的删除策略。**

| 表 | 策略 | 说明 |
|----|------|------|
| `sys_user` | **硬删** | ✅ 已实施。本项目无"注销后保留审计"需求；逻辑删除会让 `username` 唯一索引需改为部分索引，在需求明确前不引入这层复杂度 |
| `user_profile` | 硬删 | 随用户删除 |
| `sys_operation_log` | **只追加，不删** | ✅ 已实施。保留期由运维策略决定，本期不做清理 |
| `note_notebook` | **软删** | 删除笔记本时**只标记笔记本**，其下笔记需明确策略（见下） |
| `note_folder` | **软删** | 同上 |
| `note` | **软删** | 有回收站语义 |
| `note_link` | 硬删 | 是派生数据，笔记变更时重建 |
| `knowledge_base` | **软删** | |
| `knowledge_document` | **软删** | |
| `knowledge_chunk` | **硬删** | 是派生数据（可重新解析生成），且量大，软删没意义 |
| `ai_config` | 硬删 | |
| `ai_conversation` | 硬删 | 用户主动删除对话即永久删除 |
| `ai_message` | 硬删 | 随会话删除 |
| `prompt_shortcut` | 硬删 | |

**删除笔记本时的三种可选语义**（Service 层决定，**不是数据库决定**）：

```
a) 仅当笔记本为空时才允许删除（否则报错提示用户先清空）  ← 最安全，推荐毕设采用
b) 标记笔记本已删，并把其下笔记移入"未分类"
c) 标记笔记本已删，并级联标记其下笔记与文件夹已删（需要软删标记）
```

### 4.5 逻辑删除与 MyBatis-Plus 的配合

配置中已设：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: is_deleted
```

**行为**：MyBatis-Plus 的 `deleteById()` 对**声明了该字段的实体**会转成 `UPDATE ... SET is_deleted = true`；
未声明的实体则是真删除。

**风险**：这个差异是**隐式**的 —— 看代码 `noteMapper.deleteById(id)` 完全看不出是软删还是硬删。

**规范要求**：

1. 表是否有 `is_deleted` **必须在建表脚本注释里写明**
2. 查询软删表时**必须自动带 `is_deleted = false`**（MyBatis-Plus 会自动加，但要注意手写 SQL 时不会加）
3. 唯一索引要处理软删冲突：例如 `uk_note_user_id_title` 在软删后仍占用 ——
   解决方案是把 `is_deleted` 加入唯一索引，或改用部分索引（PG 的 `WHERE is_deleted = false`）

## 五、JSONB 使用规范

本项目有两处 JSONB：`knowledge_chunk.source_info`（引用溯源）与 `ai_message.metadata`（引用与用量）。

> **痛点**：JSONB 灵活，但**没有字段约定就没有契约** ——
> 后端写进去什么、前端怎么读，全靠口头约定。而且 JSONB 内的字段无法被类型和约束校验。

### 5.1 规则

| # | 规则 |
|---|------|
| 1 | **必须在本规范中写明字段结构**（见 5.2），不允许"随手塞" |
| 2 | **禁止把需要查询/排序/约束的关键字段放 JSONB**（如 `knowledge_base_id` 必须是独立列，否则无法建索引） |
| 3 | JSONB 只放**展示用的、结构可变的附注信息** |
| 4 | 写入方必须在 Java 侧用**明确的 DTO/记录类**序列化，禁止直接塞 `Map<String, Object>` |
| 5 | 需要按 JSONB 内字段查询时，建立表达式索引（`CREATE INDEX ... ((source_info->>'page'))`） |

### 5.2 字段结构约定（定稿）

**`knowledge_chunk.source_info`** —— 引用溯源的唯一数据来源：

```json
{
  "sourceType": "document",        // document | note
  "documentId": 12,
  "noteId": null,
  "fileName": "Spring实战.pdf",     // 展示用
  "pageStart": 37,                 // 起始页（文档类）
  "pageEnd": 38,
  "headingPath": ["第3章", "事务管理"],  // 标题层级路径（便于展示"来自哪一节"）
  "chunkIndex": 5,
  "score": 0.83                    // 检索时的相似度，写入时可空
}
```

**`ai_message.metadata`** —— 引用与用量：

```json
{
  "citations": [                   // RAG 模式的引用列表
    { "chunkId": 128, "fileName": "Spring实战.pdf", "pageStart": 37, "snippet": "..." }
  ],
  "reasoningContent": "……",         // 思考链（与正文分开存储）
  "usage": { "promptTokens": 1200, "completionTokens": 340 },
  "model": "deepseek-ai/DeepSeek-V4-Flash",
  "provider": "siliconflow",
  "elapsedMs": 3600
}
```

> **注意思考链的存储**：`reasoningContent` 可能与正文一样长，会让 `metadata` 显著膨胀。
> 若体积成为问题，应改为独立列 `ai_message.reasoning_content TEXT`。**建表时先按独立列设计更稳妥。**

## 六、索引规范

| 规则 | 说明 |
|------|------|
| **所有外键列必须有索引** | 否则删除/更新父行时要全表扫描 |
| **所有 `user_id` 必须有索引** | 每个查询都带它 |
| 组合索引**区分度高的列在前** | |
| 组合索引等值条件列放前面，范围条件列放最后 | `WHERE a = ? AND b > ?` → 索引 `(a, b)` |
| 唯一性业务字段必须建**唯一索引** | 不能只靠应用层校验（墨菲定律） |
| `varchar` 建索引要指定长度或改用部分索引 | |
| **向量索引现阶段不建** | 见 6.1 |

### 6.1 向量索引策略（本项目结论）

| 索引 | 问题 |
|------|------|
| `ivfflat`（原方案 `lists = 100`） | 需要**先有数据再建**（要对数据聚类）。几千行规模下每簇不足 100 行，**召回率反而下降** |
| `hnsw`（推荐后续启用） | 无需训练、小数据量表现好、召回率高 |

**当前决策：不建向量索引。** 几千行的顺序扫描 + `<=>` 排序在毫秒级完成，且结果精确。
数据量增长后（如 > 1 万块）再启用 HNSW。

> 这一条建议写进论文的"实验"章节：**索引策略与数据规模的关系**。

## 七、建表脚本规范

```sql
-- ============================================================
-- 表：note  笔记
-- 删除策略：软删（is_deleted）
-- 说明：笔记是用户核心资产，删除进入回收站语义
-- ============================================================
CREATE TABLE note (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT       NOT NULL REFERENCES sys_user(id),
    notebook_id BIGINT       NOT NULL REFERENCES note_notebook(id),
    folder_id   BIGINT       REFERENCES note_folder(id),
    title       VARCHAR(500) NOT NULL DEFAULT '未命名笔记',
    content_md  TEXT,
    word_count  INTEGER      NOT NULL DEFAULT 0,
    is_pinned   BOOLEAN      NOT NULL DEFAULT FALSE,
    is_deleted  BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

COMMENT ON TABLE  note            IS '笔记';
COMMENT ON COLUMN note.user_id    IS '所属用户，多用户隔离依据';
COMMENT ON COLUMN note.is_deleted IS '逻辑删除标记';

CREATE INDEX idx_note_user_id        ON note(user_id);
CREATE INDEX idx_note_notebook_id    ON note(notebook_id);
CREATE INDEX idx_note_folder_id      ON note(folder_id);
CREATE INDEX idx_note_user_id_updated_at ON note(user_id, updated_at DESC);
```

**要求**：

1. 每个表头有注释块：**表用途 + 删除策略**
2. 每个索引名符合 1.3 的格式
3. **不使用 `ON DELETE CASCADE`**
4. 布尔字段显式 `NOT NULL DEFAULT`
5. 字段对齐，便于阅读
6. 建表脚本按领域分组，组间用注释分隔

## 八、迁移规范

schema 变更时：

1. **不允许直接改线上表**，必须写迁移脚本
2. 迁移脚本放在 `backend/src/main/resources/db/migration/`（按 `V{序号}__{描述}.sql` 命名）
3. 每个脚本必须**可重复执行**（用 `IF NOT EXISTS` / `IF EXISTS`）或明确标注"仅执行一次"
4. **涉及数据丢失的变更必须在脚本顶部用注释警告**
5. 项目当前处于开发期，`init.sql` 是唯一真相源；进入有数据阶段后改用迁移脚本

## 九、禁止事项速查

| # | 禁止 | 原因 |
|---|------|------|
| 1 | `ON DELETE CASCADE` | 数据库擅自删数据，与业务删除语义冲突 |
| 2 | `SELECT *` | 字段增减导致映射不一致 |
| 3 | `${}` 拼接 SQL | SQL 注入 |
| 4 | `FLOAT` / `DOUBLE` 存金额 | 精度丢失 |
| 5 | 用 `timestamp` 不用 `timestamptz` | 跨时区出错 |
| 6 | 表名/字段名出现大写 | PostgreSQL 会折叠，跨平台出问题 |
| 7 | 使用保留字作表名（如 `user`） | 必须加前缀 |
| 8 | 把需要查询的字段塞进 JSONB | 无法建索引与约束 |
