## 一、设计原则

| # | 原则 | 含义 |
|---|------|------|
| 1 | **游客优先** | 不登录也能看到产品价值；身份在需要时才索取 |
| 2 | **凭据短命 + 可吊销** | 长期凭据绝不落在 JS 可读的地方；任何凭据都能被服务端立即作废 |
| 3 | **后端是唯一裁决者** | 前端的本地判断只用于体验优化，永远有 401 兜底 |
| 4 | **失败不泄露信息** | 不区分"账号不存在"与"密码错误"；不在响应里暴露内部细节 |
| 5 | **默认安全** | 配置缺失时拒绝启动，而不是静默降级 |

## 二、游客模式与登录触发时机

### 2.1 为什么要改

旧设计是**路由守卫拦截所有页面**，未登录一律跳登录页。
这在后台管理系统里没问题，但**对 C 端产品是反模式** ——
市面产品（ChatGPT、Claude、Notion、Figma）都是**先让你用，到需要身份时才要**。

### 2.2 触发时机

| # | 时机 | 处理 |
|---|------|------|
| ① | 浏览页面、查看界面 | ✅ 允许，不打扰 |
| ② | **发送 AI 消息** | 弹认证框，**保留已输入内容**，登录后续发 |
| ③ | 创建笔记本 / 文件夹 / 笔记 | 弹认证框，登录后自动创建 |
| ④ | 创建知识库 / 上传文档 | 弹认证框 |
| ⑤ | 收藏、保存等写操作 | 弹认证框 |
| ⑥ | 直接访问 `/settings` | 页面内展示"登录后可用"引导（不弹框、不跳转） |

### 2.3 核心机制：pending intent（挂起的意图）

**这是体验的分水岭。** 假设用户打了 200 字点发送：

```
❌ 整页跳转：跳登录页 → 200 字丢失 → 登录回来还要重打   ← 用户直接走人
✅ 模态框：弹出登录框（输入内容仍在）→ 登录成功 → 自动把那条消息发出去
```

统一入口是一个 composable：

```ts
// composables/useAuthGuard.ts
const { requireAuth } = useAuthGuard()

async function sendMessage() {
  // 未登录则弹框并等待结果；用户取消返回 false，输入内容保留在输入框
  if (!(await requireAuth({ reason: '发送消息' }))) return
  await chat.send(inputText)
}
```

**规则**：凡是需要身份的动作，第一行都是 `await requireAuth(...)`。
这样"哪里需要登录"在代码里是**显式**的，不依赖路由表这种间接映射。

### 2.4 登录必须是弹框，不是页面

| 形态 | 用途 |
|------|------|
| `AuthDialog`（模态框） | **主路径** —— 动作触发时弹出，不丢失上下文 |
| `/login` 独立页面 | 次要路径 —— 直接访问链接、邮件跳转、OAuth 回调失败时 |

两者**复用同一套表单组件**，避免两套实现走偏。

### 2.5 本次范围：v1（前端拦截）

游客可以浏览和打字，点发送时弹登录框，登录后自动续发。

**明确不做 v2（后端匿名身份 + 数据认领）**：
那需要引入 `anonymous_user` 概念、真实的游客数据存储、以及登录时的数据迁移。
Notion/Figma 是这么做的，但复杂度显著更高。
**翻案条件**：如果将来要统计"游客转化率"，或需要游客历史记录跨设备保留，再考虑。

## 三、注册与登录标识

### 3.1 现实约束

| 方式 | 需要什么 | 本项目 |
|------|---------|--------|
| 手机号 + 短信 | 运营商资质 + 费用 + 备案 | ❌ **不可行** |
| 微信 / QQ 登录 | 企业主体 + 审核 | ❌ 不可行 |
| **用户名 + 密码** | 无外部依赖 | ✅ |
| **邮箱** | 一个 SMTP 服务（有免费额度） | ✅ |
| **GitHub OAuth** | 个人即可申请 OAuth App | ✅ |

> **手机号为什么不做**：它需要短信服务资质与费用，毕设阶段不可行。
> 而且坦白说，手机号登录的技术含量并不比邮箱高 —— 都是"发一个验证码"。
> **这个取舍会在论文与答辩中说明**，而不是回避。

### 3.2 定稿

```
注册：用户名（唯一，3-50 字符）+ 密码 + 邮箱（必填，唯一）
登录：单一输入框「用户名或邮箱」+ 密码
找回密码：通过邮箱（本阶段只做设计，实现放到后续）
第三方：GitHub OAuth
```

**为什么邮箱必填**：没有邮箱的账号，忘记密码只能作废。这是真实产品的底线。
**为什么不强制邮箱验证**：注册门槛过高会流失用户；未验证的账号先可用，界面提示引导验证。
（GitHub、Notion 都是这个策略）

**为什么登录用统一的 `identifier` 字段**：市面常见（GitHub、Notion 都支持用户名或邮箱登录），
减少用户"我当初用哪个注册的"的困惑。

## 四、凭据方案：双 Token

### 4.1 为什么不是"单个 JWT 存 localStorage"

实现过的旧方案有四个真实缺陷：

| 缺陷 | 后果 |
|------|------|
| XSS 可直接读取 | 攻击者拿到凭据，**24 小时内随便用** |
| **登出无法真正生效** | 客户端清了 token，服务端没有任何吊销机制，token 依然有效 |
| 到期硬踢 | 用户正在写笔记，24 小时一到直接被踢，内容可能丢 |
| 无法查看/管理登录设备 | 用户无法知道"谁在什么地方登录了我的账号" |

### 4.2 定稿设计

```
┌─ Access Token ───────────────────────────────────────────┐
│ 形式     JWT（HS512，带 kid 便于密钥轮换）                  │
│ 有效期   30 分钟（可配）                                    │
│ 载荷     sub(userId) / username / jti / typ=access / exp  │
│ 存放     ★ 只放内存（Pinia）—— 不进 localStorage           │
│ 传输     Authorization: Bearer <token>                    │
│ 校验     服务端验签即可，不查库                              │
└──────────────────────────────────────────────────────────┘

┌─ Refresh Token ──────────────────────────────────────────┐
│ 形式     ★ 不透明随机串（32 字节 base64url），不是 JWT       │
│ 有效期   7 天；勾选"记住我"则 30 天                          │
│ 存放     ★ HttpOnly + Secure + SameSite=Lax Cookie        │
│          ★ Path=/api/auth（限定路径，减少暴露面）            │
│ 服务端   Redis：refresh:{sha256(token)} → {userId, 设备信息} │
│          Redis：refresh:user:{userId} → SET(所有 tokenHash) │
│ 校验     必须查 Redis —— 这正是它可吊销的原因                │
└──────────────────────────────────────────────────────────┘
```

**关键取舍说明**：

1. **Refresh Token 为什么不用 JWT** —— JWT 是无状态的，**天生无法吊销**，
   而"可吊销"正是我们要解决的问题。随机串必须查服务端，所以天然可吊销。
2. **Redis 里为什么存 hash 不存原文** —— 与密码同理：Redis 被读走也不能直接使用。
3. **Access 为什么只放内存** —— 连 localStorage 都不进，XSS 拿不到持久凭据。
   代价是刷新页面会丢，靠启动时静默换回（见 4.4）。
4. **为什么不干脆用 Cookie Session** —— 对同源 Web 来说，Cookie Session 其实更简单也更安全。
   选双 Token 是因为：**安全性已经足够好**（关键在 refresh 走 HttpOnly），
   且**保留了扩展空间**（将来接移动端或开放 API 不用重做）。
   这个权衡本身也是论文里可以写的技术决策。

### 4.3 刷新流程（含两个容易踩的坑）

```
① 请求带 access → 后端返回 401（access 过期）
② 前端拦截 401 → 调 POST /api/auth/refresh（Cookie 自动带上）
③ 成功 → 拿到新 access → **重放原请求**（用户无感）
④ 失败 → 清除状态 → 走 requireAuth 流程
```

**坑 1：并发刷新的竞态。**
页面上 5 个请求同时 401 → 都去刷新 → refresh 被轮换 5 次 → 后 4 次全失败。
**解法**：前端用 **single-flight**（模块级共享同一个刷新 Promise）：

```ts
let refreshing: Promise<string> | null = null
function refreshAccessToken(): Promise<string> {
  refreshing ??= doRefresh().finally(() => { refreshing = null })
  return refreshing
}
```

**坑 2：Refresh Token 轮换 + 重用检测（reuse detection）。**
每次刷新都**作废旧 refresh、签发新的**。如果某个**已经用过的** refresh 又被拿来用，
说明它可能被盗（合法用户和攻击者都持有一份）→
**判定为盗用，立即吊销该用户的全部 refresh**，强制重新登录。

实现：轮换时把旧 hash 写入 `refresh:used:{hash}`（TTL = 原有效期），
收到请求时若命中该 key，触发全量吊销。这是 OAuth 2.0 安全实践 BCP 推荐的做法。

### 4.4 页面刷新后如何恢复

页面刷新 → 内存里的 access 没了。**启动时无条件调一次 `/api/auth/refresh`**：

- 有有效 Cookie → 拿到 access，恢复登录态
- 没有 → 401，当作游客

**为什么不做"本地标记 + 按需刷新"**：那需要在前端存一个非敏感标记来猜"要不要刷新"，
多一个状态就多一种不一致的可能。**无条件刷新一次请求，换来实现的绝对简单。**

## 五、第三方登录：GitHub OAuth

### 5.1 为什么选 GitHub

个人即可创建 OAuth App（无需企业资质），且本项目的目标用户（开发者/学生）真实拥有 GitHub 账号，
能完整演示 OAuth 2.0 授权码流程。

### 5.2 流程（Authorization Code）

```
① 用户点「用 GitHub 登录」
   → 浏览器跳 GET /api/auth/oauth/github

② 后端生成随机 state → 存 Redis（TTL 10min）→ 302 到 GitHub 授权页
   （state 由后端生成并校验，用于防 CSRF）

③ 用户在 GitHub 授权 → GitHub 回调
   GET /api/auth/oauth/github/callback?code=...&state=...

④ 后端：
   · 校验 state（一次性，用完即删）
   · 用 code 换 GitHub access_token
   · 拉取 GitHub 用户信息（id / login / email / avatar_url）
   · 按下方绑定规则找到或创建本地账号
   · 签发我们自己的双 Token（refresh 写 Cookie）

⑤ 302 回前端 → 前端启动流程调 /refresh 拿到 access → 登录完成
```

### 5.3 ⭐ 账号绑定规则（这里有经典安全漏洞）

```
第 1 步  按 (provider=github, provider_user_id) 查 sys_user_oauth
         命中 → 直接登录该 user

第 2 步  未命中 → 按邮箱匹配已有账号
         ★ 仅当 GitHub 返回的邮箱是「已验证」时才允许匹配
         命中 → 建立绑定关系，登录

第 3 步  都未命中 → 创建新账号

★ 安全红线：如果 GitHub 返回的邮箱未验证，绝不能用它自动关联已有账号。
  否则攻击者只要在 GitHub 上填一个受害者的邮箱（不验证），
  就能通过 OAuth 直接登入受害者的账号 —— 这是 OAuth 账号劫持的经典手法。
```

### 5.4 GitHub 不返回邮箱怎么办

用户可以把邮箱设为私密，此时接口拿不到邮箱。而我们的 `email` 是必填。

**处理**：OAuth 首次注册时若拿不到已验证邮箱 → 跳到一个**补全信息页**，要求填写邮箱后
才完成注册。这比"允许空邮箱"更干净（否则"必填"这条规则就有了例外，日后必然出问题）。

## 六、安全设计

### 6.1 密钥管理（服务端）

| 措施 | 说明 | 现状 |
|------|------|------|
| 绝不进 Git | `.env`（已 gitignore）+ `.env.example` 模板 | ✅ |
| 🔴 **启动时强校验** | **生产环境下若 `JWT_SECRET` 仍是默认值，直接拒绝启动** | ❌ 待做（现在只靠注释提醒）|
| **密钥轮换** | JWT 头加 `kid`，服务端同时接受新旧密钥 | ❌ 待做 |
| **用户 API Key 加密** | 用户自填的 AI Key 用 AES-GCM 加密入库；回显只给后四位 | ❌ 待做 |
| **日志脱敏** | 禁止把 token / 密码 / Key 打进日志 | 🟡 需逐处检查 |

> **本项目的真实教训**：开发早期把**真实的 AI API Key 硬编码进了 `application.yml`
> 并提交到公开仓库**。发现时它已在 git 历史里 —— 历史擦不掉，只能吊销密钥。
> 这正是"启动时强校验"比"注释里写一句"可靠得多的原因：**靠自觉必然出事。**

### 6.2 XSS —— 对我们来说是头号威胁

凭据终究要在浏览器里流转，而**本项目的 XSS 入口非常明确**：
用户笔记、AI 回答、文档解析结果**都会被渲染成 HTML**。

```
🔴 严禁 v-html 直接渲染未经处理的用户内容
✅ 所有 Markdown 渲染统一收口到 utils/markdown.ts，必过 DOMPurify
✅ 生产环境配置 CSP（Content-Security-Policy）响应头
```

> 这也是双 Token 方案的价值所在：即使 XSS 发生，
> 攻击者拿到的也只是 **30 分钟的 access token**，而不是 24 小时的。

### 6.3 传输与 Cookie

- 生产强制 **HTTPS** + **HSTS**
- Refresh Cookie：`HttpOnly` + `Secure` + `SameSite=Lax` + `Path=/api/auth`

**CSRF 分析**：refresh / logout 是 POST，而 `SameSite=Lax` 的 Cookie **不会**随跨站 POST 发送，
因此 CSRF 被挡住；且攻击者跨站也读不到响应体。**结论：无需额外 CSRF token**，但要保持 Lax 不降级。

### 6.4 登录防爆破

**设计要点：按 IP 限流为主，不锁账号。**

| 维度 | 策略 |
|------|------|
| **IP** | `auth:fail:ip:{ip}` 15 分钟窗口内失败 ≥ 20 次 → 拒绝该 IP |
| **账号** | `auth:fail:id:{identifier}` 失败 ≥ 5 次 → 响应加入递增延迟（500ms → 1s → 2s） |
| 成功登录 | 清除该账号的计数 |

> ⚠️ **为什么不做"账号锁定"**：那会被攻击者利用来**锁死别人的账号**（拒绝服务）。
> 这是很多系统的真实缺陷。指数退避只惩罚攻击者，不影响正常用户的成功率。

### 6.5 越权与数据隔离（答辩必问项）

| 规则 | 说明 |
|------|------|
| 所有业务查询必须带 `user_id` | 多用户隔离的唯一依据 |
| 禁止只按主键查询后返回 | `GET /note/{id}` 必须校验该 note 的 `user_id` == 当前用户 |
| Service 只接收 `userId` 参数 | 不感知 Security 上下文（见第八节）|

**IDOR（不安全的直接对象引用）是最容易出的漏洞**：把 URL 里的 id 改成别人的，能不能读到？
**必须有测试覆盖。**

### 6.6 密码

- 哈希：**BCrypt**（现状）→ 可升级 **Argon2id**（更抗 GPU 破解）
- 强度：长度优先（≥ 8）+ **常见弱密码黑名单**；
  **不采用**"必须含大写+数字+符号"那类规则（已被证明效果差且降低可用性）
- OAuth 用户的 `password` 为 **NULL**；登录时若为 NULL → 提示"该账号使用第三方登录"

### 6.7 其它

- 端口只绑 `127.0.0.1` ✅ 已做
- 数据库不暴露公网 ✅
- 依赖漏洞扫描：`npm audit` / `mvn dependency-check`
- **登录审计**：登录成功/失败写入 `sys_operation_log`（该表已建但尚无写入方）

## 七、数据模型

### 7.1 `sys_user` 调整

| 字段 | 变更 | 说明 |
|------|------|------|
| `password` | `NOT NULL` → **可空** | OAuth 用户没有密码 |
| `email` | 可空 → **NOT NULL + 唯一** | 账号找回的唯一途径 |
| `email_verified` | 新增 `BOOLEAN NOT NULL DEFAULT FALSE` | |
| `status` | 新增 `VARCHAR(20) NOT NULL DEFAULT 'active'` | `active` / `disabled` |
| `last_login_at` | 新增 `TIMESTAMPTZ` | 登录审计 |

### 7.2 新增 `sys_user_oauth`（第三方账号绑定）

```sql
CREATE TABLE sys_user_oauth (
    id               BIGSERIAL    PRIMARY KEY,
    user_id          BIGINT       NOT NULL REFERENCES sys_user (id),
    provider         VARCHAR(32)  NOT NULL,   -- github / (预留 google、wechat)
    provider_user_id VARCHAR(128) NOT NULL,   -- 第三方平台的用户唯一 ID
    provider_username VARCHAR(128),
    avatar_url       VARCHAR(500),
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX uk_sys_user_oauth_provider ON sys_user_oauth (provider, provider_user_id);
CREATE INDEX idx_sys_user_oauth_user_id ON sys_user_oauth (user_id);
```

**删除策略**：硬删（解绑即删除）。一个用户可绑定多个 provider。

### 7.3 Refresh Token：**放 Redis，不建表**

理由：TTL 天然契合"到期即失效"，且我们已有 Redis。
"查看登录设备"通过 `refresh:user:{userId}` 这个 SET 实现，无需扫全库。

```
refresh:{sha256(token)}       → {userId, ua, ip, createdAt, rememberMe}   TTL 7/30 天
refresh:user:{userId}         → SET of tokenHash                          随会话维护
refresh:used:{sha256(token)}  → "1"   TTL = 原有效期                      用于重用检测
oauth:state:{state}           → "1"   TTL 10 分钟                          防 CSRF
auth:fail:ip:{ip}             → 计数  TTL 15 分钟
auth:fail:id:{identifier}     → 计数  TTL 15 分钟
```

## 八、模块边界（沿用原设计，这部分是对的）

```
Controller 层：从 Security 上下文取 userId，传给 Service
    Long userId = SecurityUtils.currentUserId();
    noteService.getUserNotes(userId);

Service 层：只关心 userId，不感知 JWT / 登录 / Security
```

```java
// ❌ 业务层直接依赖 Security 工具类
public List<Note> getMyNotes() {
    Long userId = SecurityUtils.getUserId();
    return noteMapper.selectByUserId(userId);
}

// ✅ 由 Controller 传入
public List<Note> getUserNotes(Long userId) {
    return noteMapper.selectByUserId(userId);
}
```

**理由**：便于单元测试（直接传任意 userId，不需要伪造 SecurityContext）；
将来被定时任务或管理后台复用时不必依赖 HTTP 上下文。

## 九、接口契约

```
POST   /api/auth/register              注册（username, password, email）
POST   /api/auth/login                 登录（identifier, password, rememberMe）
POST   /api/auth/refresh               用 Cookie 换新 access（无 body）
POST   /api/auth/logout                登出（吊销 refresh + 清 Cookie）
GET    /api/auth/oauth/github          发起 GitHub 授权（302）
GET    /api/auth/oauth/github/callback GitHub 回调（302 回前端）

GET    /api/user/profile               个人资料
PUT    /api/user/profile               改昵称/头像
PUT    /api/user/password              改密码
GET    /api/user/sessions              登录设备列表（进阶）
DELETE /api/user/sessions/{id}         强制下线某设备（进阶）
```

**响应约定**：沿用现有的 `Result{code, message, data}` + `ErrorCode` 分段体系。
新增错误码（2xxx 用户与认证段）：

```
2006  该账号使用第三方登录，请用 GitHub 登录
2007  登录尝试过于频繁，请稍后再试
2008  邮箱已被注册
2009  Refresh Token 无效或已过期
2010  GitHub 授权失败
2011  该 GitHub 账号已绑定其他用户
```

### 10.2 状态与组合式函数

```

                            / logout / refresh / isLoggedIn
composables/useAuthGuard.ts  requireAuth({ reason }) → Promise<boolean>
composables/useAuthDialog.ts 控制认证弹框的显隐与登录成功后的续做
```

### 10.3 路由守卫的处理

**旧守卫的拦截逻辑整个去掉。** 理由：需要登录的判断已经从"进页面"下沉到"做动作"，
再保留一层全拦守卫只会自相矛盾。

守卫只保留 `afterEach` 设置页面标题。`/settings` 这类页面对游客展示引导（不弹框、不跳转）。

### 10.4 `api/request.ts` 改造

```ts
// 请求拦截：从内存取 access（不再读 localStorage）
// 响应拦截 401：
//   · 若该请求本就来自 /auth/* → 直接失败，不尝试刷新（避免死循环）
//   · 否则调 single-flight 的 refresh → 成功后重放原请求
//   · 刷新失败 → 清状态 + 触发 requireAuth 流程
```

**注意**：刷新本身失败必须是**终态**，不能再触发刷新 —— 否则 401 会递归成死循环。

## 十二、明确不做（含翻案条件）

| 项 | 不做的理由 | 翻案条件 |
|----|-----------|---------|
| 手机号 + 短信 | 需要运营商资质与费用 | 有正式运营需求时 |
| 微信 / QQ 登录 | 需要企业主体资质 | 有企业主体时 |
| 后端匿名身份（游客模式 v2） | 需引入 `anonymous_user` + 数据认领，复杂度高 | 要统计游客转化率，或游客历史需跨设备保留 |
| Passkey / WebAuthn | 认证体验的未来方向，但当前投入产出比不合适 | 作为论文的"未来工作"提及 |
| 邮箱验证 | 注册门槛过高；未验证账号先可用 | 需要防刷注册时 |
| 多设备强制下线 | 依赖 `sessions` 接口 | 阶段 4 之后视时间而定 |
