# 问题台账

> **用途**：记录开发过程中遇到/发现的**所有真实问题**，以及根因与解决方式。
> **两个目的**：① 论文答辩的"技术难点与解决方案"章节素材；② 面试时"你遇到过什么坑"的现成答案。
>
> **维护约定**：
> - 每解决一个真问题就追加一行，**不要等到最后补**（回忆会失真）
> - 只记录**真实发生过的**问题，不写臆想的
> - "可讲的点"一列是给答辩/面试准备的**一句话总结**
>
> 排序：按分类分组，组内按发生时间。

---

## 速查总表

### A. 环境与工具链

| # | 现象 | 根因 | 解决 | 可讲的点 |
|---|------|------|------|---------|
| A1 | Spring Boot 3.5.16 看着能用，但已停止维护 | **Boot 3.5 的 OSS 支持已于 2026-06-30 结束** | 升级到 4.1.1 | 选型要查**支持周期**，不能只看"能不能跑" |
| A2 | 升级 Boot 4 后编译报 `com.fasterxml.jackson.datatype.jsr310` 不存在 | Boot 4 迁移到 **Jackson 3**，包名由 `com.fasterxml.jackson` 变为 `tools.jackson` | 删除自定义 `ObjectMapper` Bean（而非改包名） | **不要手写"全家桶"Bean 覆盖框架自动配置**——它会连带让 `spring.jackson.*` 与其他 starter 的序列化模块全部失效 |
| A3 | 引入 Tika 4.1.0 构建失败：`Could not find artifact ... jar:4.1.0` | Tika 4.x 起 `tika-parsers-standard-package` 变为 **pom 聚合包**（只发布 pom，无 jar） | 锁 Tika 3.3.2 | 依赖排查不能只看元数据列表，**要用 HEAD 请求验证产物真的存在** |
| A4 | `pom.xml` 声明了 Tika 却解析不了 PDF | 只引入 `tika-core`——**它只有 API、不含任何 parser** | 换 `tika-parsers-standard-package` | "引入了依赖"≠"功能可用"，要验证到**实际调用** |
| A5 | Spring AI 停在 `1.0.0-M6`（里程碑版） | 里程碑版 API 会变，且与 Boot 3.5 有兼容风险 | 升到 2.0.1 GA | Spring AI 与 Boot 是**硬性版本矩阵**（1.1→Boot 3.4/3.5；2.0→Boot 4.0/4.1），不能单独升一个 |
| A6 | `localhost:6379` 上的 Redis 版本是 **3.0.504**（2015 年微软移植版），且里面有 `sys_dict:*`（**若依框架的字典缓存**） | 那是**另一个项目**的 Redis，不能停 | 本项目 Redis 容器化，映射到 **6380** | dev 用 2015 年的版本、部署用 7，差了十年；且与别的项目共用一个 `db0` 会互相污染 |
| A7 | `D:\docker-data` 里有旧数据，但新建的容器不写那里 | 该目录是**旧 bind-mount 方案**的残留；当前用**命名卷**，数据在 `D:\Docker\DockerDesktopWSL\disk\docker_data.vhdx`（22.5 GB） | 明确区分，业务不混 | Windows 上 PostgreSQL 走 bind mount 要经过 NTFS↔WSL2 转换，PG 对 `fsync`/权限敏感，**命名卷更快更稳** |
| A8 | 前后端各出现一个名字带花括号的空目录 | `mkdir src/{views,components,...}` 是 **bash 语法，PowerShell 不展开** | 删除 | 跨 shell 的语法差异会产生"看起来像模板变量"的垃圾目录 |
| A9 | "残留检查"脚本报告 13 处旧类名未替换 | **PowerShell 的 `-match` 默认不区分大小写**，`\bMessage\b` 把 `Result.message` 也匹配了 | 改用 `[regex]::IsMatch`（区分大小写） | 做批量重构时，**验证脚本本身也可能有 bug**，误报会让人做错误的判断 |
| A10 | 改 `application.yml` 的 `type-aliases-package` 没生效，但命令没报错 | **CRLF 行尾让正则的 `$` 锚点匹配失败** | 改用 `\b` 词边界 | **改配置文件后必须回读确认**，"命令没报错"不等于"改成功了" |
| A11 | 后台跑 `mvn` 的 job 莫名退出 | 命令里用了 `Select-Object -First 30`，**匹配满 30 条后管道提前结束，把 maven 进程一起带走了** | 改为 `*> 日志文件` 重定向 | PowerShell 管道的提前终止会 Kill 上游进程 |
| A12 | 仓库根目录突然多出 `META-INF/`、`org/`、`embedding/` | **`jar xf` 默认解压到当前目录**，我当时只改了后续命令、忘了清理 | 清理并核对绝对路径后删除 | 操作前注意命令的**默认目标位置** |
| A13 | 写文件报 `ReplaceFileW EIO (Win32 1175)` | Docker Desktop 的文件共享**瞬时**占用（`init.sql` 被容器只读挂载） | 重试即可 | 这类错误是瞬时的，不必改方案 |
| A14 | 批量重写 import 的脚本"执行成功"，但 19 个文件的 import 路径被写成了 `@/types/`（模块名为空） | PowerShell 的 `Group-Object` 脚本块里，对**字符串**用了 `$_.Name` —— 字符串没有 `Name` 属性，取到 `$null`，于是所有类型被归到同一个空名分组 | 修正为 `$map[$_]` 后重新拆分 | **又是"验证脚本自身有 bug"**（同 A9/A10）。批量改动后必须**抽查输出内容**，不能只看"命令没报错" |

### B. 框架与依赖

| # | 现象 | 根因 | 解决 | 可讲的点 |
|---|------|------|------|---------|
| B1 | **MinIO bucket 从未被创建**，但启动日志只打了一条不起眼的 warn | `@PostConstruct` 里调用**本类的 `@Bean` 方法**是自调用，穿过 CGLIB 代理后抛 `bean currently in creation`，而异常被 `catch` 吞掉 | 改用 `ApplicationRunner` + **方法参数注入** | **静默失效的典型**：日志"看起来正常"，实际功能从未生效，要等到上传文件才炸 |
| B2 | Redis 配错了应用照样能启动 | Spring Boot 的 Redis 采用**懒连接**，容器启动时不建立连接 | 新增启动自检，主动 ping 并把版本打进日志 | 与 B1 构成一组对照：**"没报错"不代表"连上了"** |
| B3 | Spring AI 2.0 的 `options()` 传构建好的对象编译不过 | 签名是 `<B extends ChatOptions.Builder<?>> options(B)`——**收的是 Builder 不是 Options** | 传 `builder()` | 升级大版本时 API 形状会变，不能照旧记忆写 |
| B4 | `generation.getMetadata()` 当 Map 用编译不过 | 它返回 `ChatGenerationMetadata`（**不是 Map**），但提供了泛型 `get(String)` | 改用 `generation.getMetadata().get(key)` | |
| B5 | 社区 issue 说 `reasoningContent` 恒为 null，怀疑 Spring AI 不支持思考链 | 相关修复 PR 是否已进 2.0.1 未知 | **反编译 jar 字节码**确认：`REASONING_CONTENT = "reasoningContent"` 常量存在，且兼容 `reasoning_content`/`reasoning` 两种字段名 | 遇到"框架好像不支持"时，**直接看字节码比翻 issue 更快更准** |
| B6 | 同上，不换专用 DeepSeek 模块也能拿到思考链 | 2.0.1 的 OpenAI 兼容模块已内置 | 保持用 OpenAI 模块 | 用 OpenAI 兼容模块可一套代码通吃 DeepSeek/硅基流动/百炼/OpenRouter |
| B7 | **流式下拿不到思考链，非流式却能拿到** | 硅基流动的 `DeepSeek-V4-Flash`：非流式默认返回 `reasoning_content`，**流式默认完全不返回**，必须显式传参 | 通过 `OpenAiChatOptions.Builder.extraBody(Map)` 传 `{"thinking":{"type":"enabled"}}` | **同一个模型，流式与非流式的行为可能不一致**。这条不知道能卡一整天 |
| B8 | `reasoning_effort: "high"` 反而让模型不再输出思考 | 实测 `reasoning_tokens` 变为 0——**"提高思考强度"的参数把思考关掉了** | 默认不设置该项 | 对不合理的实测结果要相信数据、不要相信命名 |
| B9 | 原 `sse.ts` 里 `onDone()` 在浏览器里永远不触发，界面卡在"生成中" | **Vite 开发代理不关闭 SSE 连接**（直连后端 2.7s 正常关闭，经代理打满超时） | 前端显式处理 `done` 事件并主动 `reader.cancel()` | 前端**不能只靠"流关闭"判断结束**；生产 Nginx 更要配 `proxy_buffering off` |

### C. 数据库

| # | 现象 | 根因 | 解决 | 可讲的点 |
|---|------|------|------|---------|
| C1 | `init.sql` 写死 `VECTOR(1536)`，而选定的 Embedding 模型是 1024 维 | 原方案按 OpenAI `text-embedding-3-small` 定的维度，后来换了模型 | 统一改 1024（趁无数据，成本 1 行） | **更换 Embedding 模型会使全库向量作废**，必须在有数据前定死 |
| C2 | `init.sql` 的 `ivfflat ... lists=100` 在小数据量下**反而降低召回率** | ivfflat 需要对数据聚类，几千行规模下每簇不足 100 行 | 开发阶段不建向量索引；数据量上来后改 HNSW | 这是论文实验章节的好素材：**索引策略与数据规模的关系** |
| C3 | 删除笔记本会**不可恢复地丢失其下所有笔记** | `note` 有 `is_deleted`（逻辑删除），`notebook` 没有（硬删除），但 `note.notebook_id` 是 `ON DELETE CASCADE` | 移除所有 `ON DELETE CASCADE`，删除语义交 Service 显式决定 | **同一个删除动作两级语义相反** = 数据丢失风险，不是风格问题 |
| C4 | 改数据库时间字段为 `TIMESTAMPTZ` 后，注册登录**全返回 500** | Java 实体还是 `LocalDateTime`。`timestamptz` 的对应类型是 `OffsetDateTime`；MyBatis 的 `LocalDateTimeTypeHandler` 调 `rs.getObject(col, LocalDateTime.class)`，PG 直接拒绝 | 15 个文件 29 处改 `OffsetDateTime`，并移除 23 处 `@JsonFormat` | **数据库类型与 Java 类型必须成对改**。迷惑性极强：编译通过、启动正常、日志无警告，**只在读该字段炸** |
| C5 | `@JsonFormat(pattern="yyyy-MM-dd HH:mm:ss")` 潜藏跨时区错误 | 该 pattern **不含时区偏移**，前端 `new Date("2026-10-08 22:05:20")` 会按浏览器本地时区解析 | 移除，改用 ISO-8601（`+08:00`） | **格式化是前端的展示职责，接口只负责传无歧义的值** |
| C6 | `is_deleted` 只覆盖 14 张表中的 2 张，但全局配了 `logic-delete-field` | 哪些表软删、哪些硬删**没有任何地方写明** | 规范要求每张表在注释块声明删除策略 | 隐式行为（同一个 `deleteById` 有的是软删有的是硬删）是维护陷阱 |
| C7 | 设计文档写 `TIMESTAMP WITH TIME ZONE`，实际建表却是 `timestamp` | 文档与实现不一致，长期无人发现 | 重建时以 `timestamptz` 落实 | 文档与代码不一致时，**先查清哪个是真相** |
| C8 | 用 `citext` 让用户名/邮箱大小写不敏感后，**应用层查重全部失效**：用 `Admin@x.com` 查不到已存在的 `admin@x.com`，于是插入时撞唯一约束，用户看到 **500** 而不是"邮箱已被注册" | **`citext` 的不敏感特性只在参数类型被推断为 `citext` 时才生效。** JDBC 默认把 String 参数按 `varchar` 发送，此时 PG 会选中内置的 `text = text` 操作符（区分大小写），把 citext 彻底绕过 | JDBC URL 加 **`stringtype=unspecified`**，让驱动按 `unknown` 类型发送，由 PG 依列类型推断 | ⭐ 又一个**静默失效**：唯一索引仍拦住重复（数据安全），所以问题只在"报错不友好"上暴露。**且极难定位 —— 同一句 SQL 用字面量能命中、用参数就命中 0 条。** 最终靠 `PREPARE` 声明不同类型参数对比才找到根因 |

### D. 前端

| # | 现象 | 根因 | 解决 | 可讲的点 |
|---|------|------|------|---------|
| D1 | 访问受保护页面报"未登录或登录已过期"，看起来像**登录功能没做** | 路由守卫开头有 `if (import.meta.env.DEV) { next(); return }`——**开发环境直接放行**。于是页面能进、接口 401 | 移除该放行，并补 `redirect` 参数 | **为"开发方便"在鉴权链路上开的口子，会把"没有权限"变成"看起来像功能没做"**，排查成本远高于它节省的便利 |
| D2 | 原 `sse.ts` 是**死代码**（全项目只有定义处引用），且有 3 处缺陷 | 未按 SSE 规范以**空行**切分事件块；未处理多行 `data`；无法区分思考链与正文 | 重写为 `streamChat()`，按类型分发 | 网络分片会把一行切开，按 `\n` 切分会解析失败或丢内容 |
| D3 | 8 个业务组件（ChatHistory 等）**无人引用**，约 880 行死代码 | 早期用组件搭，后来改成全部内联 | 死代码删除或在下沉重构中复用 | 定期做"引用检查"能发现这类沉淀 |
| D4 | `AIChat.vue`(1389 行) 与 `Notebook.vue`(1125 行) **完全没用项目自己的 ui 组件库** | 页面自己手写内联 UI | 拆分时统一到设计系统 | 结果是**两套 UI 风格**：改一次主题要改两个地方，且这两个页面无法复用任何已有组件 |
| D5 | `Notebook.vue` 里有 **10+ 处**重复的"点击外部关闭"逻辑 | 每个下拉菜单各写一份 | 抽 `useDropdown()` composable | Vue 3 的核心优势就是逻辑可脱离组件复用 |
| D6 | `types/domain.ts` 每个接口都有 `[key: string]: unknown` | 为了"省事"放开类型 | 类型必须精确，禁止索引签名兜底 | 这让 **TypeScript 保护完全失效**，调用方被迫到处写 `??` 兜底。**实测：移除全部索引签名后，全项目只暴露出 14 个类型错误** —— 说明这些签名从来不是真的需要 |
| D7 | `DocumentStatus` 定义了 7 个值，后端只有 4 个 | 把同义词全列上"以防万一"（`completed`/`done`/`parsed`） | 枚举必须与后端一对一映射 | "多列几个以防万一"让类型失去约束力 |
| D8 | `v-if` 与 `v-for` 用在同一个元素上（7 处） | — | 用 `computed` 过滤 | Vue 里 **`v-if` 优先级更高**，求值时迭代变量还不存在。官方列为优先级 A（必守） |
| D9 | 前端 `api/` 有约 40 个端点定义，后端**一个都不存在** | 前端照着原型页面"顺手写"的，没经过设计 | 需要先冻结接口契约 | 前后端各写各的必然对不上 |
| D10 | `frontend/` 根目录有 3 张未引用的 `prototype-*.png`，还有 `vite-dev.log` | 早期素材未清理 | 删除 | |
| D11 | 右键会话菜单只切换高亮，**不重置 `messages` 与 `inputText`** | `openConversationMenu()` 与 `selectConversation()` 的职责被拆开了：前者只改 `activeConversationId` | 当时按"纯重构不改行为"原则**原样保留**，待接 AI 模块时修 | **同一份状态被两条路径修改、但只有一条做了完整处理** —— 结果是"高亮跳了、消息区还是上一个会话的，接着发消息就串会话" |
| D12 | `filteredConversations = computed(() => [...conversations.value])` —— 拷贝一份但**不过滤任何东西**；搜索弹窗里 24 条 `prototype-search-N` 结果与日期（`今天`/`N 天前`）都是凭空造的 | 原型阶段的占位实现，后来没接上 | 待接真实搜索时处理 | 这是"**看起来像实现了**"的残留：代码结构完整、能跑、但功能是假的。比明显的 TODO 更危险 |
| D13 | 一个 1563 行的页面文件，被误判为"已有 SSE / 已有思考链 UI / 有多处重复的点击外部关闭逻辑" | 任务书套用了**针对另一个文件**的审计结论 | 子代理执行前先读文件核实，纠正了前提 | **审计结论会过期，也会被张冠李戴。** 委派任务时必须要求执行者先核实前提，而不是假定任务书正确 |
| D14 | 排序菜单里的对勾**从来不显示**（模板 4 处 `<Check>`，但 `Check` 图标从未 import） | 只 import 了部分用到的 lucide 图标 | 结构重构时**故意不补**（以保持 DOM 逐字节一致），随后作为**独立提交**修复 | 这类问题**只在浏览器控制台有一条 warning**，界面上只表现为"少了个对勾"，很容易被当成设计如此 |
| D15 | `.editor-toolbar` 里写了 `shrink: 0` —— **CSS 里不存在 `shrink` 这个属性**（应为 `flex-shrink`），该声明一直被忽略 | 与 Tailwind 的 `shrink-0` 工具类混淆了 | 记录未改（修复会改变布局，需要单独做视觉验证） | **无效 CSS 声明不会报错、不会告警**，静默失效 |
| D16 | 同一工作区里两个 agent 并行重构，各自的临时校验目录互相被对方的"清理"动作删掉（发生两次） | 都用了同一个默认目录名 `frontend/ssr-check/`，且各自认为那是"自己的"、清理时直接删 | 明确告诉仍在运行的一方不要删该目录，并要求它改用独立目录名 | **并行协作必须有目录约定**：临时产物要用可区分的前缀，或由调度方统一分配路径。也说明"清理自己的临时文件"这个正确习惯在共享工作区里会变成破坏行为 |
| D17 | **注册按钮点了没反应** —— 用户名、邮箱、密码都填了，按钮却是灰的 | 初版用 `:disabled="!canSubmit"` 做「禁用式校验」，而 `canSubmit` 要求三项**同时**通过。**按钮禁用时没有任何提示说明是哪一项不合格**，用户完全不知道卡在哪 | 改为按钮始终可点（仅提交中禁用）、逐字段显示错误、首次提交后改实时校验 | ⭐ **禁用式校验的真实代价**：它把"告诉用户哪里错了"的机会也一并禁掉了。而且后端本来就会返回明确文案（"密码长度 8-100 个字符"），**是前端把用户挡在了能看到它之前**。更好的做法是让用户能点、点了就得到反馈 |
| D18 | 登录弹框里出现两段意思相近的说明文字（"登录后即可保存内容…" + "登录后可以保存笔记…"） | 弹框自带 `DialogDescription`，而调用方又传了 `reason`，两段都在讲"登录后能做什么" | `reason` 只在**被动作打断**时传（如"发送消息需要先登录"，那种场景用户需要一个解释）；用户主动点"登录"时不传 | 同一个信息有两个来源就会重复。要区分"用户主动进入"与"被拦下"这两种语义 —— 它们需要的提示并不相同 |
| D19 | 独立登录页 `/login` 与认证弹框**功能完全重叠**，而全站没有任何入口指向它 | 先做了弹框（主路径），又保留了独立页，没有回头审视两者的关系 | 删除独立页；`/login` 与 `/register` 路由改为「打开弹框 + 回到首页」，**URL 仍有效但只有一套认证界面** | 重复的界面面必然走偏。但 URL 本身有价值（可收藏、可作为 OAuth 回调与邮件链接的落地页），所以**删界面不等于删路由** |

### E. 安全

| # | 现象 | 根因 | 解决 | 可讲的点 |
|---|------|------|------|---------|
| E1 | **真实 DeepSeek API Key 硬编码在 `application.yml` 并已进 Git 历史**（仓库还是公开的） | 开发时图方便直接写在配置里 | 移除、改环境变量；用户已吊销密钥 | **密钥一旦进 Git 就等于泄露**——历史擦不掉，只能作废。要用 `git log -S` 主动排查 |

| E3 | `CorsConfig` 同时设 `allowedOriginPatterns("*")` 与 `allowCredentials(true)` | — | 改为显式域名白名单 | **任意第三方站点都能发起携带凭据的跨站请求**。Spring 特意让 `allowedOrigins("*")` 直接报错来防这种误用，但被绕过了 |
| E4 | 未认证请求返回 **403** 而非 401 | 未配置 `AuthenticationEntryPoint` | 补 401/403 处理器 | 前端因此无法区分"未登录"与"无权限" |

## 重点问题详解

> 以下 6 个最值得在答辩/面试展开讲，因为它们体现了**排查方法与工程判断**，而不只是"改了个 bug"。

### 1. MinIO bucket 从未创建（B1）—— 静默失效

**发现方式**：不是功能报错，而是在写"启动自检日志"时注意到只有一条 warn。

**根因链**：
```
@Configuration 类被 CGLIB 代理
  → @PostConstruct 里调用本类 @Bean 方法 = 自调用
  → 代理拦截时发现"minioConfig 这个 Bean 还在创建中"
  → 抛 BeanCurrentlyInCreationException
  → 被 catch (Exception e) 吞掉，只打了一条 warn
  → bucket 从未创建，但日志"看起来正常"
```

**为什么值得讲**：这是**异常被吞掉造成静默失效**的教科书案例。它的危害不是"报错"，而是
**让人以为一切正常**，直到真正上传文件才发现。修复方式（`ApplicationRunner` +
方法参数注入）本身很简单，难的是**意识到要去查**。

**修复后的验证方式**：把失败日志从 `warn` 提升为 `error` 并带上 endpoint，
让"MinIO 没起来"在启动日志里一眼可见。

### 2. TIMESTAMPTZ 与 LocalDateTime 不匹配（C4）—— 只在运行时炸

**发现方式**：改完数据库类型后跑端到端回归，注册登录全返回 500。

**为什么值得讲**：这是一个**跨越"编译期/启动期/运行期"三层检查**的问题：
- `mvn compile` 通过（Java 类型与 SQL 无关）
- 应用启动成功（不读该字段就不触发）
- 日志无任何警告
- **只有真正 SELECT 出该字段时才抛异常**

**教训**：数据库类型与 Java 类型是**一对必须同时修改**的绑定关系。
`TIMESTAMPTZ ↔ OffsetDateTime`、`TIMESTAMP ↔ LocalDateTime`。
这条已写入项目规范，作为强制条款。

**顺带发现**：`@JsonFormat(pattern="yyyy-MM-dd HH:mm:ss")` 不含时区偏移，
前端 `new Date()` 会按浏览器时区解析 —— 属于同一类"看着没问题、跨时区就错"的隐患。

### 3. 删除笔记本会静默丢数据（C3）—— 语义冲突

**发现方式**：做数据库审计时，把"哪些表有 `is_deleted`"和"哪些外键带 CASCADE"两张表放在一起看。

**问题**：
```
note          有 is_deleted  → 设计意图：逻辑删除（回收站）
notebook      没有           → 硬删除
note.notebook_id → notebook ON DELETE CASCADE
```
→ **删除笔记本 = 硬删它 + 级联删掉下面所有笔记，不可恢复**，而用户以为进了回收站。

**工程判断**：这里我做了一个**有意偏离《阿里巴巴 Java 开发手册》**的决定。
阿里强制"不得使用外键与级联"，但它的理由针对的是**分布式高并发**场景
（级联更新是强阻塞、外键影响插入速度）。本项目是**单机单体、数据量万级以内**，
此时外键的**完整性保障收益大于性能代价**。

**所以本项目的决策是**：
- ✅ 保留 `FOREIGN KEY`（阻止脏数据）
- ❌ 移除所有 `ON DELETE CASCADE`（不让数据库替应用做删除决策）
- ✅ 删除的级联语义由 Service 层显式实现（可加权限校验与可恢复机制）

**答辩可以这样讲**：「我保留了外键约束保证完整性，但去掉了级联删除，因为级联删除
会让数据库替应用做业务决策，且与逻辑删除语义冲突。删除的传播规则由 Service 层显式实现。」

### 4. 路由守卫的开发环境放行（D1）—— 掩盖了鉴权

**现象**：访问受保护页面报「未登录或登录已过期」，第一反应是"登录功能还没做"。

**真相**：登录功能**早已完成**，问题在于守卫开头这段：
```ts
if (import.meta.env.DEV) { next(); return }   // 开发环境直接放行
```
形成隐蔽组合：**前端放行让页面能进，后端仍要求 JWT 所以接口 401**。
用户既不会被引导登录，也会误判为功能缺失。

**为什么值得讲**：它体现了一个通用原则 ——
**为了让开发"方便"而绕过安全/鉴权链路，代价是把"没有权限"伪装成"功能没做"，
排查成本远高于它节省的便利。** 而且它会让开发阶段永远验证不到真实登录流程。

### 5. 流式与非流式的模型行为不一致（B7/B8）—— 供应商差异

**排查过程**：
1. 后端 SSE 跑通，但**没有 reasoning 事件**（统计为 0）
2. 先怀疑框架：反编译 jar 确认 Spring AI 2.0.1 **已支持** `reasoningContent`
3. 再直接 `curl` 问 API：**非流式有思考、流式没有**
4. 逐参数实测：`thinking:{type:enabled}` ✅(22 分片)、`enable_thinking:true` ✅(82)、
   `include_reasoning:true` ❌(0)
5. 又发现反直觉现象：`reasoning_effort:"high"` 在非流式下**把思考关掉了**

**解决**：通过 `OpenAiChatOptions.Builder.extraBody(Map)` 传供应商特有的参数，
并把它做成配置项（`app.ai.thinking-param`），因为不同供应商写法不同。

**为什么值得讲**：这是**"同一份标准 API 在不同供应商下有不同行为"**的典型。
排查方法值得复述：**先排除自己的代码 → 再排除框架 → 最后用最原始的方式（curl）问服务本身**。

### 6. 范围恐慌（F1）—— 概念混淆导致的停滞

**现象**：项目停滞约一个月，理由是"要完成 AI 对话，Agent 对应的流程不能少，
但完整的 Agent 我没信心做"。

**诊断**：把 5 件难度相差 10 倍的事统称为 "Agent"：

| 被统称 | 实际是什么 | 难度 |
|--------|-----------|------|
| 多轮对话 | 持久化 + Prompt 组装 | ★ |
| SSE 流式 | fetch + ReadableStream | ★ |
| 思考链路 | API 返回的一个字段 | ★ |
| RAG | 检索管道（**不是智能体**） | ★★★ |
| 建议→确认→写入 | 结构化输出 + 确认 + 应用 | ★★ |
| 真 Agent | 工具调用循环 | ★★★★ |
| 多 Agent | 编排/通信/仲裁 | ★★★★★ |

**关键结论**：真正难的只有最后两项，而**原方案本来就排除了它们**
（方案定位文档里写着"❌ AI Agent 自动执行"）。
**动摇的不是方案，是对方案的信心。**

**处理方式**：产出《范围决策书》，写明做什么/不做什么/**以及什么条件下才翻案**——
把"要不要做 Agent"从**每次开工前的情绪判断**变成**有明确触发条件的工程决策**。
